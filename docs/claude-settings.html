Claude Code settings

The Claude Code settings p4 writes into a project's local settings file, where that file is, how p4 writes and records it, the watcher that checks it again when Claude Code or a p4 plugin changes, every other key and variable placed once, every kind of approval card with how it is settled before a session's start, and the hook answers p4-phi leaves to the app. Every page of the documentation named here is under https://code.claude.com/docs/en/, so nobody researches these again.

How p4 keeps them

  • p4conf.keep_settings(project), in both copies of p4conf.py, writes the keys of WRITES, p4's two allow rules, its ask rule on the archive tool, its deny rule on the model tool and the P4_* variables of the next sections into the local settings file of a session started in project, merged with what is there.
  • The ask rule and the deny rule serve p4-phi's session tree, so the keeper writes them only where p4-phi is installed for the project and no settings file switches it off, and takes its own two entries out where it is not. p4-phi's own copy runs only where p4-phi is loaded, and p4-temportal's copy reads installed_plugins.json and enabledPlugins.
  • The two allow rules, approved by ezexe, are Bash(python -I -X utf8 "<scripts>/phi.py" *) and Bash(python -I -X utf8 "<scripts>/p4.py" sync *), with <scripts> the running copy's scripts folder on that machine, and on Windows the same two in the PowerShell(...) form. For an installed copy that folder is in Claude Code's plugin cache with the version in its path, ~/.claude/plugins/cache/p4-marketplace/p4-phi/<version>/scripts, so each update of the plugin moves it, and the check a changed plugin version runs at the next SessionStart writes both rules for the new folder beside those of each older version folder Claude Code's plugin cache still holds. A session still running the version before keeps that version's folder, by plugins/loading.md, "When auto-update runs": "The running session keeps the versions it loaded", and "Cleanup of previous versions": Claude Code "removes that directory in a background cleanup 14 days later, so a session that already loaded the old version keeps running". So its rules stay until that folder is gone, and the keeper drops them at its next run after. Each rule names one folder exactly: permissions.md, "Wildcard patterns", says "A * in a Bash rule matches any text, including spaces", so a * in place of the version would allow more than these scripts, and a rule wider than the two ezexe approved is ezexe's to write. Each is one entry of permissions.allow that p4 owns: it adds and removes only its own entries, never reorders or drops another rule, rewrites them when the plugin folder moves, and never writes back an entry deleted by hand. Only p4-phi's copy of p4conf.py writes them, and the store's claude section sets allowRules to false to have p4 remove them. The tools the p4 hooks modules declare, mcp__p4-phi__note, mcp__p4-phi__done, mcp__p4-phi__tree, mcp__p4-phi__goal, mcp__p4-temportal__lifetime and mcp__p4-native__native, need neither rule. Until the set of the section Approval cards and a session's start is in force they have no rule of their own, so in a permission mode that asks, Claude Code asks about a tool's first call as it does for any MCP tool. With the set in force both copies of p4conf.py write an allow rule for each, the tool's full name, as entries of permissions.allow p4 owns under the record's toolRules, kept by the same rule as the two above: a rule a person already wrote stays theirs, and the entries go when the set is taken out of force.
  • The ask rule, approved by ezexe, is mcp__ccd_session_mgmt__archive_session under permissions.ask, written by both copies of p4conf.py in every project where p4 runs. An explicit ask rule prompts in every permission mode, bypassPermissions included, so the app shows its approval card before every archive call, and p4-phi keeps no archive guard of its own. Source, permission-modes.md, "Actions no mode auto-approves". It is p4's own entry by the same rule as the allow rules, recorded under askRules: a user's own ask rules are never reordered, taken over or removed, and an entry deleted by hand is never written back. A store whose phi.upkeep is true wants no such rule, since ezexe decided that a session archives the finished, landed sessions it started by itself: the keeper writes none there and takes its own entry out, and the app's own rule holds, desktop.md, "Work across sessions": "You get an approval card before Claude archives a session, except in Auto mode and Bypass permissions mode". phi.py upkeep on and off write the setting and run the keeper at once. A store started anew loses the record of the entry p4 wrote, and the keeper then leaves that entry as a person's, so the card comes before every archive though phi.upkeep is on. With the set of the section Approval cards and a session's start in force, an entry that is exactly p4's own text is taken out there, and no other ask rule is touched.
  • The deny rule, approved by ezexe, is mcp__ccd_session_mgmt__set_session_model under permissions.deny, written by both copies beside the ask rule and kept by the same rule under denyRules. A session's model is chosen on its start call and never changed after, and the deny rule replaced p4-phi's own refusal of the call. Source, permissions: "Deny rules prevent Claude Code from using the specified tool", and "Rules are evaluated in order: deny, then ask, then allow."
  • What a store wants is the claude section of its p4.json, read when set and never written by default. autoMemoryDirectory names the store's temportal/memory unless the section sets it to false. attribution.commit is written only when the section gives a text, and no store gives one yet.
  • Any other key the section names is never written. The watcher names it with its value in one systemMessage, once for each value, and says when it is a permission or security key, which ezexe decides.
  • autoMemoryDirectory is not written when the user, project or managed settings file already names another folder. A key p4 owns is removed when the store stops wanting it.
  • The record is .claude/p4/claude-settings.json, which the store's seeded .gitignore keeps on one machine. For each settings file by its path it holds each owned key with the value written and the GEN of the copy that wrote it. It also holds the Claude Code binary, its size, time and version, each p4 plugin's version, the claude section last applied and the keys already named.
  • A value already in the file that equals what p4 would write becomes p4's. A value that differs from its entry was set by hand, leaves the record and is never touched again. A key the record owns that is missing from the file is written again.
  • The write goes through a temp file and os.replace, retried on Windows, two-space indented, with the file's own key order, under the store's .settings.lock. Nothing is written when nothing changes, and a file that is not a JSON object is left as it is with one line on stderr.
  • When p4 creates the file and git does not ignore it, .claude/settings.local.json goes into the repository's info/exclude.

When the check runs

  • p4conf.migrate_layout, which every plugin calls at its start, runs the check after a layout move and at a store's first start, a store with no record yet.
  • The layout handler of p4-phi's hook.py, at every SessionStart, runs p4conf.watch. It reads the binary of the process CLAUDE_PID names, by QueryFullProcessImageNameW on Windows, /proc/<pid>/exe on Linux and ps -o comm= elsewhere, and runs it with --version only when its path, size or time differ from the record. Without CLAUDE_PID it reads claude on the PATH and records the reading as weak.
  • A changed binary, a changed p4 plugin version or a changed claude section runs the whole check. A newer Claude Code also leaves the versions between the recorded one and the new one in the record's changelog part, as the sections the changelog read owes.
  • The settings handler runs p4conf.watch at a ConfigChange whose source is local_settings, project_settings or user_settings. It looks only at the keys the record owns and never blocks.
  • The changelog read, p4conf.read_changelog, runs in the layout handler's own time at every SessionStart. It takes the ## <version> sections of Claude Code's own cached changelog, cache/changelog.md under the configuration folder, after the recorded version up to the new one, and searches them for p4conf.WATCHED and the terms of every entry of claude_code_limits.json. Each read is a section of .claude/p4/phi/claude-code-watch.md, and each hit reaches the next prompt of one session as one line naming the term, the version and the issue to act on.
  • P4_PHI_SETTINGS=0 turns the watcher off.

The security class

  • No key of this class is written by p4 without ezexe's yes, and ezexe's yes covers only the two allow rules above, the ask rule on the archive tool, the deny rule on the model tool, p4's own P4_* variables under env and, by the one approval card of phi.py cards on, the allow rules for p4's own tools that the set of p4conf.CARD_SET names: every key of the topics "Permission settings", "Sandbox settings", "Authentication and providers" and "Enterprise and managed settings" of settings-reference.md, the table "Exceptions to managed settings precedence" of settings.md, and permissions.allow, permissions.additionalDirectories, extraKnownMarketplaces, env, hooks and disableAllHooks.
  • p4conf.SECURITY lists them, and p4conf.security(key) is true for each and for every dotted key under one.
  • permissions.allow rules in settings files do not pre-approve writes to the protected .claude folder, by permission-modes.md, so no rule would cover p4's own writes under .claude/p4/.

Decisions in short

  • p4 writes one key for every project, autoMemoryDirectory, into the project's local settings file, as #246 plans.
  • p4 writes one more key only when a store names its value, attribution.commit, into the same file.
  • p4 writes each of its own settings a store changes from its default as a P4_* variable under env of the same file.
  • p4 writes nothing into the shared .claude/settings.json, nothing into user settings, no env variable but its own P4_* ones and no permission or sandbox key without ezexe's yes.
  • The record of what p4 owns sits in the store, in one ignored file for each machine, and never inside a settings file.
  • The watcher learns the running version from the binary named by the documented CLAUDE_PID, run with --version, and not from claude on the PATH.
  • The merge is safe while sessions run if it rereads, touches only owned keys, replaces the file in one rename and skips writes that change nothing.

The keys p4 writes

The development project's local settings file is the reference: a fresh project's file holds the same keys in the same order, apart from ezexe's own enabledPlugins and autoMemoryEnabled, which the keeper never writes, the defaults disableAllHooks and disableSkillShellExecution, which the reference holds as ezexe wrote them and the keeper leaves to the app, and the paths. Writing those two defaults changes nothing, and a local false would override a true ezexe later sets in user or project settings. The two plugins' copies of the keeper may run in either order at a start, so env can come before permissions. A local autoMemoryEnabled of false would turn off the auto memory autoMemoryDirectory points at the store.

The P4_* variables

Every setting of p4conf.DEFAULTS that steers p4, and each phi key read only when a store sets it, has a variable of its own. p4.json stays p4's own source, and the keeper mirrors each setting it changes from its default under env of the project's local settings file, so that file shows every changed setting and a project has nothing to set by hand.

  • The name is P4_ and the setting's dotted path in upper case with each dot an underscore, by p4conf.env_name. The one exception is phi.watch_s, whose variable is P4_PHI_WATCH_SECONDS, since P4_PHI_WATCH_S is puppeteer.py's older tick for one run. The older switches P4_SCRATCHPAD_ASKS, P4_RECALL_INJECT and P4_PHI_ISSUES keep their names and mean what their setting means, and their readers in scratchpad.py, hook.py and issues.py read them as p4conf does.
  • The keeper writes a variable for each setting the store changes from its default, and for a key read only when set whenever the store sets it. It records each one in the ownership record as the p4-owned key env.<name>, and removes it once the setting is back at its default; env goes with the last of p4's variables. A variable a person wrote, changed or deleted is never touched, and one a person wrote that already holds p4's value is neither taken over nor removed. Every other entry of env is ezexe's and stays as it is.
  • The keeper writes no entry for a variable set elsewhere, in the session's environment with a text p4 did not write or in the user, project or managed settings file, since the local entry would override it, and removes its own entry once the variable appears there, as it does for autoMemoryDirectory.
  • The record keeps, for each local file, the variables last written there and the texts p4 wrote before and replaced or removed, or that a person then changed or deleted, so each local file of a store follows p4.json at its own session's next SessionStart.
  • p4conf.load reads a variable ahead of p4.json only when a person set or changed it, in the local file or in the shell. One the record says p4 wrote, now or before, is passed over, so an edit to p4.json reaches the next hook while a session still holds the entry for the old value. A variable applies only to the store of the session's own project, the one CLAUDE_PROJECT_DIR names, so a shared home store keeps its own p4.json. A record edited by hand into another shape lets no variable through, and p4.json alone holds; the keeper then adds and removes no P4_* entry, and drops each part of the record of another shape before it reads it.
  • A running session keeps the environment it started with until it restarts: in -p mode the variables the keeper wrote at a SessionStart were absent from that session's later hooks, and a variable removed from the file stays set. Source for the removal, env-vars.md: "Removing a variable from the file doesn't unset it in a running session; the removal takes effect the next time you launch claude."
  • Before the workspace is trusted the env block of the local file does not apply, and p4.json alone holds. Source, settings-reference.md, key env: "From project and local settings: after you trust the workspace, or at startup in -p mode, which never shows the trust dialog".
  • Encoding, by p4conf.env_text: a bool is 1 or 0; a string is written as it is, unless that text would read back as another value, and then as JSON; every other value is compact JSON, such as ["log","out"].
  • Decoding, by p4conf.env_value: an empty value is unset; for a key that takes a bool, 1, 0, true and false in any case; otherwise JSON, and the text itself for a key that takes a string. Each value is checked against what the key's reader in p4 takes, by p4conf.ENV_SCHEMA or the default's type, with the items of a list or an object and the strings a key knows. A value that does not fit, or that fails to read at all, is passed over with one line on stderr, so the setting falls back to p4.json's value, which is the default unless the store changed it. A value of the right type out of range is then kept at the default by the reader's own check, such as phi.apply_caps for the tree caps. P4_TEMPORTAL_CACHE is merged over the default rules as p4.json's temportal.cache is.
  • p4conf.configure puts back a module constant a variable set once the variable is gone, since a process that runs hooks in turn keeps its globals.
  • The desktop app's launch environment wins over the file for a variable it already sets, and p4 sets none there. Source, settings-reference.md, key env: "Claude Code ignores an env value from a settings file for a variable that environment already sets."

Why env reaches p4's hooks:

  • env-vars.md: "Claude Code writes each env entry into the process environment, replacing the value inherited from the shell."
  • hooks.md: "A hook process inherits the parent environment, apart from the OTEL_* exporter variables".
  • Measured on 2026-11-17 with Claude Code 2.1.322 and both plugins loaded from one checkout by --plugin-dir: a P4_ variable in a scratch project's local file reached its SessionStart and UserPromptSubmit hooks. With P4_PHI_MAX_DEPTH 5, written by the keeper, in the environment and p4.json edited to 7, p4conf.load in both hooks read 7, and the keeper rewrote the entry to 7 for the next start.

Where the local file is

  • In a git repository Claude Code reads and writes the local file at the repository root, and in a worktree at the main checkout's root.
  • On Windows, outside a git repository, and when the root's .git or .claude is not owned by the user, the file stays beside .claude/settings.json in the session's primary working directory.
  • A desktop worktree session reads project settings from the main checkout's root, and hooks there get ${CLAUDE_PROJECT_DIR} pointing at it.
  • So p4 writes the file at ${CLAUDE_PROJECT_DIR}/.claude/settings.local.json on Windows and outside git, and at the main checkout's root otherwise. A command-line session started in a worktree or a subfolder on Windows gets its own copy of the key there, with the same absolute path to the main checkout's store.
  • Source, settings.md, section "Where Claude Code keeps the local file in a git repository": "If you start Claude Code in a subdirectory of a git repository, it reads and writes that file at the repository root and applies the approval across the whole repository." and "When the file stays with .claude/settings.json instead: outside a git repository, when the repository root is your home directory, on Windows, or when the repository root or its .git or .claude entry isn't owned by your user."
  • Source, worktrees.md, section "What worktrees share with the main checkout": "In a worktree session you start from the desktop app, Claude Code reads project configuration such as settings, hooks, skills, agents, commands, and .mcp.json servers from the main checkout's root."
  • When p4 creates the file, it adds .claude/settings.local.json to the project's .git/info/exclude unless git check-ignore already reports it ignored, as it does for .claude/p4/.
  • Source, settings.md: "If you created the file by hand and Claude Code hasn't written to it yet, add it to .gitignore yourself." and permissions.md: "When the file is tracked in git, or .claude is a symlink, Claude Code treats it as repository-supplied instead and holds its rules until you trust the folder."
  • p4_memory.chosen_by_user at p4_memory.py:156-171 counts the local file as the repository's whatever git says. By the line above it should count an untracked local file as the user's own, as #246 already lists.

How p4 writes it

  • It reads the file, parses it, and leaves a file that is not valid JSON as it is, with one line on stderr, as p4conf.load already does for p4.json.
  • It changes only keys its record owns, never cuts a list, and never adds a key of its own beside Claude Code's.
  • It writes through a temp file in the same folder and os.replace, retrying a few times on Windows when another process holds the file.
  • It writes nothing when the merged content equals what is there, so no ConfigChange fires in the running sessions for nothing.
  • It reads the file back after writing and logs a lost key, which the next check writes again.
  • It holds a lock file in the store while it writes, as migrate_layout holds .layout.lock, so the hooks of one start do not write in turn.
  • It writes two-space indented JSON with a final newline and keeps the order of the keys already there.

Why the merge is safe while sessions run:

  • Claude Code watches the file and applies most edits to a running session, so a running session picks up the key without a restart. Source, settings.md: "Claude Code watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to permissions, hooks, and credential helpers such as apiKeyHelper."
  • Claude Code writes the same file itself, for "don't ask again" approvals and for a project plugin removed by /plugin, and documents no lock on it, so the reread and the single rename keep the window for a lost update to the moment between read and rename. Source, settings.md: "When Claude asks permission to run a Bash command and you choose \"Yes, and don't ask again\", Claude Code saves that permission approval here as an allow rule." The only documented config lock, CLAUDE_CODE_CONFIG_LOCK_WAIT_MS, is on ~/.claude.json.
  • A bad write is costly: "Settings Error: a user, project, or local file has invalid JSON or a value the schema rejects. At the start of an interactive session Claude Code shows a dialog that lets you fix the file with Claude's help, exit, or continue without the broken settings." So p4 writes only valid JSON and only documented keys with documented types.
  • The file is the user's by the docs, so p4 never removes a key it does not own. Source, settings.md: "To change a setting for yourself in one project without changing it for your teammates, save it in .claude/settings.local.json inside the project."

The ownership record

  • Where: one file in the store, .claude/p4/claude-settings.json, listed in the store's seeded .gitignore beside phi/catchup.json, so p4.py sync never carries it to another machine.
  • What it holds: for each settings file p4 wrote, by its absolute path, each owned key with the value written and the GEN of the copy of p4conf.py that wrote it; the Claude Code version and binary path last seen; and the version of each p4 plugin last seen.
  • The rule, the same as _written in p4conf.load: a key whose value still equals its record entry is p4's and may change at a higher GEN or be removed when a later version stops owning it; a key whose value differs was set by hand, leaves the record and is never touched again; a key the record owns that is missing from the file is written again, and a store that wants it gone says so in p4.json.
  • What p4 wants written comes from p4.json, which is synced and shared, while the record of what was written stays on one machine.

Why not inside the settings file:

  • The schema check is strict about fields it does not know. Source, settings-reference.md, key sshHostCommands: "Before Claude Code v2.1.307, the Edit tool refused a change that added this key to a valid settings file, with the error Unrecognized field: sshHostCommands."
  • A key the schema rejects can make the file a Settings Error at the next start, quoted in the section above.

Why not in p4.json:

  • p4.json moves between machines by p4.py sync, and the record holds one checkout's absolute paths, as #246 and #125 note.

Why not in CLAUDE_PLUGIN_DATA:

  • Each plugin has a data folder of its own, while the writer is p4conf.py, of which both plugins carry a copy, so whichever plugin runs first must find the same record. Source, plugins/components.md, by the inventory's row E4: CLAUDE_PLUGIN_DATA is the documented place for a plugin's lasting data, one folder per plugin.

The update watcher

The signal:

  • No hook input field carries Claude Code's version: the common input fields of hooks.md are session_id, prompt_id, transcript_path, cwd, scratchpad_dir, permission_mode, effort and hook_event_name.
  • No documented environment variable carries it either: the 418 variables of env-vars.md hold none.
  • claude --version is the documented way to read the version. Source, changelog.md: "Run claude --version to check your installed version."
  • But claude on the PATH is the wrong binary for a desktop session. Source, desktop.md, section "Claude Code version in the Code tab": "In a local session, the Code tab runs its own copy of Claude Code, which has its own version number. The desktop app downloads and updates that copy, so it can differ from the claude command in your terminal, and updating one doesn't update the other." Measured in this session: claude --version on the PATH printed 2.1.322 (Claude Code), while the binary running the session printed 2.1.325 (Claude Code). #246's untested route would have read the wrong one.
  • CLAUDE_PID names the process that runs the session, in hooks too. Source, env-vars.md, key CLAUDE_PID: "Claude Code sets this to its own process ID in the subprocesses it spawns: Bash and PowerShell tool commands and hook commands." and "Read it from your own scripts to identify or signal the parent Claude Code process deliberately."
  • Decision: the hook takes the executable path of CLAUDE_PID from the system, by QueryFullProcessImageNameW on Windows, /proc/<pid>/exe on Linux and ps -o comm= on macOS, and runs that path with --version only when the path, its size or its modified time differ from the record. Measured: --version on this session's binary took 45 milliseconds.
  • Fallback when CLAUDE_PID is unset, as before v2.1.214: claude --version on the PATH, recorded as a weaker reading.
  • Not used: the status line's version field is documented on statusline.md, but the status line is one command per scope that belongs to ezexe's interface; CLAUDE_CODE_EXECPATH and AI_AGENT carry the version in this session's environment but are on no doc page; a transcript line's version field is undocumented.

When the check runs:

  • At every SessionStart, whatever its source: the cheap comparison of binary path, size and time, and of each p4 plugin's version.
  • At a ConfigChange whose source is local_settings, project_settings or user_settings: only the owned keys are checked against the record, so an edit by hand is seen when it happens. The hook never blocks, since a block would stop ezexe's own edits. Source, hooks.md: "Claude Code runs ConfigChange hooks when a settings file, a managed policy file, or a skill file changes." and "ConfigChange hooks can block configuration changes from taking effect."
  • After p4.py sync brings a store to another machine, that machine's next start runs the whole check, since its record is its own.

What a change sets off:

  • A changed version, binary or plugin version runs the whole settings check at once: owned keys are written again where they differ, and the local file's place is worked out again.
  • It also records the versions between the recorded one and the new one as owed, and the next read of Claude Code's own cached changelog takes the ## <version> sections after the recorded version up to the new one and searches them for the watched terms below. Source, claude-directory.md, "Kept until you delete them": "cache/changelog.md | Cached copy of the Claude Code changelog, shown by /release-notes. Refreshed in the background." The path is under ~/.claude/, which CLAUDE_CONFIG_DIR moves. p4 fetches no changelog of its own.
  • The cached copy can be older than the binary that runs. On 2026-11-19 the copy on ezexe's machine ended at 2.1.311 while the desktop app ran 2.1.326. So a read takes only the sections the copy holds, the record then owes the rest from the newest version read, a copy with the time and size of the last read is not opened again, and a missing copy reads nothing and owes all of it.
  • A hit is written to a page in the store and handed to the session at its next prompt as one line naming the key and the version, so a session reads that entry and the key's doc entry and decides. No web call runs at all: the read is of a local file, which took 62 ms for 46 versions of a copy of 1.1 MB.
