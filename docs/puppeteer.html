A puppeteer and the orchestrators it controls

A session nobody started that starts an orchestrator is a puppeteer, and the orchestrators it starts stay attached under it, each at the top of a tree of its own. p4-phi reads that from the session tree, hands the puppeteer its lines beside each message, keeps its board, and names the sessions its records hold complete, while every archive call waits on the app's approval card for ezexe. Make each move on the model below, read the lines p4-phi hands out, and watch the board rewrite itself.

  • The tree makes it one.A puppeteer is a session nobody started that started an orchestrator which is still live. p4-phi reads the store's records and the app's newest records each time it matters, and keeps no list of its own.
  • A record on each side.The sessions a puppeteer controls are the live sessions that name it as their starter, read and never recorded. A controlled session stays attached under it, orchestrates its own tree, and keeps puppeteer on its own record.
  • Its state lives on a board.Claude Code compacts a puppeteer's context by itself, so p4-phi keeps board.md for it, hands it each report as one line and a page, and hands it the board's path first after every compaction.

A start waits on no other session's files

    
A worker that writes is started with use_worktree: false, so it works in its starter's checkout, on the paths of its Files: line. p4-phi keeps no lock on a file: it refuses a start whose paths overlap those of a running session that is not above the starter, queues none behind a busy writer, and warns a puppeteer of no go. A brief's Files: line says what its session covers, and the address book routes a message about one of those files by it.

  


  

    
What holds the rule up

    
scripts/controls.py holds the rule, scripts/phi.py runs it from p4-phi's hooks, and lbiza/tests/p4-phi/test_controls.py tests it.

    

      

        
How p4-phi knows a puppeteer

        
    
          
  • By the session tree: a session nobody started that started a session which is still live is a puppeteer, and a session nobody started that started none is an orchestrator.
    • 
          
  • The sessions it started are read from the store's records, which name each one's starter, and from the app's newest records for one that has sent no message yet.
    • 
          
  • The app nests a session under the session that calls the start tool, and no tool moves it after, so an orchestrator a puppeteer starts stays under it and nothing detaches it, in the app or in p4-phi.
    • 
          
  • Nothing of the app's sidebar is read, and no section, filing or setting makes a session a puppeteer. p4-phi says once, in the session and on its record as puppeteerTold, what it is, and tells each session it controls who started it.
    • 
        

      

      

        
Where each side's record is kept

        
    
          
  • The puppeteer's record is where every orchestrator's is: session.json in the store of the folder it was opened in, and a session it starts has its node in that store.
    • 
          
  • The controlled sessions are not recorded on it: each is read as a live session whose record names the puppeteer as its starter, with the store its folder is in.
    • 
          
  • A controlled session's own hook finds the puppeteer that started it and keeps puppeteer on its own record.
    • 
          
  • Each side reads the other's store. A request stays in the store of the session that filed it, and what became of it stays on the puppeteer's record.
    • 
          
  • An orchestrator the puppeteer starts has its node in the puppeteer's store, whatever project it works in.
    • 
        

      

      

        
What a puppeteer does itself

        
    
          
  • It tells ezexe in one place where each controlled session stands, each by its full title, and sends the feedback and user memories ezexe changes to all of them with SendMessage.
    • 
          
  • It writes no plugin or project files. p4-phi tells it so in the line it hands the puppeteer once.
    • 
          
  • Its turn may end on a step that waits on the sessions it controls while one of them is still working, holds something open or is not shown done.
    • 
          
  • It publishes the issues the Finding: lines of its trees need, and places the session that resolves each.
    • 
        

      

      

        
What p4-phi refuses

        
    
                              
  • Any desktop start by a session another session started, which is told to draft its worker with draft and start it with draft --start in the Terminal panel, and to ask a new orchestrator of the session above with request --to-puppeteer.
    • 
          
  • controls --decline with no open request of that id addressed to this puppeteer, or with a reason shorter than twelve characters.
    • 
                    
  • request --to-puppeteer from a session no puppeteer started.
    • 
                  

      

      

        
What p4-phi does not do

        
    
          
  • It does not compact a session, and a boundary carries no compact question and no line for ezexe to type. The context window page says: “Claude Code compacts automatically as you approach the limit, so a full context window doesn't end your session.”
    • 
          
  • It does not start a session, move one in the app's sidebar or archive one. Those are the app's tools, and the session makes the calls.
    • 
          
  • It speaks only when one of its hooks fires, so a boundary reached while the puppeteer is idle is named beside its next message. A command hook with asyncRewake could wake it at once, and p4-phi uses none. SendMessage with notify_when_idle cannot tell it of a controlled session: the desktop app runs each, and the call serves a Claude session outside the app alone, answering for one of the app's that nothing was subscribed. So p4-phi says once, for each controlled session that works, what does tell the puppeteer of its turn's end: the app's own note for one the puppeteer started, and nothing for one it did not start, which the sweep's schedule covers where phi.upkeep is on.
    • 
          
  • It hands a start request only to the session that filed it. A puppeteer may decline only a request addressed to it, and the hook of the session that filed it then closes the row as withdrawn.
    • 
          
  • It refuses no archive call. The app shows its approval card before an archive call, except in auto and bypass permissions mode, by its own rule, and the tool refuses a session with live background work itself. The settings keeper writes no ask rule on mcp__ccd_session_mgmt__archive_session, with phi.upkeep on or off, and takes its own entry out. A project that turns phi.upkeep on has the line that names a complete session hold its archive call.
    • 
        

      

      
    

  


  

    
One command and its flags

    
Only a puppeteer may run it. Every form ends by rewriting the board and printing where each controlled session stands.

    

      

        
The commandWhat it does

        
          
phi.py controlsPrints each controlled session, a live session this one started, by its full title, with its store, its state and what p4-phi's records hold against calling it complete. Then it prints the board's path.

          
phi.py controls --decline <request id> "<why>"Declines a request for a new orchestrator. The session that filed it is told at its next message, and starts no session for it.

          
      

    

  


  

    
The puppeteer and the watcher

    
A puppeteer is a session. The watcher is the plugin's hooks module, hooks/register.ts, which runs inside Claude Code: at a turn's end, at a message's arrival and on its timer it runs phi.py look, one pass of puppeteer.py over an orchestrator's subtree that ends. A look rewrites that orchestrator's ledger.md from p4-phi's records and the app's session records when one of them changed, with a reconcile line for each divergence between the two. The module keeps one look in flight at most and phi.watch_s seconds between two, and a session that is no orchestrator pays one check and then backs off. The same module wakes an idle session, which no command hook can: at the end of each turn of a session another session started it sends that session the turn's report with $.session.send, and where a look answers upkeep that is due it starts a turn for it with $.prompt.submit, inside the budget of phi.keep_going_max. It also keeps the origin Claude Code stamps on each prompt, in origin.json, for that prompt's UserPromptSubmit hooks, which read from it whose message the prompt is: ezexe's own, another session's, a plugin's or an event. And it checks a tool call before it runs, at tool.check, where it starts python only for a call python has a check for. And it gives a session phi.py note, phi.py done and phi.py tree as the tools mcp__p4-phi__note, mcp__p4-phi__done and mcp__p4-phi__tree, which it declares at a session's start and runs itself at tool.run, once a call is allowed, so a session keeps a finding with no shell line. phi.py ledger prints the ledger and rewrites it when it changed, and phi.py settle <sessionId> "<what took it up>" clears a session's row from the ledger's section of work left unfinished at an archive. A puppeteer has a watcher and a ledger like every orchestrator, and its board is a page of its own beside them.

    
ezexe sees the three pages in a pane beside the chat: the command /phi-pane, which the same module declares, opens it, and no session start does. The module reads board.md, asks.md and ledger.md from the session's folder when the command runs and after each look while the pane is open, and draws each page whole, or one line a page where the desktop app shows the pane as a widget. The pages stay the files a session reads, and the pane writes none of them.
