p4-temportal and what Claude Code keeps

p4-temportal is the plugin for what a project keeps over time. Claude Code keeps most of it by itself: a conversation past its context window, auto memory, checkpoints, transcripts, a scratchpad for each session, worktrees and plan files. This page sets each of them in one table: what was set out for the plugin, what Claude Code does and the docs page that says so, what the plugin does today, what it only configures, and what the native feature lacks, which is the one thing the plugin builds. Every docs page named here is under https://code.claude.com/docs/en/, and the index lists them.

What was set out

Read from the commits of ezexe/p4 that touch p4-memory, p4-scratchpad and p4-temportal, and from its closed issues.

  • The first design page, added in f2323b2, set the plugin out to "keep the memory and scratchpad overrides into p4 so its trackable", under the rule to "only enhance" the app "where evidence shows it will". The two overrides "change where files live, not how the model behaves."
  • b01f260 made p4-memory and p4-scratchpad one plugin "for what Claude Code leaves in AppData and temp", which "clears what is no longer relevant, as a browser does with its cache and cookies".
  • 58bdde0 wrote the rule the plugin has followed since: "a p4 copy of a native feature is replaced and deleted", and the only part kept is one the native feature lacks. The wiki's Contributing page holds it as "Native first".
  • Under that rule the memory mirror went for autoMemoryDirectory in 7ac9910, the scratchpad links went for the app's own scratchpad in 6f3fb9a, the ask before a write went for ask rules in 8b0d3d8, and the lifetime that ended with a session went in 464483f.
  • The commits and issues name memory, the scratchpad, temp files and lifetimes. They name compaction only as a source of a session's start, and never checkpoints, plan files or worktrees. The plugin is now set out wider: it picks up every native feature about what a project keeps over time, and extends each only where it lacks, with compaction first.

A conversation past its context window

Nothing in the commits or issues. Issue 155 settled p4-phi "with no PreCompact entry", since "Claude Code compacts a session by itself".

It compacts by itself. model-config.md, "Default auto-compact thresholds": "Models running with a native 1M window compact before the window fills, at about 967K tokens by default." autoCompactWindow and /autocompact move that line.

settings-reference.md, idleCompaction: it "compacts a long conversation that you've stepped away from", once "about an hour has passed since the last request" and the context has reached 200,000 tokens, a count env-vars.md lets CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS lower to 100,000 and no further.

The summary takes instructions three ways: /compact with words after it, by commands.md; a section "Compact instructions" in the project's CLAUDE.md, by costs.md; and a PreCompact hook, by hooks.md: "Claude Code uses its stdout as instructions for the compaction summary."

context-window.md, "What survives compaction": CLAUDE.md, unscoped rules, auto memory and the plan are "Re-injected from disk", and of the files read or edited "Claude Code re-reads up to five, most recently modified first".

The hooks module hooks session.compact. It adds the keep list to what every summary is told, after what was typed behind /compact. Behind the summary comes the list of the files the session wrote or edited, read from the tool calls of the transcript with no model. Since p4-temportal 0.3.46 the module hands that list as additional context of the SessionStart that Claude Code raises inside a compaction, so Claude Code keeps it as an attachment of that hook and no row of the transcript reads as a message ezexe typed. Before that it was one message added to the compaction's result, which the transcript kept as a row of the user's and recorded as the session's last prompt. A compaction that no SessionStart came inside of, and a subagent's, which has no SessionStart of its own, still get the list as that one message.

A minute after a turn of the main conversation ended, it compacts the session where the context is at or past temportal.compact_at, which is 70 percent unless p4.json sets it and 0 for none. It asks by $.session.compact, the plugin's own call, whose compaction leaves no command in the transcript, and where Claude Code refuses that call it runs /compact with no words after it, since the module's own hook tells every summary the keep list.

Seen on Claude Code 2.1.328 with p4-temportal 0.3.46, in a scripted session kept open from a scratch project whose p4.json sets temportal.compact_at to 1: a minute after a turn ended the module logged the context at 4 percent, Claude Code refused $.session.compact with the words not available in a headless (-p / SDK) session yet: compaction here runs inside a turn (a /compact prompt); catch it and carry on, and the module ran /compact. That compaction read manual and took the context from 35,449 tokens to 8,704 in 15 seconds. The transcript holds the command's row with the plugin as its origin and nothing after the command's name, the list as an attachment of the SessionStart hook's additional context, and no row of the user's that holds the list, and its record of the session's last prompt stayed the prompt a person had sent. The session's next answer named the file it had written and gave the summary and the plugin's list as where it knew it from. After a second file and a typed /compact the attachment listed both files, the first carried from the list before, which the module reads from the conversation as the model is sent it, since the event hands a hook the transcript's messages and no attachment.

Seen in the desktop app on Claude Code 2.1.326: a plugin's own call of $.session.compact is refused there, the slash command run by $.command.run compacts, the module's own hook hears that compaction, and the message it adds is in the context afterwards and among the messages of the next compaction.

Seen on Claude Code 2.1.328 in a scripted session kept open from a scratch project whose p4.json sets temportal.compact_at to 1: a minute after a turn ended the module logged the context at 5 percent and ran /compact with the keep list. The compaction read manual and took the context from 50,068 tokens to 9,549 in 23 seconds. The summary held both paths the session had written, and the list of written files followed it in the transcript as a row of the user's, the summary and the list each with the plugin as its origin. The session's next answer named both files, and gave the summary, that list and the files Claude Code attached again after the compaction as where it knew them from. No second compaction followed in the two and a half quiet minutes after it. The host was handed a result with no turn for that compaction.

Seen there too, a compaction Claude Code starts by itself, with the automatic line lowered for one run by CLAUDE_CODE_AUTO_COMPACT_WINDOW: it compacted three times inside one turn, each read auto, and the module's hook was in the chain of each. Every summary held a line for session ids, branches and commit hashes, as the keep list asks, and the list of written files followed each one. The third list held a file written before the first compaction, carried from list to list, and a file written between the second and the third.

Seen the same way, the compaction of a subagent's transcript: a subagent that read large files was compacted three times, each auto and each with the subagent's id, the module's hook was in the chain of each, and the subagent's own transcript held a summary and a list of the files the subagent wrote after each. The main conversation was not compacted.

A PreCompact command hook, compact.py keep, prints the same keep list as the summary's instructions, so a session where the module does not load is told it too. It prints nothing where the custom_instructions it is handed already hold the list, so a summary is told it once. Seen on Claude Code 2.1.328 in a claude -p run from a scratch project: a /compact with no words after it handed a PreCompact hook the module's list as custom_instructions, and with a copy of the plugin that names no module the hook was handed none.

The automatic line is ezexe's, by autoCompactWindow, and the plugin writes neither it nor idleCompaction.

The instructions go in through the hooks module's event session.compact, whose instructions the types file of the bundled skill plugin-authoring gives as "What the summary should keep or stress".

The plugin starts no compaction where auto-compaction is off, and none at the token count where Claude Code compacts by itself. It reads both by $.session.usage.

The list behind the summary goes in by the documented way. context-window.md, "What survives compaction", says of SessionStart hooks that match the compact source that "Claude Code runs them and adds their output to the compacted context".

It adds no pointer to the transcript, since Claude Code's own summary ends by naming the transcript's path.

A keep list that holds in every project with no file of the project written: every session id, file path, branch, commit hash, decision with its source, open item, and the path of any state page or hand-over note. The native ways are a section a person writes into each project's CLAUDE.md, or words typed at each /compact.

A compaction at a quiet moment below the automatic line. Idle compaction waits an hour without a request, which a session its workers keep waking never has, and the automatic one runs where the window fills, in the middle of a turn. The plugin starts one after a turn of the main conversation ends, past a line its settings give.

A list that does not depend on the summary: the paths of the files the session wrote or edited, any state page or hand-over note among them, carried from one compaction to the next.

Claude Code refuses a plugin's own $.session.compact in a session a program started, which a session of the desktop app is, so there the plugin runs the slash command, and such a compaction reads manual, as one ezexe typed does. The module makes its own call first each time, so it compacts by that call wherever Claude Code allows it, with no new version, and p4-native's probe session-compact-from-a-module tells a session when the refusal is gone. The event hands a hook no summary string and no way to check what the summary kept, so the start hook that matches the source compact stays.

Auto memory

f2323b2: "keep the memory and scratchpad overrides into p4 so its trackable". Issue 92: autoMemoryDirectory replaces the pointer, the mirror and the sweep.

memory.md: "Each project gets its own memory directory at ~/.claude/projects/<project>/memory/", and "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." settings-reference.md, autoMemoryDirectory: "Store auto memory in a directory of your choice instead of the per-project default."

It configures. The settings keeper of p4conf.py writes autoMemoryDirectory, naming the store's temportal/memory, into the project's .claude/settings.local.json, and Claude Code writes and loads the memory there itself.

It copies nothing. mirror and sweep, the two commands of the copy, are deleted from p4_memory.py, whose one command is migrate.

autoMemoryDirectory, and nothing else of memory.

Where the hooks module loads, the settings the plugin's python reads come from Claude Code. At classic.SessionStart the module reads each source by $.settings.read, keeps the keys p4 reads, and adds them as p4_settings to the input every SessionStart command hook gets on stdin. The settings keeper takes the managed settings from there, every managed tier merged, where it knew one managed file. It still reads the user, project and local files itself, since it writes a file for every later session and a session started with some sources left out loaded less than the files hold. p4_memory.py takes all four sources for its line on a write block. In a session that loads no module, at a ConfigChange and in a command run by hand, both read the files as before.

Seen on Claude Code 2.1.328 in a claude -p run from a scratch project: each source came back as its file holds it, what --settings carried came back as the source flag, the managed settings were empty where none are set, and the field the module added was on the stdin of another plugin's SessionStart command hook.

A line at a start in a worktree or a subfolder when blockWritesOutsideWorkingDirectories may keep Claude Code from saving memory in the main checkout's store. settings-reference.md gives the block and tells no session of it. p4_memory.py migrate prints the line, and stays.

Plan files

The skill page, since 384a314: "Transcripts, plans, file history and subagent memory stay where Claude Code puts them too."

settings-reference.md, plansDirectory: "Choose where Claude Code stores the plan files it writes in plan mode", as "a path relative to the project root", and unset "Claude Code uses ~/.claude/plans", which claude-directory.md lists as cleaned up after cleanupPeriodDays. permission-modes.md names what plan mode may write: "The current session's own plan files in ~/.claude/plans/, or in the plansDirectory you set".

The settings keeper writes plansDirectory, so Claude Code writes a project's plan files into the store's temportal/plan-planner, where the store's git tracks them. Until the key is there they are in ~/.claude/plans, where plans of every project lie together and go after 30 days.

plansDirectory, as a path from the project's root, .claude/p4/temportal/plan-planner. It is written where the store lies inside the project and no user, project or managed settings file names a folder for plans, and a store whose claude section sets it false gets none. The page of the settings p4 keeps has its row.

Lifetimes for plans. Claude Code's own cleanup clears a plan in ~/.claude/plans once it is older than cleanupPeriodDays and does not reach a folder a project names, so since p4-temportal 0.3.45 the retention sweep clears a plan file in the store's plans folder at that same age, temportal/plan-planner since p4-temportal 0.3.55. The hooks module reads the key by $.settings.read as Claude Code merged every settings source and hands it to each run of lifetime.py, which reads the settings files itself where none is handed and takes 30 days where no file sets the key. Where the period cannot be told, as with a settings file that cannot be read or a value that is no number of 1 or more, no plan is cleared by age, as Claude Code pauses its own sweep there. In place of that age stands a cache rule on plan-planner where p4.json holds one, an empty one keeps every plan, a plan file takes a cookie as any other file does, and a plan the store's git tracks goes with its removal staged. /lifetime list shows the age in force. The tests of lifetime.py hold each of these on a store on disk, and no live session was kept until a plan came of age.

Since p4-temportal 0.3.54 the plugin's skill plan-planner shapes the plan that plan mode writes, so every session of the project tracks a plan the way ezexe's skill of that name says, with its rules for each section of a plan word for word. skills.md gives a plugin's skill as <plugin>/skills/<skill-name>/SKILL.md, loaded "Wherever the plugin is enabled". The plans folder is .claude/p4/temportal/plan-planner, the folder of the plugin that creates it, and the plan a session works is the file plan mode wrote directly in it. Once finished, parked or dropped a plan moves into its complete, todo or unplanned subfolder by a plain move of the file, and no session reads anything there unless ezexe names the file. The source skill closes and parks plans by commits on an orphan branch, which ezexe set apart as a matter of its own, so the skill makes no commit of a move. The age clears only the files directly in the plans folder, since claude-directory.md lists what Claude Code clears there as "Plan files written during plan mode", so a sorted plan stays until ezexe's word moves it. No subfolder of the three takes a cookie whole, the copy out of ~/.claude/plans skips a plan whose name one of them holds, and a plan a worktree moved leaves its old place in the main checkout's store when the sweep carries it there, where it is the newest copy of its name. Since p4-temportal 0.3.55 the folder is temportal/plan-planner, where it was temportal/plans before. The layout move of p4conf.py takes the old folder into the new one once, with the complete and todo that p4-temportal 0.3.52 and 0.3.53 made there and the cookies and cache rules set on it, and of two differing copies of a file it keeps the newer and sets the older aside in temportal/.layout-conflicts/plans. The keeper's next whole check, which its new generation brings about at the next start, then writes the new folder into plansDirectory where the keeper wrote the old one, and leaves a value a person set as it is. A session whose Claude Code read the old value at its start writes its plan into temportal/plans until it ends. Each sweep starts with the layout move, which takes such a plan into the new folder again, and the copy out of ~/.claude/plans takes the old value of the key as naming the store's plans too, so the first last sweep after the change, which runs before the keeper's check, still copies a plan. No live session has been seen writing into the old folder after the move. The tests of lifetime.py and of the skill hold each place on a store on disk. No live session has moved a plan, and whether a session is asked about the edit of a plan file after plan mode ends was not tried.

How long the store's files stay

b01f260: it "clears what is no longer relevant, as a browser does with its cache and cookies".

claude-directory.md: the retention sweep covers Claude Code's own folders under ~/.claude and nothing a project keeps.

Cache rules and cookies in lifetime.py, swept by the hooks module at a start, on its timer and past a session's end, the slash command /lifetime for ezexe, and the tool mcp__p4-temportal__lifetime for a session, which takes the same four commands.

Seen on Claude Code 2.1.328 in a scripted session from a scratch project: the tool was in the session's list, a set wrote the cookie, and a refused set came back as the call's error.

Seen there too, in a session with no allow rule whose host answers each permission ask: every call of the tool was put to the host as an ask before anything ran. A refused call came back to the model as the call's error with no command of lifetime.py run, and an allowed one ran list and printed the cache rules.

sweep and session-end, which the command hooks ran before the module did, are deleted from lifetime.py, and so is the option --session of set.

A session in a git worktree has a store of its own, .claude/p4 under the worktree, since what a session writes by a path from its folder lands there. Since p4-temportal 0.3.47 and p4-native 0.5.19 three more things of it are settled, each with its reason.

p4.json: a worktree session reads the main checkout's. The file holds what ezexe turned on for the project, and a worktree is one more checkout of that project. Claude Code keeps a project's own configuration the same way: settings.md says of the local settings file that "In a worktree, it uses the file at the main checkout's root", and worktrees.md, "What worktrees share with the main checkout", that in a worktree session started from the desktop app "Claude Code reads project configuration such as settings, hooks, skills, agents, commands" and more "from the main checkout's root". So the cache rules and temportal.compact_at are the project's in every worktree, a p4.json in a worktree's own store is read by nobody, and p4-temportal writes none there. Where the main checkout has no store, a worktree's own is the project's.

Cookies: a worktree session keeps its own and carries each into the main checkout's store with the file it names. A cookie names a file of the store it is in, so it stays in the worktree's expires.json, where the worktree's sweep clears the worktree's file by it. Its copy in the main checkout's expires.json is marked with the worktree it came from and clears the carried copy at the same time. A cookie the main checkout holds that no worktree marked stays as it is, one that clear removed in the worktree is taken out there too, and one whose file the worktree's sweep cleared stays for the carried copy. The sweep of a worktree session clears its own store first, so a file past its lifetime is not carried, and then the main checkout's store, so what was carried goes when it is due though no session runs in the main checkout itself.

p4-native's map and probe answers: a worktree session reads and writes the main checkout's. What a host is and can do is no fact about one checkout, and a worktree's own store goes with the worktree, so each new worktree session started with no answer kept. The module asks $.session.repo for the main checkout, and p4-temportal's module reads the map there first.

Seen in the desktop app on Claude Code 2.1.326 with p4-temportal 0.3.42 and p4-native 0.5.17, before this was built, in a session whose worktree the app had made: p4-native answered "kept: for this session alone, since the project has no .claude/p4" and "No probe was read on desktop/interactive yet". A note written into the worktree's notebook was in the main checkout's store within a second of a call of the lifetime tool with set, with the same bytes, and its cookie was in the worktree's expires.json alone. That call made a p4.json in the worktree's store with phi.upkeep false, where the main checkout's holds it true beside phi.cards. With the built lifetime.py run by hand for that same worktree: the cookie was in the main checkout's expires.json with the worktree's folder beside it, the main checkout's p4.json kept its bytes, and list named the cookie of each store. Not seen: p4-native 0.5.19 in a session of the desktop app, which its module tests hold.

A command hook of a worktree session the desktop app started already runs with CLAUDE_PROJECT_DIR at the main checkout's root, by the passage of worktrees.md quoted above, so there p4-phi's hooks read the main checkout's store, and in a worktree session of any other kind they read the worktree's own.

The order of the parts

Each part lands by itself, and this page is brought up with it.

  1. Compaction. The hooks module tells the summary what to keep, adds the list of the files the session wrote behind the summary, and starts a compaction at a quiet moment below the automatic line. It came first because it was the one row where a session loses what it needs and the plugin did nothing. It landed in p4-temportal 0.3.28.
  2. A session sets a lifetime itself. The four commands of /lifetime become a tool the model can call, registered by the hooks module and served once Claude Code allowed the call. It landed in p4-temportal 0.3.29.
  3. The skill page names what Claude Code keeps. It says which native command or setting keeps each thing, so a session reaches for that and builds no copy by hand. It landed in p4-temportal 0.3.30.
  4. The leftovers of the copies go. The commands the scripts still answer for sessions of older versions are deleted, since an installed version runs the scripts of its own folder in Claude Code's plugin cache. It landed in p4-temportal 0.3.31.
  5. Plan files. The settings keeper writes plansDirectory, naming the store's plans folder, temportal/plan-planner since p4-temportal 0.3.55, and plan files come under lifetimes. It landed in p4-temportal 0.3.32.
