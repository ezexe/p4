p4-temportal and what Claude Code keeps

p4-temportal is the plugin for what a project keeps over time. Claude Code keeps most of it by itself: a conversation past its context window, auto memory, checkpoints, transcripts, a scratchpad for each session, worktrees and plan files. This page sets each of them in one table: what was set out for the plugin, what Claude Code does and the docs page that says so, what the plugin does today, what it only configures, and what the native feature lacks, which is the one thing the plugin builds. Every docs page named here is under https://code.claude.com/docs/en/, and the index lists them.

What was set out

Read from the commits of ezexe/p4 that touch p4-memory, p4-scratchpad and p4-temportal, and from its closed issues.

  • The first design page, added in f2323b2, set the plugin out to "keep the memory and scratchpad overrides into p4 so its trackable", under the rule to "only enhance" the app "where evidence shows it will". The two overrides "change where files live, not how the model behaves."
  • b01f260 made p4-memory and p4-scratchpad one plugin "for what Claude Code leaves in AppData and temp", which "clears what is no longer relevant, as a browser does with its cache and cookies".
  • 58bdde0 wrote the rule the plugin has followed since: "a p4 copy of a native feature is replaced and deleted", and the only part kept is one the native feature lacks. The wiki's Contributing page holds it as "Native first".
  • Under that rule the memory mirror went for autoMemoryDirectory in 7ac9910, the scratchpad links went for the app's own scratchpad in 6f3fb9a, the ask before a write went for ask rules in 8b0d3d8, and the lifetime that ended with a session went in 464483f.
  • The commits and issues name memory, the scratchpad, temp files and lifetimes. They name compaction only as a source of a session's start, and never checkpoints, plan files or worktrees. The plugin is now set out wider: it picks up every native feature about what a project keeps over time, and extends each only where it lacks, with compaction first.

A conversation past its context window

Nothing in the commits or issues. Issue 155 settled p4-phi "with no PreCompact entry", since "Claude Code compacts a session by itself".

It compacts by itself. model-config.md, "Default auto-compact thresholds": "Models running with a native 1M window compact before the window fills, at about 967K tokens by default." autoCompactWindow and /autocompact move that line.

settings-reference.md, idleCompaction: it "compacts a long conversation that you've stepped away from", once "about an hour has passed since the last request" and the context has reached 200,000 tokens, a count env-vars.md lets CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS lower to 100,000 and no further.

The summary takes instructions three ways: /compact with words after it, by commands.md; a section "Compact instructions" in the project's CLAUDE.md, by costs.md; and a PreCompact hook, by hooks.md: "Claude Code uses its stdout as instructions for the compaction summary."

context-window.md, "What survives compaction": CLAUDE.md, unscoped rules, auto memory and the plan are "Re-injected from disk", and of the files read or edited "Claude Code re-reads up to five, most recently modified first".

The hooks module hooks session.compact. It adds the keep list to what every summary is told, after what was typed behind /compact. Behind the summary it adds one message that lists the files the session wrote or edited, read from the tool calls of the transcript with no model.

A minute after a turn of the main conversation ended, it compacts the session by running /compact where the context is at or past temportal.compact_at, which is 70 percent unless p4.json sets it and 0 for none.

Seen in the desktop app on Claude Code 2.1.326: a plugin's own call of $.session.compact is refused there, the slash command run by $.command.run compacts, the module's own hook hears that compaction, and the message it adds is in the context afterwards and among the messages of the next compaction.

Seen on Claude Code 2.1.328 in a scripted session kept open from a scratch project whose p4.json sets temportal.compact_at to 1: a minute after a turn ended the module logged the context at 5 percent and ran /compact with the keep list. The compaction read manual and took the context from 50,068 tokens to 9,549 in 23 seconds. The summary held both paths the session had written, and the list of written files followed it in the transcript as a row of the user's, the summary and the list each with the plugin as its origin. The session's next answer named both files, and gave the summary, that list and the files Claude Code attached again after the compaction as where it knew them from. No second compaction followed in the two and a half quiet minutes after it. The host was handed a result with no turn for that compaction.

Seen there too, a compaction Claude Code starts by itself, with the automatic line lowered for one run by CLAUDE_CODE_AUTO_COMPACT_WINDOW: it compacted three times inside one turn, each read auto, and the module's hook was in the chain of each. Every summary held a line for session ids, branches and commit hashes, as the keep list asks, and the list of written files followed each one. The third list held a file written before the first compaction, carried from list to list, and a file written between the second and the third.

Seen the same way, the compaction of a subagent's transcript: a subagent that read large files was compacted three times, each auto and each with the subagent's id, the module's hook was in the chain of each, and the subagent's own transcript held a summary and a list of the files the subagent wrote after each. The main conversation was not compacted.

A PreCompact command hook, compact.py keep, prints the same keep list as the summary's instructions, so a session where the module does not load is told it too. It prints nothing where the custom_instructions it is handed already hold the list, so a summary is told it once. Seen on Claude Code 2.1.328 in a claude -p run from a scratch project: a /compact with no words after it handed a PreCompact hook the module's list as custom_instructions, and with a copy of the plugin that names no module the hook was handed none.

The automatic line is ezexe's, by autoCompactWindow, and the plugin writes neither it nor idleCompaction.

The instructions go in through the hooks module's event session.compact, whose instructions the types file of the bundled skill plugin-authoring gives as "What the summary should keep or stress".

The plugin starts no compaction where auto-compaction is off, and none at the token count where Claude Code compacts by itself. It reads both by $.session.usage.

It adds no pointer to the transcript, since Claude Code's own summary ends by naming the transcript's path.

A keep list that holds in every project with no file of the project written: every session id, file path, branch, commit hash, decision with its source, open item, and the path of any state page or hand-over note. The native ways are a section a person writes into each project's CLAUDE.md, or words typed at each /compact.

A compaction at a quiet moment below the automatic line. Idle compaction waits an hour without a request, which a session its workers keep waking never has, and the automatic one runs where the window fills, in the middle of a turn. The plugin starts one after a turn of the main conversation ends, past a line its settings give.

A list that does not depend on the summary: the paths of the files the session wrote or edited, any state page or hand-over note among them, carried from one compaction to the next.

The event has no call that starts a compaction outside a turn in a session a program started, so the plugin runs the slash command, and such a compaction reads manual, as one ezexe typed does. The event hands a hook no summary string and no way to check what the summary kept, so the start hook that matches the source compact stays.

Auto memory

f2323b2: "keep the memory and scratchpad overrides into p4 so its trackable". Issue 92: autoMemoryDirectory replaces the pointer, the mirror and the sweep.

memory.md: "Each project gets its own memory directory at ~/.claude/projects/<project>/memory/", and "The first 200 lines of MEMORY.md, or the first 25KB, whichever comes first, are loaded at the start of every conversation." settings-reference.md, autoMemoryDirectory: "Store auto memory in a directory of your choice instead of the per-project default."

It configures. The settings keeper of p4conf.py writes autoMemoryDirectory, naming the store's temportal/memory, into the project's .claude/settings.local.json, and Claude Code writes and loads the memory there itself.

It copies nothing. mirror and sweep, the two commands of the copy, are deleted from p4_memory.py, whose one command is migrate.

autoMemoryDirectory, and nothing else of memory.

Where the hooks module loads, the settings the plugin's python reads come from Claude Code. At classic.SessionStart the module reads each source by $.settings.read, keeps the keys p4 reads, and adds them as p4_settings to the input every SessionStart command hook gets on stdin. The settings keeper takes the managed settings from there, every managed tier merged, where it knew one managed file. It still reads the user, project and local files itself, since it writes a file for every later session and a session started with some sources left out loaded less than the files hold. p4_memory.py takes all four sources for its line on a write block. In a session that loads no module, at a ConfigChange and in a command run by hand, both read the files as before.

Seen on Claude Code 2.1.328 in a claude -p run from a scratch project: each source came back as its file holds it, what --settings carried came back as the source flag, the managed settings were empty where none are set, and the field the module added was on the stdin of another plugin's SessionStart command hook.

A line at a start in a worktree or a subfolder when blockWritesOutsideWorkingDirectories may keep Claude Code from saving memory in the main checkout's store. settings-reference.md gives the block and tells no session of it. p4_memory.py migrate prints the line, and stays.

Plan files

The skill page, since 384a314: "Transcripts, plans, file history and subagent memory stay where Claude Code puts them too."

settings-reference.md, plansDirectory: "Choose where Claude Code stores the plan files it writes in plan mode", as "a path relative to the project root", and unset "Claude Code uses ~/.claude/plans", which claude-directory.md lists as cleaned up after cleanupPeriodDays. permission-modes.md names what plan mode may write: "The current session's own plan files in ~/.claude/plans/, or in the plansDirectory you set".

The settings keeper writes plansDirectory, so Claude Code writes a project's plan files into the store's temportal/plans, where the store's git tracks them. Until the key is there they are in ~/.claude/plans, where plans of every project lie together and go after 30 days.

plansDirectory, as a path from the project's root, .claude/p4/temportal/plans. It is written where the store lies inside the project and no user, project or managed settings file names a folder for plans, and a store whose claude section sets it false gets none. The page of the settings p4 keeps has its row.

Lifetimes for plans: a plan file takes a cookie, a cache rule on plans clears the plans past its age or size, and a plan with neither stays, where Claude Code's own folder clears every plan after cleanupPeriodDays.

Seen on Claude Code 2.1.328 as one chain, in two scripted sessions in plan mode from a fresh scratch project: the first session's start wrote the key, and the second session's plan file was in the store's folder, its write neither asked about nor refused. The first session's own plan was in ~/.claude/plans all the same, so the key holds from the session after the one whose start wrote it.

The plan of that first session reaches the store all the same. The hooks module notes each plan file a session creates or writes again in a folder named plans, and the last sweep, which runs once the session's process is over, copies the ones in Claude Code's own plans folder into the store's folder, where the project's key names that folder. The original stays, and Claude Code's own cleanup removes it with the session's transcript. A file a session only edited gets no copy unless the store already holds one of its name, since another project's session may have made it.

Seen on Claude Code 2.1.328 in a fresh scratch project: once one scripted session in plan mode had ended, its plan was in the store, the same bytes as the original. A move was tried first and taken back: a session resumed after its plan had been moved still wrote to ~/.claude/plans, did not find its file, and made it anew. With the copy, the resumed session edited its plan where it had made it, and the store's copy held the edit once that session had ended.

Seen in the desktop app on Claude Code 2.1.326, in two sessions in plan mode that another session started in this project, one in a worktree made for it and one in a worktree a session was already working in: each wrote its plan into .claude/p4/temportal/plans under its own worktree, its write neither asked about nor refused, and neither put a file into ~/.claude/plans. The session whose start writes the key did not come about there. In each of three new worktrees settings.local.json was there half a second after the worktree's .git, with the same bytes as the main checkout's and before the session's first row. So the file is copied when the worktree is made, the key holds from a worktree's first session, and the copy at a process's end had no first plan to copy. Whether the desktop app or Claude Code's own worktree step makes that copy was not told apart.

The folder such a session writes to lies in its worktree. The key is a path from the project root, and the root of a worktree session is its worktree. The plugins' start hooks take the store from that root too: each of the two worktrees held a .claude/p4 of its own afterwards, with the keeper's record of the key in it, apart from the main checkout's store, where the project's memory stays by its absolute path. Not seen: what becomes of such a plan when its worktree is removed, since both worktrees still stand.

Still not seen: a first session of the desktop app in a project folder whose settings hold no key yet, and a session in a worktree anywhere but on Windows, where the key is in the main checkout's file. The first needs a project the keeper has not set up, and the second a machine that is not this one.

The notebook and saved code

eed8107 made the notebook temportal/notebook, and 80ca12d brought saved code back as temportal/src.

Nothing. No docs page gives a project a folder of notes or of code kept for reuse beside its memory.

It keeps both in the store, moves the notebook's logs, build output and binaries into its .out/ at a start and when one appears, and can name saved code the repository uses.

The watch. The start hook hands Claude Code the notebook's folder as watchPaths, and a FileChanged entry with no matcher runs the same move when a log, a build output or a binary is added or changed there.

The move and what counts as a log, a build output or a binary are the plugin's own. Seen on Claude Code 2.1.328 in a claude -p run from a scratch project: a folder in watchPaths raised FileChanged with the event add for a new file in it and in a folder under it, and a log written into the notebook was in .out/ within a second while a note beside it stayed.

How long the store's files stay

b01f260: it "clears what is no longer relevant, as a browser does with its cache and cookies".

claude-directory.md: the retention sweep covers Claude Code's own folders under ~/.claude and nothing a project keeps.

Cache rules and cookies in lifetime.py, swept by the hooks module at a start, on its timer and past a session's end, the slash command /lifetime for ezexe, and the tool mcp__p4-temportal__lifetime for a session, which takes the same four commands.

Seen on Claude Code 2.1.328 in a scripted session from a scratch project: the tool was in the session's list, a set wrote the cookie, and a refused set came back as the call's error.

Seen there too, in a session with no allow rule whose host answers each permission ask: every call of the tool was put to the host as an ask before anything ran. A refused call came back to the model as the call's error with no command of lifetime.py run, and an allowed one ran list and printed the cache rules.

sweep and session-end, which the command hooks ran before the module did, are deleted from lifetime.py, and so is the option --session of set.

Nothing of Claude Code's.

Where p4-native is installed, the hooks module reads that plugin's capability map first, the file .claude/p4/native/host.json, for whether this session runs on Windows, which orders its search for a python. Where the map has no entry for the session it reads the shape of its own folder, as it did before.

Two readings of the host are left as they are. The python scripts ask their own interpreter for the operating system, which costs nothing and is never out of date. The settings keeper finds the running Claude Code and asks it for its version, since a session's entry of the map is written after the start hooks ran.

All of it is the plugin's own. The Skill tool refuses a command a module registers, so a session sets a lifetime through the tool. The module serves it at tool.run, the event that fires once Claude Code allowed the call, so the permission check stands before a file is deleted.

The session's own commands and tools

Nothing in the commits or issues. This row is from an audit that held every slash command and tool of a desktop session against the plugin.

commands.md lists /clear, /compact, /resume and /memory. A session also has the Skill tool, the file tools Write, Edit and NotebookEdit, and a shell tool, each behind Claude Code's own permission check.

It relies on /clear, /compact and /resume as sources of a session's start, on /memory through autoMemoryDirectory, on the Skill tool for its skill page, and on the file tools for memory. It uses no shell tool: the skill page hands no line of lifetime.py, which issues 112 and 113 kept off the page.

Its copy of the settings keeper keeps the ask rule on the app's archive tool and the deny rule on its model tool, as p4-phi's copy does, and only where p4-phi is installed for the project and no settings file switches it off, which it reads from installed_plugins.json and from enabledPlugins. Where p4-phi is not there, it takes its own two entries out at its next start and leaves every rule a person wrote.

A call of its own by which a session sets, clears and sweeps, behind Claude Code's permission check. The tool of the second part is that call, so the skill page names the tool and still hands no shell line.

The order of the parts

Each part lands by itself, and this page is brought up with it.

  1. Compaction. The hooks module tells the summary what to keep, adds the list of the files the session wrote behind the summary, and starts a compaction at a quiet moment below the automatic line. It came first because it was the one row where a session loses what it needs and the plugin did nothing. It landed in p4-temportal 0.3.28.
  2. A session sets a lifetime itself. The four commands of /lifetime become a tool the model can call, registered by the hooks module and served once Claude Code allowed the call. It landed in p4-temportal 0.3.29.
  3. The skill page names what Claude Code keeps. It says which native command or setting keeps each thing, so a session reaches for that and builds no copy by hand. It landed in p4-temportal 0.3.30.
  4. The leftovers of the copies go. The commands the scripts still answer for sessions of older versions are deleted, since an installed version runs the scripts of its own folder in Claude Code's plugin cache. It landed in p4-temportal 0.3.31.
  5. Plan files. The settings keeper writes plansDirectory, naming the store's temportal/plans, and plan files come under lifetimes. It landed in p4-temportal 0.3.32.

What the docs do not confirm

  • No page read says anything of a pass that consolidates memory. The skill consolidate-memory is listed in a desktop session and on no docs page.
  • plugins/mods/reference.md gives session.compact one line, "The conversation is about to be compacted", and lists compact among the methods of $.session with no words. What the event's input holds and what a plugin's own compaction does was read from the types file of the bundled skill plugin-authoring and checked live in the desktop app on Claude Code 2.1.326.
  • How the app draws the message the plugin adds behind a summary. Seen in the desktop app on Claude Code 2.1.326, in a session in plan mode whose worktree's own .claude/p4/p4.json set temportal.compact_at to 1: a minute after a turn ended the plugin ran /compact, and the compaction, which read manual, took the context from 91,362 tokens to 18,383 in 43 seconds. The transcript holds the summary as a row of the type user that is marked as a compaction's summary and as visible in the transcript only, and behind it the plugin's list as a row of the same type with no such mark, each with the plugin as its origin. The transcript also records the list as the session's last prompt. On screen, in a capture of the app's window made a few minutes after the compaction: a dim line labelled p4-temportal with the module's own words, "The context is at 9 percent, at or past temportal.compact_at 1, so the session compacts."; a dim row "Compacted session · saved 73K tokens"; and under it a bubble like one ezexe typed, "/compact Keep each of these verbatim in the summary", with nothing that marks it as a plugin's. No summary text and no divider was on screen, and the transcript was empty below the bubble. The plugin's list was not drawn in view, and the compaction's row shows no arrow to unfold. Whether the list sits folded inside that row was not tried, since the capture can neither scroll nor click. That compaction was not the first one due. No compaction followed an earlier turn in the five quiet minutes after its end. p4-temportal 0.3.39 had reached the plugin cache in the half minute before that turn ended, and p4-native wrote the session's entry of its map anew 34 seconds after it, as a reload of the modules would have it do, and a reload starts a module's variables over, its timer among them. That cause is read from those times and was not seen itself, and neither was which of 0.3.38 and 0.3.39 ran the compaction. Since p4-temportal 0.3.41 the module keeps the end of the last turn in the session's state, which stays through a reload, and a module loaded anew inside the minute waits out what is left of it. The module's tests hold that, and no live session has shown it.
  • Seen on Claude Code 2.1.322 and 2.1.311, older builds kept on the same machine: tool.run is no event on either, and a hooks module that names an event its build lacks does not load at all, which is what this module did there until p4-temportal 0.3.39. Since then it names the glob tool.* under the tool's matcher and answers where the event is tool.run, which the API types give as the way a module spans versions. On both builds the debug log of a scripted run holds hooks module p4-temportal@inline loaded, the sweep's python ran and exited 0, and /lifetime list printed the two cache rules. The module registers no tool there, since on 2.1.322 a tool registered with nothing but a glob over it was answered "no tool.call hook answered this call". Seen on 2.1.328 with the same copy: the tool was registered and a list was served at tool.run. Each run on the older builds was one short turn with no compaction, so neither the module's compaction hooks nor the PreCompact command hook was seen on those builds. Not seen: 2.1.323 to 2.1.325, since this machine holds no copy of them.
  • claude-directory.md lists plans/ among the paths under ~/.claude/ that are cleaned up automatically and does not say whether the sweep reaches a plansDirectory a project names. Seen in the desktop app on Claude Code 2.1.326, one sweep did not. settings-reference.md says of cleanupPeriodDays that the deletion runs "as a background sweep after a session starts", and monitoring-usage.md, "Retention sweep event", that it runs "at most once per session" and that where a session on the machine swept in the last 24 hours "it delays this session's sweep by at least 10 minutes, so a session that exits sooner emits nothing". That would explain why the scripted sessions of the earlier check showed nothing, though none was held open past ten minutes to test it. Five times ~/.claude/.last-cleanup took a new time, each ten minutes and six or seven seconds after the first row of a desktop session's transcript, and which session swept is read from that timing alone. One of the five fits a session whose plansDirectory was in force, since its own plan had landed in that folder. At that sweep a plan file dated sixty days back went from ~/.claude/plans, one there that was twenty-one days old stayed, and a plan file dated sixty days back in the session's own plans folder stayed, and was still there 38 seconds later, when the check removed it. An earlier one of the five, of another session, had removed a first such file from ~/.claude/plans. So where that one sweep left a project's plan alone, the plugin's lifetimes are what clears it. Not seen: the sweep of a terminal session. One on Claude Code 2.1.328, started with --settings and kept open for seventeen minutes at a plan's approval, wrote no .last-cleanup and removed nothing. Its debug log ends with four reads of the settings ten minutes and one second after its first line, and monitoring-usage.md gives a sweep as skipped where the retention period cannot be safely determined, so it may have been skipped, which was not found out.
  • The types file of the bundled skill plugin-authoring gives the input of a classic event as the hook's whole stdin input, and puts the hooks modules above the command hooks in that event's chain. It does not say that a field a module adds to the input reaches those command hooks. Seen on Claude Code 2.1.328 it does, and the hand-over of the settings a module read by $.settings.read rests on that.
  • hooks.md does not say whether a folder in watchPaths raises FileChanged for a new file in it. Seen on Claude Code 2.1.328 it does, with the event add, also for a file in a folder under it, and the notebook's move rests on that.
