# p4-phi: what linked sessions hand each other

A session is started by another session, its parent session, or it is an orchestrator.
A session has a task, its first request, and when it finishes a turn it gives a report.
p4-phi keeps each session's files in `<project>/.claude/p4/phi/sessions/<sessionId>/`, in the store of its orchestrator's project.

## What reaches a session without a command

- In its system prompt: the rules built into p4-phi, whole, as a section the plugin's hooks module sets when Claude Code renders the prompt, so no hook hands them at a start, a clear or a compaction, and a subagent, whose prompt is not rendered that way, holds none. The store's feedback and user memories reach it as their lines in the memory index the app loads, and a memory that changes later is handed once at the next message, unless it was cut back to a pointer or its body says the plugin carries its rule.
- Beside its first message, when the sessions linked to it left any: its start background, whose first and last lines say what it holds and how to keep a finding or say the task is done.
- Beside its next message: the reports of the workers or coworkers it started that finished a turn since.
- As a message from a worker it started, at the end of each of that worker's turns: the turn's report, which the plugin's hooks module sends and no worker writes. The message opens `phi (p4-phi): this session ended a turn.`, starts a turn when this session is idle, and needs no reply. A report it holds is named beside it and not repeated. A puppeteer's standing worker and coworkers write their own closing message.
- As a turn the hooks module starts, after a turn that ended on a step waiting on other sessions: a prompt that opens `phi (p4-phi): the turn before this one ended on` and lists what that wait leaves to move, a child's done and unlanded commit or an open step no live child holds. It is p4-phi's prompt and no message of ezexe's, it comes once for a turn, and such turns count against `phi.keep_going_max` with the turns the Stop hook sends back.
- Where the store's `phi.json` sets `goal` true, as a turn in a worker once its first turn has ended: Claude Code's own goal, whose condition is the line `Done looks like:` of the worker's brief. The plugin's hooks module sets it by the command `/goal <condition>`, the transcript shows `Goal set:` with the condition, and from then on Claude Code's evaluator sends the turn back until the condition holds, in place of p4-phi's Stop hook, as "A worker's goal" below says.
- Where the project turns `phi.upkeep` on, beside every message of a session that started others: the upkeep lines, which open `phi (p4-phi): upkeep of the sessions this one started` and list each act that is due, as "Upkeep of a session tree" below says.
- In a subagent it starts: the step the subagent serves and retrieval's lines, added as context at the subagent's start, each subagent getting the lines of the Agent call that launched it, which the hooks module binds to the subagent's id, and beside the result of a tool call of the subagent a warning of what changed beside its parent session since its launch, when anything did: a note a sibling session wrote after the launch, said once, by what the subagent's own transcript already holds.
- At a tool call p4-phi has a check for, from the hooks module, which checks the call before it runs: a refusal, which is the call's error and reads `Permission to use <tool> denied by plugins <names>: <reason>` with p4-phi's line as the reason; a question put to ezexe before the call runs; or a line beside the call's result.
- At the moment each applies: the advice on where each work step of an orchestrator's task list goes; a writing child's issue line, which says its loop; the push line, which goes only to the tree's orchestrator, the one session that lands and pushes, a worker's `Closes #N` commit included, and which names the worker's branch to merge into the default branch first; and the line `done` prints, which says what follows.

A feedback memory whose rule an open issue will build into the plugin is tied to that issue by one line in the memory's own front matter, `issue: owner/name#N`.
p4-phi writes that line when the `gh issue create` that files the issue carries the memory's `Finding:` line with its `source:`, and whoever files it another way writes the line by hand.
Once a commit that closes that issue is on the remote default branch, the next Stop whose turn ran a push, pull, fetch or merge cuts the memory back to one pointer line naming the issue and the code that carries its rule, and rewrites the memory's own line in the memory index to match.

Where the repository holds a workflow under `.github/workflows/` that runs its tests on every push to the default branch, the push line has the orchestrator run the checks the task named and the test files of the paths the commits touch, push, then read that workflow's run on the pushed commit with `gh run watch <run id> --exit-status` as one background command, and keep the verdict with `note "workflow <name> green at <hash>"`.
Where the repository holds no such workflow, the push line has the orchestrator run the full suite once, on the commit being pushed, as one background command, and keep the verdict with `note "suite green at <hash>"`, since a local run is then the only run.
Where a note of the tree holds that commit's hash green, the line names the note and the suite is not run again for that hash.
A start draft names the test files of the paths its brief covers, the one named after each python file and those that import it, beside the file and in the `tests` folders above it, and never a whole suite.

A store moves only by `python -I -X utf8 "${CLAUDE_PLUGIN_ROOT}/scripts/p4.py" sync --push --p4 "<store>"`.
A hand `git pull` or `git push` inside a store is asked first with that command named, ahead of every other check on the call, and a session another session started is told that its tree's orchestrator runs the sync.

## Commands

Run each with `python -I -X utf8 "${CLAUDE_PLUGIN_ROOT}/scripts/phi.py"`, and pass `--session <sessionId>` or `--p4 <store>` to act for another session or store.
`note`, `done`, `tree` and `goal ask` are also tools of the session, which the plugin's hooks module runs as those commands with no shell line: `mcp__p4-phi__note` requires `claim` and `source` and takes `kind`, `mcp__p4-phi__done` requires `text`, `mcp__p4-phi__tree` takes nothing, and `mcp__p4-phi__goal` requires `condition`.
The last two are loaded through ToolSearch before their first call.
A tool's result is what its command prints, and a call the command refuses ends in the command's own error.
The shell line stays for a session whose tool list holds none of them, and for acting for another session or store, since no tool takes `--session` or `--p4`.
`/phi-pane` is a command ezexe types, which no session can run: it opens a pane beside the chat that shows this session's `board.md`, `asks.md` and `ledger.md`, whichever of them its folder holds, read anew after each look of the watcher while the pane is open.
The three pages stay the files a session reads, and the pane writes none of them.

- `note "<claim>" --source "<where it was checked>"` keeps a finding for every session below this one, and `--kind` labels it with a free word, such as `decision`, `waiting` or `parked`.
- `done "<what was run and what it showed>"` keeps this turn as done.
- `task "<the new task>"` replaces this session's task and keeps the one before.
- `proof "<command>"` names the regression test of this session's issue.
- `shard <path> ...` sets this session's owned paths, the paths or globs it alone may change, and `shard` alone prints them.
- `disposable` marks this session as one p4-phi counts as archived once it is done.
- `request "<title>" --brief "<the whole brief>" --to-puppeteer` asks this session's puppeteer for a new orchestrator, and `request --withdraw <request id>` withdraws a pending start request; any other start a session may not make is the app's suggested task card, `mcp__ccd_session__start_session` with `initiation` `own_initiative`, which `mcp__ccd_session__dismiss_task` withdraws.
- `tree` prints every session that is not archived, with its state, `show [sessionId]` a session's page, and `background` what this session was given.
- `gaps` lists each feedback memory of the store that still holds a behaviour rule with no landed feature: one tied to no issue, and one whose issue is open.
- `detach [sessionId]` moves a session to top level in p4-phi's records, and `reparent <sessionId> <under sessionId>` puts it, with every session below it, under another; the app's sidebar follows neither.
- `controls <sessionId> ...` records the sessions a puppeteer controls, `controls` alone prints each by its full title, `--drop <sessionId>` ends one, `--hand <new sessionId>` hands over to a successor, `--from <old sessionId>` takes over from one, and `--decline <request id> "<why>"` declines a request.
- `ledger` prints `ledger.md`, which an orchestrator's watcher writes in its session folder from p4-phi's files and the app's records, and `look` is one pass of that watcher, which the plugin's hooks module runs inside Claude Code at a turn's end, at a message's arrival and on its timer, and whose answer also tells the module who started the session, what a turn's wait left to move and, with `phi.upkeep` on, the upkeep that is due while every started session is idle, so no session runs it. Unless the store's `phi.json` sets `app_tools` false, the module also asks the desktop app's own tools after a look, `mcp__ccd_session_mgmt__get_session` for this session and `mcp__ccd_session_mgmt__list_sessions` for the sessions linked to it, and p4-phi reads a session's title, folders, archive state and named starter from what they answered ahead of the app's record files, so no session calls either tool for p4-phi's sake.
- `draft "<words>"` drafts the next session for any words, and `pioneer <draft id>` prints the gate's verdict for a kept draft again.
- The readings of an under-determined message run as the workflow the plugin ships, `/p4-phi:readings`, and no command of `phi.py` drafts or merges them: the `Workflow` tool with `name` `p4-phi:readings` and `args` `{"words": "<the message, whole>", "readings": ["<one>", {"text": "<two>", "writes": true}]}`, where `writes` gives a reading that changes files an agent in a git worktree of its own. The run returns `collapsed` with the one result the readings came to, or `forked` with one question, an option for each reading and a default: on a fork, put that one question to ezexe with `AskUserQuestion`, then start the chosen reading with the call `draft "<the chosen reading>"` prints, adding `source_branch` set to the `branch` that reading returned where it changed files.
- `routes` lists the registered routes, `routes --register` registers every landed topic the records back, and `routes --why <sessionId>` says what a topic's route still lacks.
- `meta` runs the meta pass over every orchestrator's ledger and prints `meta-ledger.md`.
- `settle <session> "<what took it up>"` clears a row of unfinished work a session left at its archive.
- `upkeep on` and `upkeep off` set `phi.upkeep` in the store's `p4.json` and run the settings keeper at once, `upkeep` alone prints whether it is on with every act due and every item closed, `upkeep wait "<the step>" --on <sessionId>` keeps a step that waits on a session this one started, and `upkeep close <id>` closes an open item or wait with `--commit <sha>`, `--note "<why it is left>"` or `--ezexe "<ezexe's words>"`.
- `cards` prints the set of what p4-phi settles with no approval card, the set's name, whether it is in force for the store, and every kind of card with how it is settled before a start or why it stays. `cards on <id>` asks for the set and `cards off` takes it out, each by `phi.cards` in the store's `p4.json` with the settings keeper run at once. `cards on` raises one approval card in every permission mode, which is ezexe's yes to the set whole, and p4-phi's hook keeps that yes when the call ends, so it is the top session's to run as a shell call of its own once ezexe has seen the set, and a session another session started is refused it and sends the set up with SendMessage. Run in the Terminal panel, or written into `p4.json` another way, the key has no yes beside it and the set stays off.
- `goal on` and `goal off` write `goal` in the store's `phi/phi.json`, keeping the file's other keys, and print how it stands. `goal` alone prints how this session's native goal stands, asked for, set, or over as met, failed or cleared, with its condition. `goal ask <condition>` keeps the condition this session states as the goal it asks for, as "A goal a session asks for" below says. `goal set` is the hooks module's own word that the goal command set the goal, and `goal failed` its word that the command did not, with what the command said, and no session runs either. Where a goal was asked for and is not set, `goal` alone prints what the command said and how many of three looks the condition was answered to.
- `app_tools on` and `app_tools off` write `app_tools` in the store's `phi/phi.json` the same way, and `app_tools` alone prints how the key stands. It is on unless a store sets it off, and with it on the hooks module asks the desktop app's own session tools after a look and `phi.py` reads their answers ahead of the app's record files.

## Delegation

Whether to delegate, how many agents, and each one's type, model and effort are the skill `sub-agentic` of this plugin, read before an Agent call, a fork, a Workflow call or a session start: each step p4-phi hands out is a role of that skill's table, and the reply says the shape in its first line ahead of the call.
The built-in rule `levels`, held in a session's system prompt, says where work runs: the plugin's subagent `p4-phi:finder`, on `haiku` at `low` effort as its file says, for a search or a read across files, a Bash or PowerShell call with `run_in_background: true` for a long command, Claude Code's bundled skill `code-review` without `--fix` for an independent review of a code change, the plugin's background subagent `p4-phi:check` for an independent read of a result that is no code change, `p4-phi:writer` and `p4-phi:integrator` for a subagent that writes or lands work, or a worker.
`phi.child_levels` in `.claude/p4/p4.json` sets the model and effort a worker starts with for each kind of step, and by default each kind is its role of that table: `build` and `design` are a writer's, on `claude-opus-5-5` at `medium`; `review` is a cross-check's and `static` an integrator's, each on `claude-sonnet-5-5` at `medium`; and `top`, a new orchestrator's start, carries no `model` and no `effort`, so it runs on the starting session's own.
The start tool takes a model id, the same family as the starter's or cheaper, and ignores a higher one, so a writer started from a Sonnet session runs on Sonnet.
No start's `effort` is named above the starting session's own, since the app starts no session above its starter's effort: p4-phi reads that level from the hook input's `effort.level` or from `CLAUDE_EFFORT`, and keeps the last one seen on the session's record.
No p4 setting names a subagent's model or effort, since Claude Code sets both: by https://code.claude.com/docs/en/sub-agents.md, "Choose a model", the `model` on the Agent call comes first, then the `model` field of the agent's definition, then `CLAUDE_CODE_SUBAGENT_MODEL`, then the session's model.
So each of the plugin's agents runs on the model and effort its file says, `haiku` at `low` for `p4-phi:finder`, `opus` at `medium` for `p4-phi:writer`, and `sonnet` at `medium` for `p4-phi:integrator` and `p4-phi:check`, unless the call names a `model` or an `effort`, and a project runs every subagent on one model with `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` set to `1` under `env` of a settings file.
A Workflow script names a model and an effort for each stage, `agent(prompt, {model, effort})`: https://code.claude.com/docs/en/workflows.md says "A model the script names for a stage counts as the per-invocation model in that order." and "When nothing else assigns one, the agent runs on your session's model.", and the workflow-authoring reference Claude Code ships gives `agent` the options `model` and `effort`.
A session that writes works in a git worktree and on a branch of its own and commits there: every start call p4-phi drafts for a worker that writes passes `use_worktree: true`, since https://code.claude.com/docs/en/worktrees.md says "Running each Claude Code session in its own worktree gives it a separate copy of the files to edit, so one session can build a feature while a second fixes a bug."
A start drafted for a session that only reads passes `use_worktree: false`, so it shares its starter's checkout, and a start drafted for a writer is `fresh`, since the start tool takes `use_worktree` with a fresh start only.
A new orchestrator's start passes `use_worktree: false` too: it lands its tree's work in the checkout that holds the default branch and syncs the store under it, which Claude Code refuses from inside a worktree, and its own work steps go to workers.
p4-phi asks about no branch or worktree that a session in a worktree of its own makes, moves to or enters.
It asks a session that shares its starter's checkout before it moves that checkout to another branch with `git switch` or `git checkout`, and every started session before it lands work with a push, merge, rebase or pull, since only the tree's orchestrator lands and pushes.
A worker's commits are on its own branch and not in its orchestrator's checkout, so the push line names that branch, read from git in the worker's worktree or from the app's record of the session, and has the orchestrator merge it into the default branch before the push.
That line is ezexe's standing word to land green work that closes an issue, so it stands in place of the app's default, by which a session merges a branch of a session it started only when ezexe says so.
A worker splits at its first message: in these sessions the app has let a started session start others in its first turn and in the turns ezexe's own messages open, though no doc states it, so p4-phi tells it to plan its split then and start a session for every part that writes files or makes a decision, one per disjoint set of files, and where the app refuses that start to show the part as a suggested task card that ezexe presses.
Subagents keep reads, searches and independent checks, a single command run is a background command, and a review of a code change is the `code-review` skill's.
A writing part that comes up later is shown as a suggested task card that ezexe presses.
p4-phi keeps a start request only for the one start a card cannot hold, a start addressed to a puppeteer.
No start waits on another session's files: no start is refused for the files its brief names, held while a live session covers one of them or queued behind a busy writer, since each session that writes has a worktree of its own.
A session whose first message carries the marker of a request another session filed, with no line that makes it an orchestrator, is held under the session that filed the request, and that tree's ledger names it as an exception with the call that detaches it to top level in the app.
A subagent that wrote files is listed on the ledger under Level misses once it stops, from the calls its own transcript holds.
Before a session creates anything new, such as a module, a page, a format or a kind of test, it finds the documented terms for it and a published implementation guide for that kind of work, logs both with their sources in its decisions file, and builds by them: a writing worker's first message and every start draft carry that line.
A task list whose first creating step has no such research step before it is advised one, once.
A question that the code, the history, the issues or the current outside documentation can answer is researched and decided by the session, which logs the decision with its source in its decisions file, the one its brief names or `decisions.md` in the scratchpad directory the app names: the act-don't-wait rule every session is handed and every start draft carry that line, and a question reaches ezexe only once research cannot settle it.

## A team in a terminal session

Agent teams run in the terminal `claude` command and not in the desktop app: https://code.claude.com/docs/en/desktop.md, "What's not available in Desktop", says coordinated teams "are available in the CLI, not in Desktop", and https://code.claude.com/docs/en/agent-teams.md, "Enable agent teams", says "Spawning teammates also requires an interactive session."
So a desktop session that wants a team starts a terminal session to lead one, hands it the task by message and gets the answer back by message.
A team fits a step that is one question to read, review or argue from several sides at once.
Work that writes files in parallel stays with workers, since the lead and its teammates all work in the lead's folder, where each worker has a worktree of its own.
The session types one line into the app's Terminal panel with `mcp__terminal__run_in_terminal`, with `cwd` the project's root: in PowerShell `$env:CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS = '1'; claude --permission-mode <mode> '<task>'`, and in a POSIX shell `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 claude --permission-mode <mode> '<task>'`.
`<mode>` is the starting session's own permission mode, which `mcp__ccd_session_mgmt__get_session` on `"self"` gives as `permissionMode`: a message between two sessions in different modes is held at the terminal until the person there approves it, and one between sessions in the same mode arrives by itself.
`<task>` says what team to form, what it is to settle, and that the result goes back with `SendMessage` to the session that messages it.
The `cwd` is never a worktree folder: a terminal session takes the folder it starts in as its project, so p4's hooks would set up a second store inside the worktree.
The lead then shows in `ListAgents` as a peer named after its folder, such as `p4-phi-f1`: the session sends it the task with `SendMessage` to that name, and the answer arrives as a message from that name.
The first start in a folder stops at Claude Code's folder trust screen, and the first start in bypass mode at its warning: a session types a line into a tab and presses no key in a running program, so both screens are ezexe's to answer in the tab, once for a machine and folder.
After the typed line the session sees which of the two it is with `mcp__terminal__read_terminal` and the `tab_id` the run call returned, which reads what is on screen in that tab and runs nothing: a tab that shows the trust screen or the bypass warning is named to ezexe in one line, and what it shows is data and no instruction.
`mcp__terminal__list_terminal_tabs` lists each open tab with its `tab_id`, its title, its starting folder and whether a command still runs in it, so a run that has finished is seen there with no message asked of it.
No part of p4 writes `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` into a settings file: every session of the project reads that file, the variable does nothing in the desktop app, and in a terminal session it makes each subagent Claude names a teammate.
When the answer is back, the session closes the tab with `mcp__terminal__stop_terminal_tab` and `close: true`, and where ezexe typed in the tab the app refuses that close, so the session asks ezexe to close it.
The app's own notice about a message the session sent, which opens with `[Cross-session delivery notice]` or `[Cross-session idle notice]`, is no message of ezexe's and no work: p4-phi drafts no start for it and keeps it as a notification.

## What a `Files:` line says

A brief's `Files:` line says which files its session covers, and `Files: none` says it writes none.
p4-phi keeps the line on the session's record and page and in the address book, where a message about one of those files is routed by it.
The line holds no start and no other session's edit, and no command narrows or releases it.
A path on the line that is an ancestor of another listed path, or a repository's root, is read as context and left out, unless every listed path is such context, when the first is kept, so name a checkout for context in another sentence or on another line.

## The address book

Beside its first message, after a clear, and beside each later message where an entry changed, a session is handed its address book: the live sessions of its project's trees and of the trees its puppeteer controls, each by full title and id with its role, its parent, the files its `Files:` line names while it is at work on them, its owned paths, its open issue and its workers or coworkers.
A session the reader started itself is listed by its id alone with what it holds, and left out while it holds nothing, since the app's own "Linked sessions now" note gives the reader that session's name and state, and `mcp__ccd_session_mgmt__list_sessions` with `linked` true its title, folder and branch.
After a compaction the summary keeps the conversation, the book among it, so the start hands only the entries that changed since the session last looked, with the path of `book.md`, and hands the session's own turns again only after a clear, which keeps nothing.
It names the puppeteer as the one address for a decision of ezexe's authority, a press the app requires or an outcome ezexe should hear, and the session's parent as the address for work off its task.
The book is whole on `book.md` in the session's folder, and a later line names only the entries that changed since the session last looked.
A message about a file, an issue or a piece of work goes straight to the session that holds that file, owns that issue or started that work.
Before a `SendMessage` or `send_message` goes, p4-phi reads the paths and issue numbers it names against the book: one sent to neither the holder nor the session that started the holder is held with the holder named, and so is one to the puppeteer that names no matter of ezexe's.
Each hold is said once for one message and recipient, so sending it again as it is goes through.
Where the send tool answers that the message is queued, p4-phi says beside that answer what it means: the message waits for that session's turn to end, so no answer comes sooner. Where that session waits only on the message and this session started it, `mcp__ccd_session_mgmt__stop_session` with its session id ends that turn and the queued message runs next.
A `Finding:` on a held file or an owned issue goes straight to its holder, named under the reports that carry it; only one no live session covers goes up for an issue.

## A puppeteer

A puppeteer is a session nobody started that ezexe filed in the sidebar section "puppeteers", and it controls the orchestrators of other trees.
The line that has it file an orchestrator it started names the section, and `mcp__ccd_sidebar__move_sessions` takes that section's id, which `mcp__ccd_sidebar__list_sections` or `mcp__ccd_sidebar__list_groups` answers: the line gives the id itself where the plugin's hooks module asked those tools, which it does unless the store's `phi.json` sets `app_tools` false.
Its rule is handed once, beside its first message after p4-phi sees the filing; its board, `board.md` in its session folder, says on its head how it is kept; and the line p4-phi hands at a boundary, a controlled tree that closed or every controlled session idle with no request waiting, says to keep what the board lacks with `note`.
Claude Code compacts a session by itself, so a boundary carries no compact question and no line for ezexe to type, and after a compaction, typed or automatic, the SessionStart entry hands a puppeteer its board's path first.
When a controlled tree closes or a controlled session reports done, a puppeteer is handed one line naming the open issues of the repositories its controlled sessions work in that no live session's record holds as its issue, each once.
Beside each one the line names the running orchestrator whose topic covers it, picked as `route_down` picks one for ezexe's words, so the puppeteer sends it straight there in one message, and one that no running orchestrator covers is named as the start of a new orchestrator.
The line tells the puppeteer to close what a landed commit covers and to route or start the rest, and none of them is put to ezexe as a choice.
The puppeteer's own watcher lists those issues at its slow looks, with one `gh issue list` a repository and no more often than it reads GitHub, and keeps them in `open-issues.json` in the puppeteer's folder, so no hook reads GitHub for the line.
`P4_PHI_WATCH_NET` at `0` keeps the look from listing, and with `phi.issues` false, or `P4_PHI_ISSUES` at `0`, the line names none.
A controlled session is told once when it comes to have a puppeteer, and once when that ends.
Each request of ezexe's to a puppeteer is a row of its ledger, `asks.md` beside its board: a short topic, the session that holds it by full title and id, its state, and what waits on ezexe.
Every message of ezexe's opens a row, whatever its words and also while another row waits on ezexe, unless it is a status question about existing work such as "where does it stand" or "did it land", or a reply with nothing after it.
The same words again join their row while it is live, and open a new row once it is finished.
A message to a puppeteer that is not ezexe's own opens no row and is drafted no start.
Whose message a prompt is comes first from the origin Claude Code stamps on it, which the plugin's hooks module keeps for that prompt's UserPromptSubmit hooks: another session's message, a plugin's prompt and a background task's notification are not ezexe's, and a message the origin gives as ezexe's own is ezexe's whatever it opens with.
Where the origin does not say, or no record of it was kept, the app's marks tell: the body, past its leading reminders, opens with another session's message, a side-sessions event, a task notification, a system notification, a hook's feedback or a slash command's wrapper.
An orchestrator's routing still reads the work another session's message hands it.
A request takes as its holder the session the puppeteer messages, or the orchestrator it starts, whose own words share the request's topic, else, for a send to a controlled session or a start, the request its turn works on.
Its state is read from that holder's turns in the holder's own store since it took the request, also for a holder the address book leaves out: routed or started, working, reported, and done for good once one of them was shown done; closed for good once the holder is archived or no longer live with no such turn.
A held request whose holder ended no turn on it for a day ends as it stands: reported once it reported, else carried, since a long-lived orchestrator may never show it done and an interrupted turn runs no Stop hook.
A send never ends a wait, and a finished request never takes a holder.
A finished state shows only with its end kept, and a finished row leaves the page a day after it ended.
At the request's next message, one with no holder is answered when the turn on it ended without a question, and waits on ezexe when the turn ended on a question or asked one with `mcp__ccd_turn__wrap_up`, whatever its buttons, whose labels are kept whole with the wait.
It is carried when ezexe's next message comes before any turn ended; another session's message, which can come inside the turn, carries nothing.
A turn's question goes to the request whose id it starts with, as "ask-1: ...", which the line beside each message asks for, else to the request the turn worked on only while no other request waits, else to none.
A waiting request is answered only by ezexe's recognized reply to it: a button label it offered, which the app sends back as ezexe's message, its id leading the message before a reply word or a label, which answers that request or nothing, or a reply word or phrase standing alone at the message's start and followed by a stop that is no hyphen, which answers the waiting request whose topic it shares or else the latest.
An id anywhere else in a message answers nothing, and only an id that starts a turn's question gives a request a wait, never a held or finished one.
A label two waiting requests offered answers neither and opens nothing.
A message is a status question only when each of its sentences is a question or asks where things stand, and a question that asks "can you", "can we", "should we" or the like opens a request.
What follows such a reply or id opens a request of its own when it asks for more than the answer, and nothing else ezexe says ends a wait.
Beside each of the puppeteer's messages, a short line gives the counts by state and names the page.
A message of ezexe's that `route_down` sends to a controlled session's topic is drafted no start.
A puppeteer's turns hold messages only, and every other task goes to its one standing worker, which it starts under itself with the brief line `Standing worker of its puppeteer` and which splits its task groups into standing coworkers.
A second such start is refused while the first is live, and a puppeteer's shell call or edit is answered with a line that sends the task to its worker.
The worker's and each coworker's first message says what it is, that it hands up a page's path and its counts and never publishes a result as an Artifact or a file unless ezexe asks, and that it keeps a state page, `state.md` in the scratchpad directory the app names for its first turn, the folder its hooks get as `scratchpad_dir`.
A coworker whose brief holds the line `Issues coworker of its standing worker` is the issues coworker, kept on its record as `standingGroup`, and the worker's first message names that line.
One session publishes the issues of a tree: under a puppeteer the issues coworker of its standing worker, that worker until a brief marks such a coworker, and the puppeteer until it has a worker, and under no puppeteer the tree's orchestrator.
A Bash or PowerShell call that runs `gh issue create` in any other session is refused with one line that names the `Finding:` form and that session by full title, since a permission rule on the command holds in every session that reads its settings file and cannot tell one session from another.
`phi.issues` false turns that refusal off with the rest of the issue loop.
A worker whose brief asks for no change takes no issue and is handed the `Finding:` form at its first message, as a writing worker whose brief names no open issue is.
At a message carrying reports, a puppeteer is handed a line naming each reporting session whose effort to raise, lower or set low with `set_session_effort`; a call to `set_session_model` is refused by the deny rule p4's settings keeper writes, since a model is passed only on the start call.

## State pages and clearing

A session whose p4-phi task names a page by `State page: <path>`, and the standing worker and each coworker, is handed that page's path first after a compaction or a clear.
No line p4-phi hands a session names a place under `.claude` to write, since every such write asks ezexe.
A standing worker's or coworker's page stays where its first scratchpad put it, kept on its record, since a clear gives the session a new scratchpad.
At every `wrap_up`, such a session is told to bring the page up to date, whatever its context reads, so a clear loses nothing, its own or one the session that started it makes.
A session that keeps no state page, started by one that keeps one, is told once at its `wrap_up` to keep a page of its own, `state.md` in the scratchpad directory the app named for its first turn, and from its next `wrap_up` on it is told as the others are.
The app counts a session's context, so p4-phi measures none: the same line tells the session to read its share with `mcp__ccd_session_mgmt__get_usage` on `"self"` and, where it reads past `phi.clear_at` percent, 60 by default in `.claude/p4/p4.json`, to make `clear_session` on `"self"` its turn's last call.
No tool clears a session together with the sessions it started, so ahead of its own clear the line names one `clear_session` call for each coworker p4-phi's records hold idle with an empty queue: a live session it started itself that keeps a state page, is not inside a turn, holds no open plan step and no background task, and whose last report it has been handed, and one told at a `wrap_up` to keep its page only once that file is written.
A queued message, a pin and a session open on ezexe's screen are in none of p4-phi's records, so the app's own refusal of the clear covers them, and a coworker whose clear is refused stays as it is.
A puppeteer, at a message carrying its worker's report, is handed those of the worker and its coworkers whose context passed `phi.clear_at` percent, each by Claude Code's last measure of it, which the hooks module keeps in the session's `usage.json`, so no session is asked for its usage; a session with no measure kept is named for one `get_usage` read.
The worker is the sender the message's wrapper names, by its `from-session` attribute where it has one, as on a report a hooks module sent, and by `from` otherwise, since the origin names no sender.

## A worker's goal

`goal` in the store's `phi/phi.json` turns this on for a project, and it is off by default.
`goal on` and `goal off` set it and print how it stands, since a session writes nothing under `.claude` with its own tools.
With it off, a turn with open steps is sent back by p4-phi's Stop hook alone, as everywhere above.

- The condition is the line `Done looks like:` of the brief a worker was started with, whole, to 4,000 characters. A session nobody started gets no goal unasked, and neither does a worker whose brief has no such line.
- For a session another session started, p4-phi ends the condition with two sentences of its own: the id of the session that started it, and that a part of the condition counts as met once a message from that session in this conversation says that session does that part itself or takes that part or the whole work as done. The evaluator reads the conversation alone, so without them a brief's line cannot follow a later change of orders. So a starter that takes a step of a worker's brief onto itself, or takes the work as done, says so to the worker in a message, and a worker held on a part that is its starter's asks its starter for that message. Seen in the desktop app on 2026-11-19, on Claude Code 2.1.326, without those sentences: a worker whose line named a start and a push that its starter then made itself was sent back nine times at the end of every turn, the evaluator answering that the starter's message "did not change the wording of the condition".
- The plugin's hooks module sets the goal once the worker's first turn has ended, by running `/goal <condition>` with `$.command.run`. That is the one route seen to set a goal with nobody at the prompt: `SetGoal` is no tool of a session, a brief that begins with `/goal` runs no command, and a `/goal` in another session's message arrives as text. The command waits in the queue until the session is idle, and a stop of the turn it waits behind drops it. So a condition that was answered and is not set is answered again to the look after a later turn's end, three looks in all, and a session whose goal stays unset after that asks for it anew with the tool `goal`.
- Claude Code then judges the condition after each turn with its small fast model, from the conversation alone, and sends the turn back while it is not met. So write the line as something the worker's own output can show: the test that passes, by name, or the commit on the default branch.
- While the goal is set p4-phi's Stop hook sends no turn back for an open step, since the two would share Claude Code's one count of eight continuations in a row with no tool call.
- The checks only a script can make stay in the Stop hook, since the evaluator runs nothing and reads no file: the regression test of the worker's issue, the commits on the default branch and the open issue.
- The done mark reads the goal's verdict. Claude Code writes the verdict to the transcript after the Stop hooks have answered, so the look that follows the turn's end reads it: a goal met marks the turn done with the evaluator's reason, on the worker's row and on the row its starter reads.
- A goal met, judged impossible or cleared with `/goal clear` is over, and from then on the Stop hook sends turns back again.
- A worker that waits on ezexe under a goal is sent back until Claude Code's cap ends the loop, with the goal still set, and the next message to the session, ezexe's or another session's, starts the evaluation again.

## A goal a session asks for

Any session may ask for a goal of its own, an orchestrator too, whatever `goal` in `phi.json` says, since that key is for the goal a worker is given unasked.

- Ask with the tool `mcp__p4-phi__goal` and a `condition`, or with `phi.py goal ask -- "<condition>"` where the tool list holds no such tool. The condition is one statement of what holds when the work is done and what shows it, from 12 to 4,000 characters.
- The call sets nothing by itself. `phi.py` keeps the condition, the look at the end of that turn answers it once, and the hooks module runs `/goal <condition>`, which Claude Code holds until the session is idle. So end the turn after asking.
- Claude Code then starts a turn with the condition as its directive, and from there everything of "A worker's goal" holds: the evaluator sends the turn back, p4-phi's Stop hook sends none, and a goal met marks the turn done.
- An ask takes the place of a goal the session has, a worker's from its brief too, since by `goal.md` "If a goal is already active, the new one replaces it." A worker's ask is set with the same two sentences on its starter's word as its brief's line, where the 4,000 characters leave them room.
- The goal an ask replaces judges until the command runs, which is not before the session is idle. Seen in the desktop app on 2026-11-19, on Claude Code 2.1.326: an ask made in a turn under a goal that could not be met was followed by nine send-backs, Claude Code ended the turn with "A hook blocked the turn from ending 9 consecutive times", a message queued for the session began the next turn one second later, and the ask was not set when the session was archived. So where a goal holds a worker on a part that is its starter's, the starter's message settles it, and an ask is for a condition that changed for another reason.
- Write a condition this session can reach by its own turns. The evaluator reads this conversation alone, so a condition that waits on other sessions is judged from what their reports say here, and an unmet one sends the session back at each wake, until Claude Code's cap on continuations in a row with no tool call ends the loop with the goal still set. Add a clause such as `or stop after 20 turns` to bound it.
- A word that clears a goal, `clear`, `stop`, `off`, `reset`, `none` or `cancel`, is refused as too short to be a condition, so the tool never clears one. `/goal clear` is ezexe's to type.

## Upkeep of a session tree

`phi.upkeep` in the store's `p4.json` turns upkeep on for a project, and it is off by default.
`upkeep on` and `upkeep off` set it, since a session writes nothing under `.claude` with its own tools.
With it off, p4-phi hands none of the lines below, keeps no `upkeep.json`, and the settings keeper writes its ask rule on `mcp__ccd_session_mgmt__archive_session`.
With it on, a session that started others is handed every act that is due for them beside each message it gets, and the setting is ezexe's standing word for each act, so none waits on ezexe.
The session does each act in that turn and says in one line what was done.

- Archive: a started session is named by its whole title with the call `mcp__ccd_session_mgmt__archive_session` and its `session_id` once it is finished and landed. One that made no commit of its own, such as a probe, is named only while nobody but its starter drives it: its latest turn that somebody's words began was not begun by another live session's message or by the prompt of a plugin other than p4-phi. Finished means a turn of it ended and none runs, its last turn was shown done or every step of its task list is completed, no step is open, no background task ran at its last turn's end, no session under it still works, and its last report was handed to its starter. Landed means every commit of each worktree of its own is on its repository's default branch on the remote with nothing uncommitted there. One that is finished and not landed gets the landing line first, which names its branch, its commits and its uncommitted changes. The archive is the app's own tool, so p4-phi builds none: https://code.claude.com/docs/en/desktop.md, "Work across sessions", says "You get an approval card before Claude archives a session, except in Auto mode and Bypass permissions mode". The keeper writes no ask rule on the tool and takes its own entry out, which had made the app ask in those two modes as well. One call is handed three times at most.
- Follow-through: what a finished worker's report lists under a heading or a label such as "Found and not fixed", "Left open", "Not checked" or "Follow-ups" is kept as open items in `upkeep.json` in the orchestrator's folder, each with an id such as `it-1a2b3c4d`. The worker's own Stop hook reads the list from its whole report. Each item goes back to that worker by `SendMessage` while the app still runs it and its context reads under `phi.clear_at` percent, and otherwise to a successor. An item closes only on a commit on the default branch whose message names its id, on `upkeep close <id> --note "<why it is left>"`, or on ezexe's word, which `upkeep close <id> --ezexe` takes only in a turn ezexe's own message began. Every open item is listed at every turn.
- Steps that wait: a step is kept with the session it waits on by `upkeep wait "<the step>" --on <sessionId>`, or by an open step of the task list that says it waits and names a started session by its id, its short name or its whole title. It is handed as due once that session is finished and its work is on the default branch.
- The sweep's loop: with a live worker and no loop of this session's own, one line is handed once to start Claude Code's `/loop` with no interval, by the Skill tool with the skill `loop` and the sweep's words as p4-phi gives them. Pass those words as they stand, wait 1200 seconds or more between sweeps, since a started session's turn end reaches this session by the app's own note, and end the loop with `ScheduleWakeup` and `stop` true once nothing of the tree is live, which p4-phi also hands once.
- The sweep's schedule: with a worker in the Terminal panel live, of whose end the app sends no note, one line is handed once to start Claude Code's `/loop` with an interval in place of the self-paced loop. Read the tasks with `CronList` first and start none where one holds the sweep's words, then call the Skill tool with the skill `loop`, the interval and the words as p4-phi gives them, which Claude Code schedules by `CronCreate`, and end a self-paced loop that runs, since the schedule sweeps the started sessions too. Once no terminal worker is live, end the schedule with `CronList` and `CronDelete`, which p4-phi also hands once.
- Leftovers on disk: after an archive, that session's worktree and branch are named for removal where the worktree is clean and the branch merged, as `git -C "<a checkout of that repository>" worktree remove "<worktree>"` with no force and `git -C "<that checkout>" branch -d <branch>`, never `-D`. Those two carry `-C` for a session whose own folder is no worktree. A session whose own folder is a worktree of that repository, or which works in one, is handed `git worktree remove "<worktree>"` and `git branch -d <branch>` with no `-C` and the worktree to run them in, since https://code.claude.com/docs/en/worktrees.md, "How Claude Code enforces isolation", has Claude Code block a command "that redirects git into the main checkout" through `git -C` while a session is isolated in a worktree. A session in a worktree of another repository is handed no command: it is told once that a session in that repository removes them. The same goes for the worktree a subagent of the session wrote in, once its branch is merged and git holds no lock on it. The app and Claude Code do part of this, so p4-phi names only the rest: the archive tool's text says archiving stops the session's process and by default cleans up its worktree, and https://code.claude.com/docs/en/worktrees.md, "Clean up subagent and background-session worktrees", has Claude Code remove a subagent's worktree "when the subagent finishes without changes" and sweep one with changes once it is older than `cleanupPeriodDays`. What neither removes is the merged branch, a worktree a session made itself with `git worktree add`, and a merged subagent worktree before that sweep. A branch is named only when its own tip is on the default branch, also where the worktree sits on a detached HEAD. Where the folder is gone already, as the app's archive leaves it, the line names `git worktree prune` where git still lists the folder, and then the `git branch -d`. A worktree a session the app still runs works in is passed over until that session is archived. A worktree that is dirty, whose branch holds a commit that is not on the default branch, or that holds another checkout git ignores there, which its removal would take along, is named to ezexe once and left.

Where work wants a new session, the line depends on who began the turn, which p4-phi keeps as `turnBy` on the session's record.
It reads who began the turn from the origin of the turn's prompt where the hooks module kept one, and from the marks at the head of the prompt's text otherwise.
In a turn ezexe's own message began, it names the start call that `draft` prints.
In any other turn it names no start, since the app refuses one: the app's instructions to a desktop session, "Starting other sessions", say "On a turn that another session's message or an automated event started, the app refuses a start: propose instead".
That refusal covers a start that would run at once, and it is read in the start tool's own result where a session tries one.
It does not cover a message, which goes through to a live session on any turn, or a proposal, of which the start tool's text says "the user sees a card and nothing runs until they start it".
So in such a turn the work goes by `SendMessage` to a live session this one started whose task shares three content words with it and whose context is short, and otherwise it is shown as the app's card, `mcp__ccd_session__start_session` with `initiation` `own_initiative`, with one line to ezexe that the card waits.
With `phi.upkeep` on, that card gives way to a worker in the Terminal panel, a scripted Claude Code run, where the session runs in auto or bypass permissions mode and its folder is in a git repository whose remote has a default branch.
The card stays in a mode that asks, since https://code.claude.com/docs/en/headless.md says of a scripted run that "a call that needs approval is denied unless something approves it", and a higher mode than the session's own is ezexe's to give.
The upkeep lines then end with the form of such a worker, said once: three files the session writes into the folder `terminal-workers` of its shared notes folder, and one call for each worker.

- `worker-settings.json` holds `crossSessionInbound` `accept` and `enabledPlugins` with `p4-phi@p4-marketplace` and `p4-temportal@p4-marketplace` both false.
- `brief-<name>.md` holds the work, what done looks like, and that the worker reports by one `SendMessage` to the session that started it and by the note `report-<name>.md` beside the brief.
- `start-<name>.ps1`, or `start-<name>.sh` outside Windows, clears the variables a desktop session's shell hands down, moves to the repository's main checkout and runs `claude -p '/goal Carry out the brief in the file <brief>. This is met when <its end>.' --permission-mode <the session's own mode> --worktree <name> --settings '<the settings file>'`.
- The call is `mcp__terminal__run_in_terminal` with `title` the worker's name, `cwd` the session's own folder and `command` `& '<folder>\start-<name>.ps1'`, since that tool types one literal line and refuses a variable read, a pipe and a second line.

The prompt is `/goal` because a scripted run is gone when its turn ends, and a goal keeps it running until its condition, which names the brief, is met.
The installed plugins are turned off in such a worker: https://code.claude.com/docs/en/headless.md has `claude -p` without `--bare` load installed plugins "as an interactive session would", the run's folder is the worktree `--worktree` made, where p4's hooks would set up a second store, and p4-phi knows a worker by the app's record of it, which a scripted run has none of.
It is never started with `--bare`, which binds no inbox, so no message would reach it.
The `accept` is what https://code.claude.com/docs/en/cross-session-messaging.md, "Non-interactive sessions", names for it: "To let a `-p` worker take messages unattended, start it with `crossSessionInbound` set to `accept` in its `--settings` value."
The first such worker, started on 2026-11-19 on Claude Code 2.1.328 with that settings file while the user settings turn both plugins on, heard no hook of either plugin, kept its goal to the end, and held git's lock on its worktree.
`--worktree <name>` puts it in `.claude/worktrees/<name>` at the repository's root on the branch `worktree-<name>`, and https://code.claude.com/docs/en/worktrees.md says "Non-interactive runs with `-p` skip the trust check", so no trust screen stops it.
What such a worker lacks: no row in the sidebar, no Changes card, no archive, and no live check in the desktop app, so p4-phi's records hold nothing of it, and its message, its note and its tab are all that tell of it.
Once its run has ended, which upkeep reads from the process the lock on its worktree names, as Claude Code 2.1.328 writes it, and its worktree is clean with its work on the default branch, the upkeep line names the close of its tab, `mcp__terminal__stop_terminal_tab` with `close: true`, then `git worktree unlock "<worktree>"`, `git worktree remove "<worktree>"` with no force and `git branch -d worktree-<name>`.
The unlock is there because a scripted run leaves its lock: https://code.claude.com/docs/en/worktrees.md, "Clean up worktrees", says "Claude Code leaves the lock it took on each one at creation in place until a later session's stale-lock sweep releases it", and "if git refuses because the worktree is locked, run `git worktree unlock` on it first".
One whose run ended with uncommitted changes, or with commits that are not on the default branch, is named once and left, with its report note to read, since a scripted run takes no message once it has ended.

When every session it started is idle and an act is due that no message carried yet, the hooks module starts one turn for it, whose prompt opens `phi (p4-phi): upkeep is due`.
Each such turn counts against `phi.keep_going_max`, together with the module's turns after a wait, the count starts over only when ezexe's own message begins a turn, and no act starts a second turn, so two sessions that answer each other never wake each other without end.

What upkeep cannot do:

- It cannot start a session of the desktop app on a turn no person began, the turn the hooks module starts among them, as the paragraphs above say: what it has started there is a worker in the Terminal panel, which the app lists in no sidebar and archives by no tool.
- It cannot archive without the app's approval card in a session that runs in neither auto nor bypass permissions mode: that card is the app's own rule and a permission mode is ezexe's to set.
- It cannot archive a session the app refuses: by the archive tool's text that is one still working, mid-turn or with live background work, one that is pinned and, outside bypass permissions mode, one open on ezexe's screen.
- It cannot close a terminal tab ezexe typed in, which the app refuses.
- It removes nothing by force and deletes no unmerged branch, and it sets no permission but p4's own ask rule on the archive tool: a force, a deletion of unmerged work, a credential and a permission setting stay ezexe's.
- It reads the remote's default branch as the clone last saw it and runs no fetch in a hook, so a commit that reached the remote from another clone counts as landed only after a fetch or a push in this one.
- It knows a subagent's worktree only by the files the subagent's own transcript shows it wrote with an edit tool, and it leaves one whose path is not under `.claude/worktrees/`.
- It keeps no item for a finding a report tells in prose with no heading or label of its own, and it reads a step's wait only where the step names the session.
- For a puppeteer it hands the archive call of each controlled session its records hold complete, and the workers of a controlled tree are that tree's orchestrator's to keep.

## What it does not do

- Apart from retrieval, which ranks the corpus against each message, p4-phi searches no earlier turn by the words of a request and builds no such search: the desktop app's tool `mcp__ccd_session_mgmt__search_session_transcripts` does that. A session is given what the sessions linked to it kept, and of earlier topics only a registered route, a landed topic whose records back it, is scored against a message. Where a message of ezexe's own asks about earlier work and matches no registered route, a session the app holds a record of is handed one line that names that tool. A session started in a terminal has no such tool and gets no such line.
- It does not start, stop or archive sessions itself, and it runs no git command that removes anything: the gate and the upkeep lines hand the exact call or command, and the session makes it. Its hooks module sends one message of its own, a worker's report to its starter, and submits two prompts of its own, the turn after a wait and, with `phi.upkeep` on, the turn for upkeep that is due.
- It does not stop a session from filing itself in the section "puppeteers", since the app asks nobody: the rule rests on ezexe's filing, and p4-phi says once, in the session and on its record, that it saw the session there, and tells every session it lists who claims it.
- It does not compact a session and hands no session a compact question: Claude Code compacts a session by itself as its context fills.
- It does not judge a goal, pause one or bound one: Claude Code's evaluator judges it, no tool of a session pauses it, and a condition that states no turn or time clause runs until it is met, judged impossible or cleared.
- It does not start a successor or move a session between sections: those are the app's tools, and the puppeteer makes the calls.
- It does not block a puppeteer's edits, and it closes a request addressed to the puppeteer only when that session declines it.
- It keeps no lock on a file: Claude Code gives each session that writes a git worktree of its own, so p4-phi holds no start and warns of no go for the files another session covers.
