# p4-phi: upkeep of a session tree

## Upkeep of a session tree

`phi.upkeep` in the store's `p4.json` turns upkeep on for a project, and it is off by default.
`upkeep on` and `upkeep off` set it, since a session writes nothing under `.claude` with its own tools.
With it off, p4-phi hands none of the lines below, keeps no `upkeep.json`, and the settings keeper writes its ask rule on `mcp__ccd_session_mgmt__archive_session`.
With it on, a session that started others is handed every act that is due for them beside each message it gets, and the setting is ezexe's standing word for each act, so none waits on ezexe.
The session does each act in that turn and says in one line what was done.

- Archive: a started session is named by its whole title with the call `mcp__ccd_session_mgmt__archive_session` and its `session_id` once it is finished and landed. One that made no commit of its own, such as a probe, is named only while nobody but its starter drives it: its latest turn that somebody's words began was not begun by another live session's message or by the prompt of a plugin other than p4-phi. Finished means a turn of it ended and none runs, its last turn was shown done or every step of its task list is completed, no step is open, no background task ran at its last turn's end, no session under it still works, and its last report was handed to its starter. Landed means every commit of each worktree of its own is on its repository's default branch on the remote with nothing uncommitted there. One that is finished and not landed gets the landing line first, which names its branch, its commits and its uncommitted changes. The archive is the app's own tool, so p4-phi builds none: https://code.claude.com/docs/en/desktop.md, "Work across sessions", says "You get an approval card before Claude archives a session, except in Auto mode and Bypass permissions mode". The keeper writes no ask rule on the tool and takes its own entry out, which had made the app ask in those two modes as well. One call is handed three times at most.
- Follow-through: what a finished worker's report lists under a heading or a label such as "Found and not fixed", "Left open", "Not checked" or "Follow-ups" is kept as open items in `upkeep.json` in the orchestrator's folder, each with an id such as `it-1a2b3c4d`. The worker's own Stop hook reads the list from its whole report. Each item goes back to that worker by `SendMessage` while the app still runs it and its context reads under `phi.clear_at` percent, and otherwise to a successor. An item closes only on a commit on the default branch whose message names its id, on `upkeep close <id> --note "<why it is left>"`, or on ezexe's word, which `upkeep close <id> --ezexe` takes only in a turn ezexe's own message began. Every open item is listed at every turn.
- Steps that wait: a step is kept with the session it waits on by `upkeep wait "<the step>" --on <sessionId>`, or by an open step of the task list that says it waits and names a started session by its id, its short name or its whole title. It is handed as due once that session is finished and its work is on the default branch.
- Steps that fall due when no session is open: a step that waits on a time is kept by `upkeep wait "<the step>" --at "<when>"`, with the step written whole, as for a run that knows nothing of this session. It prints the scheduled run that fits and makes none, since making one starts sessions later and is ezexe's. For a step that needs only the repository it prints a `/schedule` command: give it to ezexe to type, as it stands and in a fenced block of its own, and do not run it yourself. With `--local`, for a step that needs the project's local store, it prints a Desktop scheduled task's instructions: put it to ezexe once, by the app's own question, and make it with `mcp__scheduled-tasks__create_scheduled_task` on ezexe's yes alone. Close the wait with `upkeep close <id> --note` once ezexe has answered.
- The sweep's wake-ups: p4-phi hands no `/loop`. A session this one started in the app is told of by the app's own note of its turn end. For a worker in the Terminal panel, of whose end the app sends no note, one line is handed once while its run works, and again after each notice: call `SendMessage` with `to` the worker's name, `notify_when_idle` true and no `message`. One `[Cross-session idle notice]` then begins a turn here once that worker goes idle or exits. One subscription gives one notice, and a worker that was stopped from outside sends none.
- The sweep's schedule: with any worker out and no schedule of the sweep kept, one line is handed once: read the tasks with `CronList` and start none where one holds the sweep's words, then call `CronCreate` with the expression and the words as p4-phi gives them and `recurring` true. Pass the words as they stand. The schedule covers what no event tells: a session that stalls, a worker whose notice does not come, and for a puppeteer a session it controls and did not start, of whose turn's end nothing else tells it. Once nothing is live, end it with `CronList` and `CronDelete`, which p4-phi also hands once.
- Leftovers on disk: after an archive, that session's worktree and branch are named for removal where the worktree is clean and the branch merged, as `git -C "<a checkout of that repository>" worktree remove "<worktree>"` with no force and `git -C "<that checkout>" branch -d <branch>`, never `-D`. Those two carry `-C` for a session whose own folder is no worktree. A session whose own folder is a worktree of that repository, or which works in one, is handed `git worktree remove "<worktree>"` and `git branch -d <branch>` with no `-C` and the worktree to run them in, since https://code.claude.com/docs/en/worktrees.md, "How Claude Code enforces isolation", has Claude Code block a command "that redirects git into the main checkout" through `git -C` while a session is isolated in a worktree. A session in a worktree of another repository is handed no command: it is told once that a session in that repository removes them. The same goes for the worktree a subagent of the session wrote in, once its branch is merged and git holds no lock on it. The app and Claude Code do part of this, so p4-phi names only the rest: the archive tool's text says archiving stops the session's process and by default cleans up its worktree, and https://code.claude.com/docs/en/worktrees.md, "Clean up subagent and background-session worktrees", has Claude Code remove a subagent's worktree "when the subagent finishes without changes" and sweep one with changes once it is older than `cleanupPeriodDays`. What neither removes is the merged branch, a worktree a session made itself with `git worktree add`, and a merged subagent worktree before that sweep. A branch is named only when its own tip is on the default branch, also where the worktree sits on a detached HEAD. Where the folder is gone already, as the app's archive leaves it, the line names `git worktree prune` where git still lists the folder, and then the `git branch -d`. A worktree a session the app still runs works in is passed over until that session is archived. A worktree that is dirty, whose branch holds a commit that is not on the default branch, or that holds another checkout git ignores there, which its removal would take along, is named to ezexe once and left, and so is one that holds a link among what git does not track there. `phi.py remove "<worktree>"` does one removal whole: it refuses while the shell that ran it stands in the worktree, checks that the worktree is clean, landed and free, removes it with no force and deletes its landed branch, and it deletes the folder a failed removal left. See more: https://code.claude.com/docs/en/worktrees.md

Where work wants a new session, the line depends on who began the turn, which p4-phi keeps as `turnBy` on the session's record.
It reads who began the turn from the origin of the turn's prompt where the hooks module kept one, and from the marks at the head of the prompt's text otherwise.
In a turn ezexe's own message began, it names the start call that `draft` prints.
In any other turn it names no start, since the app refuses one: the app's instructions to a desktop session, "Starting other sessions", say "On a turn that another session's message or an automated event started, the app refuses a start: propose instead".
That refusal covers a start that would run at once, and it is read in the start tool's own result where a session tries one.
It does not cover a message, which goes through to a live session on any turn, or a proposal, of which the start tool's text says "the user sees a card and nothing runs until they start it".
So in such a turn the work goes by `SendMessage` to a live session this one started whose task shares three content words with it and whose context is short, and otherwise it is shown as the app's card, `mcp__ccd_session__start_session` with `initiation` `own_initiative`, with one line to ezexe that the card waits.
With `phi.upkeep` on, that card gives way to a worker in the Terminal panel, a scripted Claude Code run, where the session runs in auto or bypass permissions mode and its folder is in a git repository whose remote has a default branch.
The card stays in a mode that asks, since https://code.claude.com/docs/en/headless.md says of a scripted run that "a call that needs approval is denied unless something approves it", and a higher mode than the session's own is ezexe's to give.
The upkeep lines then end with the form of such a worker, said once: three files the session writes into the folder `terminal-workers` of its shared notes folder, and one call for each worker.

- `worker-settings.json` holds `crossSessionInbound` `accept` and `enabledPlugins` with `p4-phi@p4-marketplace` and `p4-temportal@p4-marketplace` both false.
- `brief-<name>.md` holds the work, what done looks like, and that the worker reports by one `SendMessage` to the session that started it and by the note `report-<name>.md` beside the brief.
- `start-<name>.ps1`, or `start-<name>.sh` outside Windows, clears the variables a desktop session's shell hands down, moves to the repository's main checkout and runs `claude -p '/goal Carry out the brief in the file <brief>. This is met when <its end>.' --permission-mode <the session's own mode> --worktree <name> --settings '<the settings file>'`.
- The call is `mcp__terminal__run_in_terminal` with `title` the worker's name, `cwd` the session's own folder and `command` `& '<folder>\start-<name>.ps1'`, since that tool types one literal line and refuses a variable read, a pipe and a second line.

The prompt is `/goal` because a scripted run is gone when its turn ends, and a goal keeps it running until its condition, which names the brief, is met.
The installed plugins are turned off in such a worker: https://code.claude.com/docs/en/headless.md has `claude -p` without `--bare` load installed plugins "as an interactive session would", the run's folder is the worktree `--worktree` made, where p4's hooks would set up a second store, and p4-phi knows a worker by the app's record of it, which a scripted run has none of.
It is never started with `--bare`, which binds no inbox, so no message would reach it.
The `accept` is what https://code.claude.com/docs/en/cross-session-messaging.md, "Non-interactive sessions", names for it: "To let a `-p` worker take messages unattended, start it with `crossSessionInbound` set to `accept` in its `--settings` value."
The first such worker, started on 2026-11-19 on Claude Code 2.1.328 with that settings file while the user settings turn both plugins on, heard no hook of either plugin, kept its goal to the end, and held git's lock on its worktree.
`--worktree <name>` puts it in `.claude/worktrees/<name>` at the repository's root on the branch `worktree-<name>`, and https://code.claude.com/docs/en/worktrees.md says "Non-interactive runs with `-p` skip the trust check", so no trust screen stops it.
What such a worker lacks: no row in the sidebar, no Changes card, no archive, and no live check in the desktop app, so p4-phi's records hold nothing of it, and its message, its note and its tab are all that tell of it.
Once its run has ended, which upkeep reads from the process the lock on its worktree names, as Claude Code 2.1.328 writes it, and its worktree is clean with its work on the default branch, the upkeep line names the close of its tab, `mcp__terminal__stop_terminal_tab` with `close: true`, then `git worktree unlock "<worktree>"`, `git worktree remove "<worktree>"` with no force and `git branch -d worktree-<name>`.
The unlock is there because a scripted run leaves its lock: https://code.claude.com/docs/en/worktrees.md, "Clean up worktrees", says "Claude Code leaves the lock it took on each one at creation in place until a later session's stale-lock sweep releases it", and "if git refuses because the worktree is locked, run `git worktree unlock` on it first".
One whose run ended with uncommitted changes, or with commits that are not on the default branch, is named once and left, with its report note to read, since a scripted run takes no message once it has ended.
A worktree that holds a link among what git does not track, such as a directory Claude Code linked by `worktree.symlinkDirectories`, is held from removal and named once with `phi.py unlink "<worktree>"`, which takes each link away and never its target, and then prints the `git worktree remove` to run, with no force.
The hold is there because https://github.com/git-for-windows/git/pull/6151 says "Similar to how `git clean` already avoids traversing NTFS junctions, `git worktree remove` now does the same", a fix that first shipped in Git for Windows 2.54.0.

When every session it started is idle and an act is due that no message carried yet, the hooks module starts one turn for it, whose prompt opens `phi (p4-phi): upkeep is due`.
Each such turn counts against `phi.keep_going_max`, together with the module's turns after a wait, the count starts over only when ezexe's own message begins a turn, and no act starts a second turn, so two sessions that answer each other never wake each other without end.

What upkeep cannot do:

- It cannot start a session of the desktop app on a turn no person began, the turn the hooks module starts among them, as the paragraphs above say: what it has started there is a worker in the Terminal panel, which the app lists in no sidebar and archives by no tool.
- It cannot archive without the app's approval card in a session that runs in neither auto nor bypass permissions mode: that card is the app's own rule and a permission mode is ezexe's to set.
- It cannot archive a session the app refuses: by the archive tool's text that is one still working, mid-turn or with live background work, one that is pinned and, outside bypass permissions mode, one open on ezexe's screen.
- It cannot close a terminal tab ezexe typed in, which the app refuses.
- It removes nothing by force and deletes no unmerged branch, and it sets no permission but p4's own ask rule on the archive tool: a force, a deletion of unmerged work, a credential and a permission setting stay ezexe's.
- It reads the remote's default branch as the clone last saw it and runs no fetch in a hook, so a commit that reached the remote from another clone counts as landed only after a fetch or a push in this one.
- It knows a subagent's worktree only by the files the subagent's own transcript shows it wrote with an edit tool, and it leaves one whose path is not under `.claude/worktrees/`.
- It keeps no item for a finding a report tells in prose with no heading or label of its own, and it reads a step's wait only where the step names the session.
- For a puppeteer it hands the archive call of each controlled session its records hold complete, and the workers of a controlled tree are that tree's orchestrator's to keep.
