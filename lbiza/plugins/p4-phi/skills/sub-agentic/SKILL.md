# sub-agentic: the right agent, the right number, said before it runs

Apply the rules as written.
Nothing here is a setting: each role's model and effort sit in the file of the agent this plugin ships for it, and in the start calls p4-phi drafts, so no project and no call has to name them.
The code-style rule is whatever the repository's own style skill or CLAUDE.md states.

## The rules

1. **Do it here unless delegation buys something.** A few tool calls, a lookup whose target is known, a quick targeted change, or work that shares context with the next phase stays in the conversation. A subagent is for verbose output kept out of context, independent work run in parallel, a reviewer that has not seen the reasoning, or a tool restriction to enforce. Handing the same task to a subagent does not make the answer better.
2. **Scale the count to the task.** Simple fact-finding is one agent; a comparison or a few independent checks is two to four; more than ten is for a broad audit, sweep or migration, and only when ezexe asked for that scale, by "thoroughly", by "use a workflow" or with ultracode on. The session's size guideline may be overridden, but say so; never silently. The read of a plan has a count of its own: the planner, a terminal session in plan mode, leads three teammates in its own session, where a group of the plan's sections earns a team at five fences or a check and smaller groups are joined to their neighbours.
3. **Say the shape first**, as the first line of the reply about the delegation and ahead of any Agent, Workflow or session-start call: the agent count or its bound, the phases, the model and effort per role, the loop's bound, and what each agent may write. Queue nothing behind a running workflow without the same line for it.
4. **Bound every loop.** A verify-and-fix loop names its maximum rounds; loop-until-dry stops after two dry rounds; the rounds of a plan's read end, group by group, at the group's first clean round and stop short of it only where its held findings are more than in its round before, as p4-temportal's skill `plan-planner` says; a baseline runs only when ezexe asked for the comparison. One workflow is one phase: launch the next after reading the result, never queued ahead.
5. **Set model and effort on every agent by its role; nothing inherits by default.** On an Agent call, the `subagent_type` of the role's agent carries its `model` and `effort` in its file; a call that needs another passes `model`, an alias such as `opus`, `sonnet` or `haiku`, and `effort`. In a Workflow script, `agent(prompt, {model, effort})`. A session start takes `model` as a model id, the same family as the starter's or cheaper, and `effort` at or below the starter's, and p4-phi's start advice names both for each step. A fork runs on the session model.

   | Role | Agent type / model / effort | A session start | The work |
   |---|---|---|---|
   | writer | `p4-phi:writer` / opus / medium | `claude-opus-5-5` at `medium` | content the tree does not hold yet: a plan, a section, a skill, a build, a decision with its sources; the brief carries the scope |
   | planner | never a subagent | never a desktop start: `draft --start` starts a draft whose brief says its session starts in plan mode as a terminal worker in plan mode, with the team variable set, on the kind `plan`'s model and effort, `claude-fable-5-2` at its starter's own effort | holds and writes a plan in plan mode: it is the one writer of its plan file, forms its three readers in its own session, and the plan's approval is answered in its tab |
   | integrator, fixer | `p4-phi:integrator` / sonnet / high | `claude-sonnet-5-5` at `high` | lands written fences, verified findings or static and mechanical work; its brief names the check that proves the landing |
   | cross-check, judge, grader, truth check | `p4-phi:check` / sonnet / high, or the bundled skill `code-review` without `--fix` for a code change | `claude-sonnet-5-5` at `high` | re-reads another agent's output from the sources against stated criteria, nothing of the first agent's report |
   | evidence finder | `p4-phi:finder` / haiku / medium | never a session | paths, line numbers, snippets, inventories, link checks, counts: no decision |
   | team of readers | never an agent type of its own: the lead runs on Sonnet at high by its start line and names each teammate by the side it takes, on Sonnet, where it inherits the lead's effort | never a start call: a terminal lead, as the skill `phi` says under `A team in a terminal session` | one question read, reviewed or argued from several sides at once, where the readers must challenge each other; never parallel writing |
   | worker below an orchestrator | never an agent type of its own: a terminal session in the checkout, with no worktree, on the model and effort of the kind `static` by its start line, with a goal as its prompt | never a desktop start: `phi.py draft` and then the `draft --start` line, or `phi.py sections` for an approved plan, each printing the `mcp__terminal__run_in_terminal` call that opens its tab | the task of one brief, or the landing of one group of an approved plan, held to its `Files:` paths, ending on a report file its orchestrator waits for |
   | a run exercising a skill or the product as the day-to-day agent would | the session model | no `model`, no `effort` | a test of what the everyday agent does |
   | orchestrator, fork | the session model | no `model`, no `effort` | the main loop, an orchestrator under the session that started it, and a fork of it |
   | fable | only when ezexe names it | only when ezexe names it | named for the planner, and never the default writer |

   The levels rest on the two model pages. Each model starts at its own default effort: `medium` for Opus and Haiku, `high` for Sonnet and Fable, since Sonnet at `medium` loses on code. Effort is raised before the model is switched: a writer whose check fails at `medium` runs again at `high` or `xhigh` before anything moves to Fable. `low` is only for work a test or another failure signal checks, so that its failures run again at a higher effort; a finder has no such signal, and runs at Haiku's default. Fable is only for what ezexe names it for, or where Opus at `xhigh` still falls short. Haiku is for evidence finding and other high-volume work whose output can be checked. An orchestrator with cheaper workers pays only where the work fans out across independent files or more than one context window, as rules 1 and 13 split it; a single chain of dependent steps stays with one model at a lower effort. Compare a level by its cost per finished task, not per token.

6. **The brief is the agent's only context.** It carries the objective; the output form, a schema when the result feeds code; the files and pages to read; the boundaries: the directory it may write, the read-only list, no commit, no build, no apply; the done-when it runs itself; and every premise about the tree as a question with the file that answers it. A code-writing brief makes the repository's code-style rule part of its done-when, and the cross-check's brief checks it. A brief asks for no test of a document's or a string's wording, since a test checks what code does. A brief carries what was asked, the files and what done looks like, and adds no step nobody asked for: no research or plan document, no decision log, no leftover of another session's work, which gets a commit of its own once the task in flight has landed, and no stop at a context mark, since Claude Code compacts by itself. A brief that adopts a skill or a document from elsewhere says to build it on the feature the project already uses and to name each departure from the source, and asks for no word-for-word copy. A session's brief asks it to name in its first report everything the task will need from ezexe, so its starter brings all of it to ezexe once. A session started with `mcp__ccd_session__start_session` is the exception for the house rules: Claude Code loads its CLAUDE.md and the first lines of its memory index `MEMORY.md` at its start, p4-phi hands it each feedback or user memory that changes while it works, so its brief never tells it to read `.claude/CLAUDE.md` or `MEMORY.md` and names only the skills, plans, files and memory files this task needs. A subagent or a workflow agent gets no memory index, and its brief carries what it needs. A brief for an agent that works in a git worktree carries the lines `phi.py shared` prints, which name the main checkout's environment that the worktree runs on.
7. **Large outputs go to files.** An agent writes its report or spec to the session scratchpad and returns the path and a ten-line summary; structured results use a schema.
8. **Report the spend.** After a run: the agents launched and finished, the tool calls and tokens from the completion notice, `/workflows` or `/usage`, and what the next phase will cost before it starts.
9. **Ultracode changes the opt-in, not the duty.** It drops the warnings, the first-launch approval and the subagent concurrency limit, and tokens are spent faster; rules 2, 3 and 5 still hold.
10. **Writers never share files.** Two agents that write take disjoint paths in the one checkout; verifiers and finders are read-only, and `p4-phi:check` and `p4-phi:finder` hold only Read, Grep and Glob.
11. **What an agent wrote is read once before it counts, and the findings go back to the agent that wrote it.** The reader has not seen the writing: `p4-phi:check`, or the bundled skill `code-review` without `--fix` for a code change. Send what it finds to the same agent with `SendMessage` and its id, which continues that agent with its context, where a new agent would have to learn the work again. A finding is mended or answered with the reason it is no fault. One second read follows a mend, and there is no third, since a reader asked to find problems always finds something. A subagent cannot loop by itself, so the session that started it runs the round.
12. **A team is for readers that must challenge each other, and one reader is for the rest.** A step goes to an agent team only where its own words ask for several sides, lenses or competing explanations of one question, and where the sides gain from arguing: research across sources that disagree, a review split by lens, a fault with more than one likely cause. The read of a plan is such a review for each group of its sections: three readers by the lenses fences, sources and checks under a coworker, in rounds that the same team reads until one has nothing to mend, as p4-temportal's skill `plan-planner` says, and the planner asks the session that started it to start the coworkers by one command, since a session in plan mode writes only its plan file. A plan's one small group of prose, under five fences and with no check, stays with one reader. The read of rule 11 and a review of a code change each stay with one reader, `p4-phi:check` or the skill `code-review`: their criteria are stated ahead and one reader costs one agent's run. Sides that need no argument between them are subagents, or a workflow in the desktop app. A team's count follows rule 2, its shape is said first by rule 3, and its spend is reported by rule 8 from what `phi.py spend` prints for the lead, since a teammate's finish notice holds no token count. A team is led from a terminal session and never from the desktop app, and its teammates share the lead's folder, so rule 10 keeps every teammate a reader, and a coworker lands its group only once its teammates are shut down and only in a permission mode that does not ask. See more: https://code.claude.com/docs/en/agent-teams.md and https://code.claude.com/docs/en/costs.md
13. **Prep the shards before starting terminal workers.** Split the work into parallel worker shards before any `draft --start`, each shard held to its own `Files:` paths, disjoint from every other shard's. Choose the variant of each by its purpose, from what p4-phi states: Billing, the worker profile `p4-workers` bills a Claude Console account whose credit covers `claude -p` but not interactive Claude Code; Purpose, `-p` is meant for headless work such as landing changes, tests and checks; What you lose, under `-p` no teammates spawn, so an agent team, `ExitPlanMode` or a tab a person steers needs an interactive session. So `print`, `print api` or `print max` for headless landing, test and check work, `interactive` for work a person steers or approves, `team` for a step that rule 12 sends to a team. Size the count of each variant by the independent pieces with disjoint files and by the free slots of each pool, `worker_slots` of `phi.json`, `{"api": 4, "max": 2}` by default, where `print` takes an API slot and `interactive` and `team` take a Max slot. Say the split as one line before starting any, the variant and count per variant with the purpose that picked each, such as `split: 3 print (landing the parser, the writer and their tests), 1 team (review of the format from three sides)`; then write one draft per shard whose task file holds its `Runner:` line and its `Files:` line. A draft with no `Runner:` line falls back to a keyword guess, which `draft --start` labels as the fallback.

## Where p4-phi already does it

- Each role's model and effort is in its agent's file.
- A start p4-phi drafts names its model and effort in one line, `Model and effort: <model> at <effort> effort`, and `phi.child_levels` in `.claude/p4/p4.json` sets another for a kind of step; a brief's own `Model and effort:` line wins over its kind's.
- Where `phi.goal_review` is on, a worker's own goal asks for the round of rule 11 on its own change, so a session that changes files has it read without being told.
- No setting is needed for any of it: the agents' files and the drafted starts carry the table.
