Two trees that share a name

p4-phi keeps a tree of Claude desktop sessions. ezexe/phi has two trees of its own: the recursive Fibonacci call tree its Zeckendorf register page draws on its Tree tab, and the ensemble of shard models that phi_rank/tree.py builds out of small rankers. Change each tree below, then read the three side by side.

p4-phi · ezexe/p4

The session tree

Each place in it is a session. You make the tree one move at a time, and p4-phi writes each move down.

ezexe/phi

The call tree and the ensemble

Each place is a call or a store address. You choose one number, and the whole tree follows from it.

Side by side

The first column is p4-phi. The other two are ezexe/phi: the tree its page draws, and the ensemble its code builds and keeps.

What the tree is made of

Session treeSessions of the Claude desktop app, each with a task, turns, notes and a page.
Call tree, drawnCalls of fib(k). The page keeps each as an object with n, left, right, leafCount and a random id.
Ensemble, builtSmall rankers, its members, one at each store address. An address is a string of 1 for p4 and 0 for .claude that starts and ends with 1 and never holds two 1s in a row.

What a link means

Session treeThis session started that one. p4-phi hands tasks and notes down the link, and reports and replaces: notes up it.
Call tree, drawnThis call made that call. The left link goes to fib(k-1) and the right link to fib(k-2).
Ensemble, builtThe store at this address is grown under that one. A member with children starts its training from the mean of their weights as they stood before their fine-tuning.

How the tree grows

Session treeA session calls mcp__ccd_session__start_session. When the app refuses the call, the session shows a suggested task card for ezexe to start. p4-phi keeps a start request only for a start that waits behind a busy writer and for one addressed to a puppeteer.
Call tree, drawnYou move the slider. buildTree(n) makes every node of the tree at once, by recursion.
Ensemble, builtYou run python -m phi_rank.tree train with --k. It trains the first K addresses, the deepest first, and fine-tunes each member on every labelled pool. Pretraining each member on one shard of the store's tracked text is off unless --minutes turns it on.

How a part of it moves

Session treeWith phi.py detach a session is detached to top level, which makes it an orchestrator. phi.py reparent puts it, with every session below it, under another. Both rewrite spawnedFrom in its session.json, and the app's own nesting does not follow.
Call tree, drawnIt never moves. A call's place follows from its number.
Ensemble, builtIt never moves. parent(a) computes a member's parent from its address alone.

How a part of it leaves

Session treeOne at a time. A worker whose brief says “report when done” is counted as archived at the end of the turn that shows its work done, once the issue it closes, if any, is proven. Its outcome stays on its parent session as a replaces: note. ezexe archives it in the app with a press, or approves a session's archive call on the app's approval card, which an ask rule p4-phi's settings keeper writes shows in every permission mode. A message to it makes it a live session once more.
Call tree, drawnAll at once. A new n replaces the whole tree with a new one.
Ensemble, builtAll at once. A new training run writes tree.json again, and only the addresses that file lists are loaded. Training deletes no file, so the .pt files of a larger earlier run stay on disk unread.

What is stored, and where

Session treespawnedFrom in each session.json, under <project>/.claude/p4/phi/sessions/<sessionId>/, or under the shared store that phi.home in p4.json names. The app keeps its own record of the nesting, which p4-phi reads it from.
Call tree, drawnNothing. The tree lives in the page's memory and is built again each time.
Ensemble, builttree/<address>.pt for each member, tree.json and tree-oof.json, in the store's models folder, phi/models/ in the current layout. No file holds a link.

What the tree is for

Session treeDeciding who is given a session's start background, notes and reports.
Call tree, drawnShowing that fib(n) holds a whole fib(n-1) and a whole fib(n-2).
Ensemble, builtAnswering by effort. At medium one member answers, the one whose rows carry the most weight on the task's features. At high every member answers, and their scores are z-scored and averaged.

The same idea, and where it stops

Where they are the same idea

  1. Each part exists because the one above it made it. A call makes two calls, a store is grown under a store, and a session starts a session.
  2. Results travel up the link. A call returns its sum to its caller, and a session's reports and its replaces: note go to its parent session. The ensemble only half does: a parent member starts from the mean of its children's weights as they stood before their fine-tuning, so with pretraining off, as it is by default, nothing a child member learned travels up.
  3. A subtree is one whole thing. fib(6) holds a complete fib(5). A reparent moves a session with every session below it, and phi.py tree prints nothing under a session archived in the app.
  4. The work is at the leaves. The call tree's value is its count of base cases. In p4-phi an orchestrator hands each work step to a worker that declares the files it writes, and keeps itself for orchestration, while phi.top_orchestrates is on, as it is by default.

Where they differ

  1. A computed parent against a recorded one. In ezexe/phi a parent follows from a call's number or a member's address. In p4-phi the parent is written in spawnedFrom, so it can be rewritten, and the app's record can disagree with it.
  2. One number against many moves. n or K fixes the whole shape of each tree of ezexe/phi. The session tree has no shape until sessions are started, detached to top level, reparented and archived.
  3. Sides against no sides. Left and right mean different things in the call tree. Sessions under one parent have no order beyond when they were created.
  4. Repeats against one of each. The same subtree appears many times in the call tree. Each session appears once.
  5. One root against several. Each tree of ezexe/phi has one root, fib(n) or the address 1. A p4-phi store holds many orchestrators, siblings at the top, which message each other with SendMessage.
  6. Replaced whole against archived one by one. A tree of ezexe/phi is replaced as a whole. A session leaves alone, and its outcome stays behind as a replaces: note.

What the two sources do not say

  • Neither tree of ezexe/phi names the other. The Zeckendorf register page calls its drawing the call tree of the naive recursive fib(n), and the docstring of tree.py opens with The node tree. This page cannot tell you that one was drawn to explain the other.
  • The two trees of ezexe/phi do not have the same shape. The call tree is binary. In the ensemble the root 1 gains a child at every address length from 3 on, since no address of length 2 exists, as the drawing above shows from K = 4 on.
  • Nothing in either repository says that p4-phi's session tree was modelled on a tree of ezexe/phi. The shared word tree is all the sources show.
  • No tree.json was in the store this page was written against, so the address drawing follows addresses(k) and parent(a), not a trained ensemble on disk.
