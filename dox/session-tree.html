The session tree

A session in the Claude desktop app is either an orchestrator, a session with no parent session, or a session that another session started. p4-phi hands tasks, notes and reports along those links. Make each move on the tree below, watch the links redraw, and copy the call or command that makes the move for real.

  • The app keeps one record.It is the nesting in the sidebar. It decides which session is told when a turn ends, and which sessions are archived together.
  • p4-phi keeps another.It is spawnedFrom in each session's session.json. It decides who gets a session's start background, notes and reports.
  • They can disagree.Some moves change only one record. Switch the view above the tree to see each side, and follow the dashed line to the other side's parent.

    Three rules p4-phi holds
    
    
    The moves above follow these rules, and each card says what p4-phi does.
    
    
    
      
    A worktree for each session that writes
    
      
      
        
    • A brief names the files its session covers on a line Files: <paths>, or Files: none for a session that writes none. p4-phi keeps the line as fileSet in the worker's session.json, shows it under Files on the worker's page, and names the worker in the address book as the session a message about one of those files goes to.
      • 
        
    • The line holds no start and no edit. p4-phi refuses no start for the files its brief names, holds none while a live session covers one of them and queues none behind a busy writer, and no command narrows or releases the line: each session that writes has a worktree of its own, so no two share a file on disk.
      • 
        
    • A worker that writes works in a git worktree and on a branch of its own: each start p4-phi drafts for one passes use_worktree: true, a start for a session that only reads passes false, and so does a new orchestrator's, since it lands its tree's work in the checkout that holds the default branch. p4-phi asks about no branch or worktree that a session in a worktree of its own makes, moves to or enters. It asks a session that shares its starter's checkout before it moves that checkout to another branch, and every started session before it lands work with a push, merge, rebase or pull, since only the tree's orchestrator lands and pushes.
      • 
        
    • Green work that closes an issue is landed at once, by the tree's orchestrator alone. A worker commits its Closes #N commit on its own branch, in its own worktree. Once its regression test passes, the orchestrator is handed a line that names that branch and tells it to merge the branch into the default branch first, then to push and to sync each store the change touches, without asking ezexe. The line is ezexe's standing word, so it stands in place of the app's default, by which a session merges a branch of a session it started only when ezexe says so.
      • 
      
    
    
    
    
    
      
    ezexe archives
    
      
      
        
    • Every archive call is ezexe's to approve. p4-phi's settings keeper writes an ask rule on mcp__ccd_session_mgmt__archive_session into the project's local settings, so the app shows its approval card before the call in every permission mode, bypass included, and the tool itself refuses a session with live background work.
    • A project that turns phi.upkeep on, with phi.py upkeep on, has the session that started others keep them by itself. The keeper writes no ask rule there and takes its own entry out. Beside each message p4-phi hands that session the acts that are due, and none waits on ezexe: the archive call of each started session that is finished and landed, named by its whole title, each open item a finished worker's report listed as found and not fixed, each step whose wait on another session is over, and the removal of a clean worktree and its merged branch by git worktree remove with no force and git branch -d. When every started session is idle and an act is due, the hooks module starts the turn for it, inside phi.keep_going_max. A force, a deletion of unmerged work, a credential and a permission setting stay ezexe's.
      • 
        
    • A worker that is done shows no button and asks for nothing. It reports, and when its brief said “report when done” it is counted as archived once the issue it closes, if any, is proven, its outcome kept on its parent session as one replaces: note.
      • 
        
    • An orchestrator that is done ends its turn with mcp__ccd_turn__wrap_up whose first action is the app's archive. ezexe archives it with one press.
      • 
        
    • phi/ready-to-archive.md lists the sessions counted as archived that the app has not archived yet.
      • 
        
    • A session counted as archived that is messaged again is named to its parent session as reopened.
      • 
        
    • A worker that archives itself has its last turn kept first, and p4-phi's hook refuses that archive while the issue it closes is open or unproven.
      • 
      
    
    
    
    
    
      
    A puppeteer and the sessions it controls
    
      
      
        
    • A puppeteer is the session ezexe files in the sidebar section “puppeteers”. It controls the orchestrators of other trees, which stay at the top of their own trees in their own sections. The puppeteer page models it.
      • 
        
    • A session whose turn another session began shows the worker as a suggested task card, the start call with initiation own_initiative, which ezexe starts in that session. p4-phi keeps no request for it, and mcp__ccd_session__dismiss_task withdraws a card that went stale.
      • 
        
    • An orchestrator that has a puppeteer starts no new orchestrator itself. It writes phi.py request ... --to-puppeteer, and its puppeteer starts the session, files it in that environment's section and takes it under control, or declines it.
      • 
        
    • A puppeteer is told which sessions it controls p4-phi's records hold complete, which no tool of the app tells. Its archive of one goes through the app's approval card like any other. With phi.upkeep on, that line holds the archive call of each, which waits on nobody.
