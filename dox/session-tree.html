The session tree

A session in the Claude desktop app is either an orchestrator, a session with no parent session, or a session that another session started. p4-phi hands tasks, notes and reports along those links. Make each move on the tree below, watch the links redraw, and copy the call or command that makes the move for real.

  • The app keeps one record.It is the nesting in the sidebar. It decides which session is told when a turn ends, and which sessions are archived together.
  • p4-phi keeps another.It is spawnedFrom in each session's session.json. It decides who gets a session's start background, notes and reports.
  • They can disagree.Some moves change only one record. Switch the view above the tree to see each side, and follow the dashed line to the other side's parent.

    Three rules p4-phi holds
    
    
    The moves above follow these rules, and each card says what p4-phi does.
    
    
    
      
    One writer per file
    
      
      
        
    • Every brief declares the files its session may write on a line Files: <paths>, or Files: none.
      • 
        
    • p4-phi refuses a start, or a start request, whose brief declares no write set. The brief of a new orchestrator is exempt from the check on a start.
      • 
        
    • p4-phi holds a start whose write set overlaps a live session's until that session reports done. A session above the parent session never holds it.
      • 
        
    • An archived session holds nothing, and neither does a session the app shows as stopped, until its next turn.
      • 
        
    • p4-phi keeps the set as fileSet in the worker's session.json and shows it under Files on the worker's page. phi.py files <path> ... replaces it with the paths given and phi.py files --release empties it, so a start request held on the freed paths is handed out at the next turn ezexe begins in the session that filed it.
      • 
        
    • There is one work tree. p4-phi asks before a start that passes use_worktree: true or names a branch, and before a worker makes a worktree or a branch of its own or moves the checkout to another branch. It also asks before a worker lands work with a push, merge, rebase or pull, unless its brief hands it the landing or it works on an issue of its own.
      • 
        
    • Green work that closes an issue is pushed at once. A worker that took an issue is told to push its Closes #N commit itself once its regression test passes, and the orchestrator is told to push and sync the issue-closing commits of a finished worker that took none.
      • 
        
    • Setting phi.file_sets to false in p4.json turns the check on a start call off. A start request still declares its write set, and one that overlaps a live writer still waits.
      • 
      
    
    
    
    
    
      
    ezexe archives
    
      
      
        
    • No session archives a session on its own. p4-phi's hook refuses the archive call, for the session itself and for another, except for a session ezexe picked, below.
      • 
        
    • A worker that is done shows no button and asks for nothing. It reports, and when its brief said “report when done” it is counted as archived once the issue it closes, if any, is proven, its outcome kept on its parent session as one replaces: note.
      • 
        
    • An orchestrator that is done ends its turn with mcp__ccd_turn__wrap_up whose first action is the app's archive. ezexe archives it with one press.
      • 
        
    • In that closing turn the orchestrator puts the finished sessions of its tree to ezexe as one AskUserQuestion with multiSelect, and archives exactly the ones ezexe picks. Those calls, and a puppeteer's archive of a session ezexe picked, are the only archive calls the hook lets through.
      • 
        
    • phi/ready-to-archive.md lists the sessions counted as archived that the app has not archived yet.
      • 
        
    • A session counted as archived that is messaged again is named to its parent session as reopened.
      • 
        
    • Setting phi.session_archives to true in p4.json lets sessions archive sessions with the app's tool.
      • 
      
    
    
    
    
    
      
    A puppeteer and the sessions it controls
    
      
      
        
    • A puppeteer is the session ezexe files in the sidebar section “puppeteers”. It controls the orchestrators of other trees, which stay at the top of their own trees in their own sections. The puppeteer page models it.
      • 
        
    • A start request is handed only to the session that filed it, at the next turn ezexe begins in that session, so the app nests the worker where p4-phi does.
      • 
        
    • A session whose turn another session began shows the worker as a suggested task card first, the start call with initiation own_initiative. It writes a start request only where the card is refused too.
      • 
        
    • An orchestrator that has a puppeteer starts no new orchestrator itself. It writes phi.py request ... --to-puppeteer, and its puppeteer starts the session, files it in that environment's section and takes it under control, or declines it.
      • 
        
    • A puppeteer may archive a session it controls, or one in such a session's tree, only when ezexe picked it in that turn and p4-phi's records hold it complete.
