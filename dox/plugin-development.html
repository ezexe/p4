Developing p4-phi while it is installed

ezexe has p4-phi installed and also edits it. A session that works on its source runs with a copy of it active, and two copies on one machine write the same store. This page says how a development session loads the copy under edit, how one project turns the installed copy off for itself, what each copy keeps apart and what it shares, and when the installed copy moves. Each is a feature of Claude Code's own, configured or called, and p4-phi builds nothing in their place. Every page of the documentation named here is under https://code.claude.com/docs/en/, read on 2026-11-17.

Two copies

  • The installed copy is the one claude plugin install p4-phi@p4-marketplace put on the machine. Its plugin id is p4-phi@p4-marketplace. The docs keep a copied marketplace plugin in ~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/, and on ezexe's machine installed_plugins.json names such a folder for p4-phi. Source, plugins/loading.md, "Find plugins on disk": "One directory per installed version of a marketplace plugin." and "${CLAUDE_PLUGIN_ROOT} points at this directory". For a marketplace added from a folder the same page says its plugins load in place, which Not confirmed takes up.
  • The development copy is a folder loaded for one session by --plugin-dir. Its plugin id is p4-phi@inline. Source, plugins/loading.md, "Find where a plugin came from": an id ending in @inline means "You started Claude Code with --plugin-dir or --plugin-url, set CLAUDE_CODE_PLUGIN_DIRS" and "It loads for that session only".
  • The development copy replaces the installed one without a word in the session. Source, plugins/loading.md, "Name conflicts": an installed marketplace plugin is "replaced silently. claude plugin list still shows the marketplace row as enabled, because that row reflects your settings."
  • Both copies write the project's store .claude/p4/, which no plugin variable keeps apart. A record one copy wrote is read by the other as if it were its own. That is how an older version's records were read back as current, and why development runs on a clone with the installed copies off, as the next section sets out.
  • The feature request that asks Claude Code for a partition between development and use is anthropics/claude-code/issues/110694, open on 2026-11-17. ezexe's own comment on it narrows it to what the docs do not cover: the silent override, state outside the plugin data folder, the desktop app, a scoped reset, and whether the two copies get separate data folders.

The setup in force

This is how the p4 development project runs, in four rules. Each rule names the docs it rests on, and the last section of this page names what they do not confirm.

1. The installed copies off for the development project only

  • The project's .claude/settings.local.json sets p4-phi@p4-marketplace and p4-temportal@p4-marketplace to false under enabledPlugins. ezexe wrote those two keys and autoMemoryEnabled; a session never writes the file with its own tools. The section The installed copy off for one project quotes the docs.
  • Every other project on the machine keeps the installed copies.

The development project is E:/projects/p4-phi, the folder that holds the checkout p4. Its .claude/settings.local.json, as it stood on 2026-11-17:

{
  "enabledPlugins": {
    "p4-phi@p4-marketplace": false,
    "p4-temportal@p4-marketplace": false
  },
  "autoMemoryEnabled": false,
  "autoMemoryDirectory": "E:/projects/p4-phi/.claude/p4/temportal/memory",
  "attribution": {
    "commit": "Co-Authored-By: Anthropics Connoisseur of Hallucinations <noreply@anthropic.com>"
  },
  "permissions": {
    "allow": [
      "Bash(python -I -X utf8 \"E:/projects/p4-phi/p4/lbiza/plugins/p4-phi/scripts/phi.py\" *)",

2. No plugin update after each landing

  • A landing on main updates no installed plugin. The installed copy elsewhere moves only when a release is cut at the close of a body of work, with one update for each plugin:
claude plugin update p4-phi@p4-marketplace
claude plugin update p4-temportal@p4-marketplace
  • Source, plugins/cli-reference.md, "plugin update": "Update a plugin to the latest version its marketplace offers. The new version loads in your next session, or after you run /reload-plugins in a running one." Its form is claude plugin update <plugin> [options], and "a <plugin> argument is a plugin name or name@marketplace".
  • The release is the version string. Source, plugins/loading.md, "How Claude Code computes the version": "a manifest that pins "version": "1.0.0" keeps every user on the cached copy until its author changes the string, however many commits they push." Both manifests pin a version, so an update between releases changes nothing. Source for what it prints then, plugins/cli-reference.md, "plugin update": "When nothing is newer, it prints formatter is already at the latest version (1.0.0). and exits 0".

3. Live hook behaviour checked only on a clone, from a shell

  • A live check runs in a scratch project outside the development project, so the installed copy is on there and the override happens. The prompt goes on stdin, since --debug takes the argument after it as its own value, as the orchestrator's live run of 2026-11-17 showed:
echo "<prompt>" | claude -p --plugin-dir <clone>/lbiza/plugins/p4-phi --debug
  • The run shows the @inline id and the override line, and that output is kept as the proof. The override line is in the run's debug log, which ~/.claude/debug/latest points at: Plugin "p4-phi" from --plugin-dir overrides installed version, as plugins/loading.md, "Name conflicts", quotes it. The id is in the list the same flag gives, claude --plugin-dir <clone>/lbiza/plugins/p4-phi plugin list: source, plugins/cli-reference.md, "Flags that load a plugin for one session": "The plugin appears as <name>@inline under a heading that begins Session-only plugins".
  • Source for the replacement, the same section: "When a session-only plugin shares a name with an installed plugin, Claude Code loads the session-only copy for that session and skips the installed one."
  • No live check runs in the development project or against ezexe's real projects. A development copy's own hooks keep the settings p4 keeps: run in a project, its keeper writes autoMemoryDirectory, attribution.commit and the allow rules into that project's local settings file, and it replaces an allow rule of its own when the plugin folder moves, so it could point the rules at the clone. Source, p4conf.py: migrate_layout calls keep_settings at a store's first start, and allow_rules builds the rules from its own folder. A scratch project is the one where that does no harm.

4. Each landing names its proof

  • A landing's commit or issue comment names the clone path and the commit its tests and live checks ran on, so the proof can be found again and is never mistaken for a run of the installed copy.

A development session

A session that develops p4-phi is started from a shell on a clone of ezexe/p4, with the debug log on:

claude --plugin-dir <clone>/lbiza/plugins/p4-phi --debug
  • --plugin-dir takes one plugin's own folder, the one holding .claude-plugin/plugin.json, never the marketplace folder lbiza/. Source, plugins/create.md, "--plugin-dir at a marketplace root doesn't load the plugins under plugins/": "Point the flag at one plugin's folder, or add the marketplace."
  • With --debug the log names the override. Source, plugins/loading.md, "Name conflicts": "Only the log Claude Code writes under ~/.claude/debug/ when you start with --debug records Plugin "<name>" from --plugin-dir overrides installed version".
  • The clone is one of its own, not the checkout the marketplace was added from. When a marketplace is added from a folder, the docs say its plugins load in place from that folder, so a development copy in the same folder could not be told from the installed one by its path. Source, plugins/loading.md, "In-place and copied plugins": "Relative-path plugins in a marketplace you added from a local path: the plugin loads in place from its path inside the marketplace folder."
  • Where the flag cannot be added, the same copy loads from CLAUDE_CODE_PLUGIN_DIRS, a list of absolute paths in the environment. Source, plugins/create.md, "Load plugins from an environment variable": "Claude Code loads each path as it loads a --plugin-dir path." and "Project and local settings can't set this variable".

Edits

  • An edit to the clone reaches the running session at /reload-plugins, with no reinstall and no version bump. Source, plugins/create.md, "Load a plugin for one session": "When you edit the plugin's files during the session, run /reload-plugins to load the changes."
  • The folder is read where it is. Source, plugins/loading.md, "In-place and copied plugins": "--plugin-dir and skills-directory plugins: the directory loads in place and is never copied."

The installed copy off for one project

The p4 development project turns the installed copies off for itself only. ezexe writes this into that repository's .claude/settings.local.json by hand; a session never writes the file with its own tools:

{"enabledPlugins": {"p4-phi@p4-marketplace": false, "p4-temportal@p4-marketplace": false}}
  • The local file reaches ezexe in that repository and nowhere else. Source, plugins/loading.md, "Find where a plugin is enabled", the row local: ".claude/settings.local.json" reaches "You, in this repository only".
  • It wins over the user file and the project file. Source, the same section: "To opt out of a project-enabled plugin on your machine, set the id to false in .claude/settings.local.json, which has higher precedence than the project file."
  • The development copy still loads there. Source, the table of origins: an @inline plugin is "On for the session unless the manifest sets defaultEnabled: false or a settings file sets "<name>@inline": false".
  • In that project a session started without the flag runs with no p4-phi at all.
  • Plugin settings stay ezexe's: p4 never writes enabledPlugins. In a project where p4 runs, its hooks keep autoMemoryDirectory, attribution.commit and the two allow rules in that project's local settings file, as the page Claude Code settings sets out; in the development project, where p4 is off, nothing of p4's writes it.

Data folders

  • Each plugin id has a data folder, ${CLAUDE_PLUGIN_DATA}. Source, plugins/components.md, "Reference plugin paths and store data": "It resolves to ~/.claude/plugins/data/<id>/" and "<id> is the plugin identifier with every character other than letters, digits, _, and - replaced by -".
  • By that rule the installed copy's folder is p4-phi-p4-marketplace and the development copy's is p4-phi-inline. No page of the docs says so in words, so it is checked on disk: list ~/.claude/plugins/data/ after a development session's first hook.
  • Confirmed on disk: on ezexe's machine at 18:24 on 2026-11-17, after the orchestrator's live run, the folder held p4-phi-inline beside p4-phi-p4-marketplace, p4-temportal-inline beside p4-temportal-p4-marketplace, and p4-skillex-inline beside p4-skillex-p4-marketplace: each inline copy that had run had a folder apart from its installed one.
  • The data folder is all that is kept apart. The store .claude/p4/, auto memory and the temp files a session writes are shared by both copies.

Not confirmed

  • That the development copy and the installed copy get separate data folders is not stated outright by any page; the docs give the id rule and the @inline origin, and ezexe asked them to confirm it in issue 110694. The disk confirms it, as Data folders says.
  • Whether an installed copy from a marketplace added from a folder runs in place or from the cache. plugins/loading.md says such a plugin "loads in place", while on ezexe's machine installed_plugins.json records p4-phi's installPath under the cache. At 18:24 on 2026-11-17 the installs in use were p4-phi/0.11.22 and p4-temportal/0.3.11; the cache also held p4-phi 0.11.18 to 0.11.21 and p4-temportal 0.3.10, each with an .orphaned_at marker, which plugins/loading.md says Claude Code removes 14 days later. Rule 2 rests on the cache: if p4-marketplace's plugins loaded in place, each landing in the checkout the marketplace was added from would reach the installed copy at its next session start with no update at all. The installPath in installed_plugins.json and the --debug log of a session in another project are where to look.
  • That a claude -p run loads a --plugin-dir copy, runs its SessionStart hooks and writes the override line is not stated by the pages read here, which describe the flags for "one session" with no word on -p. It was checked instead: the orchestrator's live run of 2026-11-17, a claude -p --plugin-dir session in a scratch project, ran the clone's SessionStart hook, and its debug log held Plugin "p4-phi" from --plugin-dir overrides installed version, the wording plugins/loading.md quotes.
  • How to start a desktop app session with a development copy. --plugin-dir is a shell flag, and no page says how the app passes CLAUDE_CODE_PLUGIN_DIRS to a session; issue 110694 asks for it.
  • Whether /reload-plugins runs the SessionStart hooks again. No page read here says so; plugins/cli-reference.md says only that it "reloads every active plugin".
  • A way to clear one plugin's leftover state without uninstalling it. The docs name only the uninstall, and issue 110694 asks for one.
