Developing p4-phi while it is installed

ezexe has p4-phi installed and also edits it. A session that works on its source runs with a copy of it active, and two copies on one machine write the same store. This page says how a development session loads the copy under edit, how one project turns the installed copy off for itself, what each copy keeps apart and what it shares, how what the plugin makes a model do is checked, and when the installed copy moves. Each is a feature of Claude Code's own, configured or called, and p4-phi builds nothing in their place. Every page of the documentation named here is under https://code.claude.com/docs/en/, read on 2026-11-17.

Two copies

  • The installed copy is the one claude plugin install p4-phi@p4-marketplace put on the machine. Its plugin id is p4-phi@p4-marketplace. The docs keep a copied marketplace plugin in ~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/, and on ezexe's machine installed_plugins.json names such a folder for p4-phi. Source, plugins/loading.md, "Find plugins on disk": "One directory per installed version of a marketplace plugin." and "${CLAUDE_PLUGIN_ROOT} points at this directory". For a marketplace added from a folder the same page says its plugins load in place, which Not confirmed takes up.
  • The development copy is a folder loaded for one session by --plugin-dir. Its plugin id is p4-phi@inline. Source, plugins/loading.md, "Find where a plugin came from": an id ending in @inline means "You started Claude Code with --plugin-dir or --plugin-url, set CLAUDE_CODE_PLUGIN_DIRS" and "It loads for that session only".
  • The development copy replaces the installed one without a word in the session. Source, plugins/loading.md, "Name conflicts": an installed marketplace plugin is "replaced silently. claude plugin list still shows the marketplace row as enabled, because that row reflects your settings."
  • Both copies write the project's store .claude/p4/, which no plugin variable keeps apart. A record one copy wrote is read by the other as if it were its own. That is how an older version's records were read back as current, and why development runs on a clone from a scratch project, while the development project keeps the installed copies off and starts no development copy, as the next section sets out.
  • The feature request that asks Claude Code for a partition between development and use is anthropics/claude-code/issues/110694, open on 2026-11-17. ezexe's own comment on it narrows it to what the docs do not cover: the silent override, state outside the plugin data folder, the desktop app, a scoped reset, and whether the two copies get separate data folders.

The setup in force

This is how the p4 development project runs, in four rules. Each rule names the docs it rests on, and the last section of this page names what they do not confirm.

1. The installed copies off for the development project only

  • The project's .claude/settings.local.json sets p4-phi@p4-marketplace and p4-temportal@p4-marketplace to false under enabledPlugins. ezexe wrote those two keys and autoMemoryEnabled; a session never writes the file with its own tools. The section The installed copy off for one project quotes the docs.
  • Every other project on the machine keeps the installed copies.

2. No plugin update after each landing

  • A landing on main updates no installed plugin. The installed copy elsewhere moves only when a release is cut at the close of a body of work, with one update for each plugin:
claude plugin update p4-phi@p4-marketplace
claude plugin update p4-temportal@p4-marketplace
  • Source, plugins/cli-reference.md, "plugin update": "Update a plugin to the latest version its marketplace offers. The new version loads in your next session, or after you run /reload-plugins in a running one." Its form is claude plugin update <plugin> [options], and "a <plugin> argument is a plugin name or name@marketplace".
  • The release is the version string. Source, plugins/loading.md, "How Claude Code computes the version": "a manifest that pins "version": "1.0.0" keeps every user on the cached copy until its author changes the string, however many commits they push." Both manifests pin a version, so an update between releases changes nothing. Source for what it prints then, plugins/cli-reference.md, "plugin update": "When nothing is newer, it prints formatter is already at the latest version (1.0.0). and exits 0".

3. What the plugin makes a model do is checked by its evals suite, and a development copy runs only from a scratch project

  • What p4-phi makes a model do, such as a question it does not ask, a skill it calls or a subagent it starts, is checked by the suite in lbiza/plugins/p4-phi/evals/, which The evals suite sets out. No prompt is piped by hand to a session that loads a clone for it: an eval run is that check, and Claude Code makes it. Source, plugin-evals.md, "How runs are isolated": each run gets a temporary home directory, working directory and Claude Code configuration, and the agent under test runs there as a claude -p child process with only the plugin loaded.
  • An eval run needs no clone and no scratch project, since it makes its own. Its hooks run in the run's temporary working folder, so the store and the local settings file they write are that folder's and no installed copy is there to be replaced. Seen on 2026-11-19 with Claude Code 2.1.322: the kept folder of a run held .claude/p4 and .claude/settings.local.json under its own home/cwd, and the run's plugin list named p4-phi@inline beside Claude Code's built-in plugins alone.
  • A development copy is any session that loads a clone of p4, by the --plugin-dir flag or by the CLAUDE_CODE_PLUGIN_DIRS variable set in a shell or in user settings. It runs only from a scratch project: never in the development project, and never in a project where p4 is used. Its hooks run wherever it is started, and its settings keeper can rewrite autoMemoryDirectory and attribution.commit in that project's local settings file and point the allow rules at the clone. Source, p4conf.py: migrate_layout calls keep_settings at a store's first start; watch, which hook.py runs at every SessionStart, calls it once Claude Code's binary or the p4 plugins' versions change, and at every ConfigChange of a settings file; and allow_rules builds the rules from the running copy's own folder.

4. Each landing names its proof

  • A landing's commit or issue comment names the clone path and the commit its tests and live checks ran on, so the proof can be found again and is never mistaken for a run of the installed copy.

A development session

A session that runs the copy under edit is started from a shell in a scratch project, never in the development project or a project where p4 is used, on a clone of ezexe/p4, with the debug log on. Rule 3 of The setup in force says why. Sessions in the development project start without the flag, so no p4 hook runs there.

claude --plugin-dir <clone>/lbiza/plugins/p4-phi --debug
  • --plugin-dir takes one plugin's own folder, the one holding .claude-plugin/plugin.json, never the marketplace folder lbiza/. Source, plugins/create.md, "--plugin-dir at a marketplace root doesn't load the plugins under plugins/": "Point the flag at one plugin's folder, or add the marketplace."
  • With --debug the log names the override. Source, plugins/loading.md, "Name conflicts": "Only the log Claude Code writes under ~/.claude/debug/ when you start with --debug records Plugin "<name>" from --plugin-dir overrides installed version".
  • The clone is one of its own, not the checkout the marketplace was added from. When a marketplace is added from a folder, the docs say its plugins load in place from that folder, so a development copy in the same folder could not be told from the installed one by its path. Source, plugins/loading.md, "In-place and copied plugins": "Relative-path plugins in a marketplace you added from a local path: the plugin loads in place from its path inside the marketplace folder."
  • Where the flag cannot be added, the same copy loads from CLAUDE_CODE_PLUGIN_DIRS, a list of absolute paths in the environment. Source, plugins/create.md, "Load plugins from an environment variable": "Claude Code loads each path as it loads a --plugin-dir path." and "Project and local settings can't set this variable".

Edits

  • An edit to the clone reaches the running session at /reload-plugins, with no reinstall and no version bump. Source, plugins/create.md, "Load a plugin for one session": "When you edit the plugin's files during the session, run /reload-plugins to load the changes."
  • The folder is read where it is. Source, plugins/loading.md, "In-place and copied plugins": "--plugin-dir and skills-directory plugins: the directory loads in place and is never copied."

The evals suite

p4-phi carries a suite for claude plugin eval, Claude Code's own check of what a plugin makes a model do, in lbiza/plugins/p4-phi/evals/. A case is a prompt and its graders, and a run scores it with the plugin loaded and again with no plugin. The page is plugin-evals.md, read on 2026-11-19 with Claude Code 2.1.322 on native Windows.

When to run it

  • By hand, before a release is cut, and after a change to the words a case rests on: the two built-in rules of scripts/phi.py, the description of skills/phi/SKILL.md, agents/check.md, or the SessionStart entries of hooks/hooks.json.
  • Again when the pinned model moves to a newer one, so a change of model is read apart from a change of the plugin.
  • It gates no landing. A landing rests on python -X utf8 suite/run.py and claude plugin validate, which call no model. Source, plugin-evals.md, the note under the opening: every eval run is a real model call on the account, counted against the plan's usage or the API bill. Source, the same page, "How a case is scored": one run of an agent that is not deterministic tells little, which is why a case runs three times.

The command

From the plugin's folder, lbiza/plugins/p4-phi:

claude plugin eval . --scaffold --trust-plugin --model claude-sonnet-5-5 --judge-model claude-haiku-5-5 --no-publish --max-cost-usd 5
  • --scaffold runs a case's seed.sh, which copies the case's project folder into the run's empty workspace. Four cases have one. Source, plugin-evals.md, "Seed the workspace or conversation": the script runs only when the flag is passed, as the person who runs the suite and outside the agent's sandbox.
  • --trust-plugin answers the first-run trust prompt, which a run a session starts cannot stop for. From a terminal the flag is left out and the prompt answered once.
  • Both models are pinned. Source, the same page, "Command options", the row --model: pin it so a model rollout is not mistaken for a plugin regression. claude-sonnet-5-5 is the model phi.child_levels gives a worker's static step. No case has a judge grader yet, so the judge model is pinned for the day one does.
  • --no-publish keeps the report in evals/results/, which git ignores.
  • --max-cost-usd 5 is a ceiling on the run's list-price estimate and not on plan usage, by the same table. The first run's estimate was $2.13 for its 48 runs.
  • No --allow-tools: no case needs the shell, a write or a fetch, and every tool a case lists is of the read-only set. Source, the same page, "Shell grants need a sandbox": native Windows has no sandbox backend, so a run that grants the shell there is refused.
  • While a case is being written, one case runs once in one arm: claude plugin eval . --scaffold --trust-plugin --case <name> --runs 1 --ablation none --model claude-sonnet-5-5 --no-publish.
  • Every case is graded without a judge and is tagged smoke. A case that takes a judge grader later is left untagged, so --tag smoke stays the run that calls no judge.

What a run's trace showed

The page does not say what a trace holds of a hook, so one case was run with --keep-temp and its out/trace.jsonl read, on 2026-11-19 with Claude Code 2.1.322.

  • A SessionStart hook's added context is in the trace. A system line of subtype hook_response holds the hook's whole output, its additionalContext among it. A regex grader with target: trace reads it, which is how hands-the-rules-at-start is graded.
  • A UserPromptSubmit hook's added context is in no line of the trace, though it reached the session: p4-phi's own log of the run recorded the hook's 446 characters, and the session's transcript under the kept config/projects/ held them. No grader reads that transcript, so what a hook adds beside a prompt is graded by its effect on the reply or on the tool calls.
  • A tool call a PreToolUse hook refused counts for tool_used. No hook of p4-phi refuses a call of a read-only tool, so this was checked with a throwaway plugin whose hook denied every Glob call: the grader counted one call, and the trace held the call with an error result that opens PreToolUse:Glob hook error: and goes on with the hook's reason. So tool_used counts the calls a session made, not the calls that ran, and a refusal is asserted by a regex over the trace on the hook's reason.
  • A run's session was offered no AskUserQuestion tool, though a case may list it by the page's "Grant tools" and two cases do. The tools sent to the model were Agent, Glob, Grep, Read, Skill and ToolSearch, in the p4-phi run and in the throwaway plugin's. So both cases on the act-don't-wait rule grade the reply, and the tool_used grader on AskUserQuestion with both bounds at 0 has nothing to count until a build offers the tool.
  • context.add_dirs gave the session leave to read the fixture folder and no word of where it is: the session's list of working directories was empty and it searched its own workspace in vain. So the cases seed the workspace with context.scaffold_script, which ran under Git Bash on native Windows.

The installed copy off for one project

The p4 development project turns the installed copies off for itself only. ezexe writes this into that repository's .claude/settings.local.json by hand; a session never writes the file with its own tools:

{"enabledPlugins": {"p4-phi@p4-marketplace": false, "p4-temportal@p4-marketplace": false}}
  • The local file reaches ezexe in that repository and nowhere else. Source, plugins/loading.md, "Find where a plugin is enabled", the row local: ".claude/settings.local.json" reaches "You, in this repository only".
  • It wins over the user file and the project file. Source, the same section: "To opt out of a project-enabled plugin on your machine, set the id to false in .claude/settings.local.json, which has higher precedence than the project file."
  • This turns off only the installed copies. A --plugin-dir copy would still load there and run its hooks, which is why no session in the development project is started with the flag. Source, the table of origins: an @inline plugin is "On for the session unless the manifest sets defaultEnabled: false or a settings file sets "<name>@inline": false".
  • In that project a session started without the flag runs with no p4-phi at all.
  • Plugin settings stay ezexe's: p4 never writes enabledPlugins. In a project where p4 runs, installed or from --plugin-dir, its hooks keep autoMemoryDirectory, attribution.commit and the two allow rules in that project's local settings file, as the page Claude Code settings sets out. In the development project sessions start without the flag and the installed copies are off, so no hook of p4's runs there to write it.

Data folders

  • Each plugin id has a data folder, ${CLAUDE_PLUGIN_DATA}. Source, plugins/components.md, "Reference plugin paths and store data": "It resolves to ~/.claude/plugins/data/<id>/" and "<id> is the plugin identifier with every character other than letters, digits, _, and - replaced by -".
  • By that rule the installed copy's folder is p4-phi-p4-marketplace and the development copy's is p4-phi-inline. No page of the docs says so in words, so it is checked on disk: list ~/.claude/plugins/data/ after a development session's first hook.
  • Confirmed on disk: on ezexe's machine at 18:24 on 2026-11-17, after the orchestrator's live run, the folder held p4-phi-inline beside p4-phi-p4-marketplace, p4-temportal-inline beside p4-temportal-p4-marketplace, and p4-skillex-inline beside p4-skillex-p4-marketplace: each inline copy that had run had a folder apart from its installed one.
  • The data folder is all that is kept apart. The store .claude/p4/, auto memory and the temp files a session writes are shared by both copies.

Not confirmed

  • That the development copy and the installed copy get separate data folders is not stated outright by any page; the docs give the id rule and the @inline origin, and ezexe asked them to confirm it in issue 110694. The disk confirms it, as Data folders says.
  • Whether an installed copy from a marketplace added from a folder runs in place or from the cache. plugins/loading.md says such a plugin "loads in place", while on ezexe's machine installed_plugins.json records p4-phi's installPath under the cache. At 18:24 on 2026-11-17 the installs in use were p4-phi/0.11.22 and p4-temportal/0.3.11; the cache also held p4-phi 0.11.18 to 0.11.21 and p4-temportal 0.3.10, each with an .orphaned_at marker, which plugins/loading.md says Claude Code removes 14 days later. Rule 2 rests on the cache: if p4-marketplace's plugins loaded in place, each landing in the checkout the marketplace was added from would reach the installed copy at its next session start with no update at all. The installPath in installed_plugins.json and the --debug log of a session in another project are where to look.
  • That a claude -p run loads a --plugin-dir copy, runs its SessionStart hooks and writes the override line is not stated by the pages read here, which describe the flags for "one session" with no word on -p. It was checked instead: the orchestrator's live run of 2026-11-17, a claude -p --plugin-dir session in a scratch project, ran the clone's SessionStart hook, and its debug log held Plugin "p4-phi" from --plugin-dir overrides installed version, the wording plugins/loading.md quotes.
  • What the trace of an eval run holds of a hook's output, and whether a call a hook refused counts for tool_used, are not stated by plugin-evals.md. That page lists AskUserQuestion among the tools a case may allow, and a run on Claude Code 2.1.322 offered its session none. The evals suite records what a kept trace showed for each.
  • How to start a desktop app session with a development copy. --plugin-dir is a shell flag, and no page says how the app passes CLAUDE_CODE_PLUGIN_DIRS to a session; issue 110694 asks for it.
  • Whether /reload-plugins runs the SessionStart hooks again. No page read here says so; plugins/cli-reference.md says only that it "reloads every active plugin".
  • A way to clear one plugin's leftover state without uninstalling it. The docs name only the uninstall, and issue 110694 asks for one.
