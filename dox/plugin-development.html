Developing p4-phi while it is installed

ezexe has p4-phi installed and also edits it. A session that works on its source runs with a copy of it active, and two copies on one machine write the same store. This page says how the marketplace is registered, how a development session loads the copy under edit, how one project turns the installed copy off for itself, what each copy keeps apart and what it shares, how what the plugin makes a model do is checked, and when the installed copy moves. Each is a feature of Claude Code's own, configured or called, and p4-phi builds nothing in their place. Every page of the documentation named here is under https://code.claude.com/docs/en/, read on 2026-11-17 where a section names no other day.

Two copies

  • The installed copy is the one claude plugin install p4-phi@p4-marketplace put on the machine. Its plugin id is p4-phi@p4-marketplace. It is a copy in Claude Code's plugin cache, ~/.claude/plugins/cache/p4-marketplace/p4-phi/<version>/, since the marketplace is registered from GitHub, as The marketplace sets out. Source, plugins/loading.md, "In-place and copied plugins": "Every other marketplace plugin: Claude Code copies the plugin into cache/<marketplace>/<plugin>/<version>/ at install and loads that copy." Source for the folder, the same page, "Find plugins on disk": "One directory per installed version of a marketplace plugin." and "${CLAUDE_PLUGIN_ROOT} points at this directory".
  • Read on ezexe's machine on 2026-11-19: installed_plugins.json gives cache\p4-marketplace\p4-phi\0.11.46 and cache\p4-marketplace\p4-temportal\0.3.22 under ~/.claude/plugins/ as each installPath, each at user scope and each with the commit 787f94d of ezexe/p4 as its gitCommitSha, and claude plugin list prints those two versions as enabled.
  • So no checkout of ezexe/p4 on the machine is the installed copy. A pull or an edit in a checkout changes no session that runs the installed copy, and a commit on main reaches one only as a new version in the cache, by rule 2 of The setup in force.
  • The development copy is a folder loaded for one session by --plugin-dir. Its plugin id is p4-phi@inline. Source, plugins/loading.md, "Find where a plugin came from": an id ending in @inline means "You started Claude Code with --plugin-dir or --plugin-url, set CLAUDE_CODE_PLUGIN_DIRS" and "It loads for that session only".
  • The development copy replaces the installed one without a word in the session. Source, plugins/loading.md, "Name conflicts": an installed marketplace plugin is "replaced silently. claude plugin list still shows the marketplace row as enabled, because that row reflects your settings."
  • Both copies write the project's store .claude/p4/, which no plugin variable keeps apart. A record one copy wrote is read by the other as if it were its own. That is how an older version's records were read back as current, and why development runs on a clone from a scratch project, while the development project keeps the installed copies off and starts no development copy, as the next section sets out.
  • The feature request that asks Claude Code for a partition between development and use is anthropics/claude-code/issues/110694, open on 2026-11-17. ezexe's own comment on it narrows it to what the docs do not cover: the silent override, state outside the plugin data folder, the desktop app, a scoped reset, and whether the two copies get separate data folders.

The marketplace

How p4-marketplace is registered on ezexe's machine, read from ~/.claude/plugins/ and the user settings file on 2026-11-19 with Claude Code 2.1.328. The pages quoted here, plugins/marketplace-reference.md, plugins/install.md, plugins/create-marketplace.md, plugins/host-marketplace.md and plugins/loading.md, were read that day.

  • The marketplace is the repository ezexe/p4 on GitHub, added with one command, and each plugin is installed from it by name:
claude plugin marketplace add ezexe/p4
claude plugin install p4-phi@p4-marketplace
claude plugin install p4-temportal@p4-marketplace
  • The catalog is .claude-plugin/marketplace.json at the repository's root, the one catalog the repository holds. It names each plugin by its folder from there, ./lbiza/plugins/p4-phi and ./lbiza/plugins/p4-temportal, and gives no entry a version. Source, plugins/marketplace-reference.md, "Marketplace file": "The directory that contains .claude-plugin/ is called the marketplace root, and every relative plugin source resolves from it, not from .claude-plugin/."
  • What the machine holds: known_marketplaces.json records p4-marketplace with the source github, the repo ezexe/p4, autoUpdate true and Claude Code's own clone at ~/.claude/plugins/marketplaces/p4-marketplace, which stood at the commit 787f94d. claude plugin marketplace list prints Source: GitHub (ezexe/p4).
  • Auto-update is on. ezexe's user settings file, ~/.claude/settings.json, declares the marketplace under extraKnownMarketplaces with autoUpdate true:
{
  "extraKnownMarketplaces": {
    "p4-marketplace": {
      "source": {
        "source": "github",
        "repo": "ezexe/p4"
      },
      "autoUpdate": true
    }
  }
}
  • That entry decides. Source, plugins/loading.md, "Which marketplaces and plugins auto-update": whether a marketplace auto-updates follows the first that is set of "autoUpdate on its extraKnownMarketplaces entry in a settings file", then "autoUpdate on its known_marketplaces.json entry", then the default, which is off for a marketplace like this one. p4 never writes the key: extraKnownMarketplaces is of the security class on Claude Code settings.
  • What path did. The catalog used to be lbiza/.claude-plugin/marketplace.json, with each source spelled from lbiza/, as ./plugins/p4-phi. Declared with path set to that file on its source, Claude Code 2.1.328 found the catalog, looked for each relative source from the clone's root, and failed with Source path does not exist. The docs read otherwise: plugins/marketplace-reference.md, "Fields by type", gives path as "The marketplace file's path inside the repository", and "Marketplace file" gives the folder that holds .claude-plugin/ as the root of every relative source. So the catalog moved to the repository's root, the default place, where the docs and the run agree, and lbiza/ holds none.
  • A marketplace added from a folder runs its plugins in place. This page listed that as not confirmed, and it is settled. Until 2026-11-19 p4-marketplace was added from the folder lbiza/ of the working checkout, and claude plugin list showed both plugins read from that checkout, as the docs say. Source, plugins/loading.md, "In-place and copied plugins": "Relative-path plugins in a marketplace you added from a local path: the plugin loads in place from its path inside the marketplace folder. Your edits to the source directory take effect at the next session start or /reload-plugins, and you don't need to increase the version."
  • So the installed copy was the working checkout. An edit there reached every project's next session with no version change, and a landing pushed to main from a worktree reached no session until that checkout was pulled. The question stood open here because installed_plugins.json held an installPath under the cache on 2026-11-17, and claude plugin list answered it. That is why the marketplace is registered from GitHub now.
  • The cache still holds the versions before: p4-phi 0.11.18 to 0.11.31 and p4-temportal 0.3.10 to 0.3.15, each with an .orphaned_at marker. Source, plugins/loading.md, "Cleanup of previous versions": "It removes that directory in a background cleanup 14 days later, so a session that already loaded the old version keeps running."
  • A folder marketplace is still there for a machine that wants an install it edits in place, with the checkout's root as the folder: claude plugin marketplace add <checkout>. Source, plugins/create-marketplace.md, "Test an edit to a plugin": "Your edits take effect at the next session start or when you run /reload-plugins in a session, with no change to the plugin's version." It cannot stand beside the GitHub one. Source, plugins/marketplace-reference.md, "Marketplace file": "Each user registers one marketplace per name". The setup in force keeps the GitHub one and loads a clone with --plugin-dir.
  • A machine that still has the marketplace added from the folder lbiza/ has no catalog to read there once its checkout holds this layout. Source, plugins/marketplace-reference.md, "Fields by type": for a folder, path is "The marketplace root, the directory that contains .claude-plugin/marketplace.json". Its source from then on is ezexe/p4 or the checkout's root.
  • Removing a marketplace uninstalls its plugins. Source, plugins/install.md, "Manage marketplaces": "When you remove a marketplace, Claude Code uninstalls every plugin you installed from it and removes their enabledPlugins entries from your settings files." So after claude plugin marketplace remove p4-marketplace each plugin is installed again. Source for a refresh that keeps them, plugins/cli-reference.md, "plugin marketplace remove": "To refresh a marketplace without losing its plugins, run plugin marketplace update instead."

The setup in force

This is how the p4 development project runs, in four rules. Each rule names the docs it rests on, and the last section of this page names what they do not confirm.

1. The installed copies off for the development project only

  • The project's .claude/settings.local.json sets p4-phi@p4-marketplace and p4-temportal@p4-marketplace to false under enabledPlugins. ezexe wrote those two keys and autoMemoryEnabled; a session never writes the file with its own tools. The section The installed copy off for one project quotes the docs.
  • Every other project on the machine keeps the installed copies.

The development project is E:/projects/p4-phi, the folder that holds the checkout p4. Its .claude/settings.local.json, as it stood on 2026-11-17:

2. A landing's version bump reaches the installed copy by auto-update

  • The release is the version string, and it lives in one file. A landing that changes a plugin's files bumps the version in that plugin's .claude-plugin/plugin.json, and no entry of the catalog carries one. Source, plugins/loading.md, "How Claude Code computes the version": "The version field in the plugin's manifest comes first", and "a manifest that pins "version": "1.0.0" keeps every user on the cached copy until its author changes the string, however many commits they push." So a landing that bumps no version moves no installed copy.
  • Auto-update is on for p4-marketplace, as The marketplace shows, so the bump reaches the installed copy at the pass after the landing, with no command. Source, plugins/loading.md, "When auto-update runs": "In an interactive session, after you send your first message, Claude Code waits a random delay of up to ten minutes. It then refreshes every marketplace with auto-update on and updates the plugins installed from them on disk."
  • Seen on ezexe's machine on 2026-11-19 with Claude Code 2.1.328: the landing of 92c34f7, committed at 07:59 UTC, bumped p4-phi to 0.11.48 and p4-temportal to 0.3.23, and installed_plugins.json then gave each plugin that version, an installPath in a new version folder of the cache, the gitCommitSha 92c34f7 and a lastUpdated of 08:04:54 UTC, with installedAt still at 07:37 UTC, the install. The cache held the folders 0.11.48 and 0.3.23 beside 0.11.46 and 0.3.22.
  • A session of the desktop app runs the pass. The app's records give desktop sessions created at 07:55:38 UTC and at 08:04:44 UTC, each within the ten minutes before the move, no terminal session was open, and no session ran an update command.
  • A session that is running keeps what it loaded. Source, the same section: "The running session keeps the versions it loaded, and you see Plugin updated: <name> · Run /reload-plugins to apply. Whether or not you reload, the new versions load on your next launch."
  • The move by hand is one update for each plugin:
claude plugin update p4-phi@p4-marketplace
claude plugin update p4-temportal@p4-marketplace
  • Source, plugins/cli-reference.md, "plugin update": "Update a plugin to the latest version its marketplace offers. The new version loads in your next session, or after you run /reload-plugins in a running one." Its form is claude plugin update <plugin> [options], and "a <plugin> argument is a plugin name or name@marketplace".
  • An update with no bump before it changes nothing. Source for what it prints then, plugins/cli-reference.md, "plugin update": "When nothing is newer, it prints formatter is already at the latest version (1.0.0). and exits 0".
  • Each update moves the installed copy's folder, since the version is in its path. p4's two allow rules name the running copy's scripts folder, and at the first session start after the version changes the settings keeper writes them for the new folder and keeps those of each older version folder still in the cache, so a session that still runs the version before stays covered, as Claude Code settings sets out.

3. What the plugin makes a model do is checked by its evals suite, and a development copy runs only from a scratch project

  • What p4-phi makes a model do, such as a question it does not ask, a skill it calls or a subagent it starts, is checked by the suite in lbiza/plugins/p4-phi/evals/, which The evals suite sets out. No prompt is piped by hand to a session that loads a clone for it: an eval run is that check, and Claude Code makes it. Source, plugin-evals.md, "How runs are isolated": each run gets a temporary home directory, working directory and Claude Code configuration, and the agent under test runs there as a claude -p child process with only the plugin loaded.
  • An eval run needs no clone and no scratch project, since it makes its own. Its hooks run in the run's temporary working folder, so the store and the local settings file they write are that folder's and no installed copy is there to be replaced. Seen on 2026-11-19 with Claude Code 2.1.322: the kept folder of a run held .claude/p4 and .claude/settings.local.json under its own home/cwd, and the run's plugin list named p4-phi@inline beside Claude Code's built-in plugins alone.
  • A development copy is any session that loads a clone of p4, by the --plugin-dir flag or by the CLAUDE_CODE_PLUGIN_DIRS variable set in a shell or in user settings. It runs only from a scratch project: never in the development project, and never in a project where p4 is used. Its hooks run wherever it is started, and its settings keeper can rewrite autoMemoryDirectory and attribution.commit in that project's local settings file and point the allow rules at the clone. Source, p4conf.py: migrate_layout calls keep_settings at a store's first start; watch, which hook.py runs at every SessionStart, calls it once Claude Code's binary or the p4 plugins' versions change, and at every ConfigChange of a settings file; and allow_rules builds the rules from the running copy's own folder.

4. Each landing names its proof

  • A landing's commit or issue comment names the clone path and the commit its tests and live checks ran on, so the proof can be found again and is never mistaken for a run of the installed copy.

A development session

A session that runs the copy under edit is started from a shell in a scratch project, never in the development project or a project where p4 is used, on a clone of ezexe/p4, with the debug log on. Rule 3 of The setup in force says why. Sessions in the development project start without the flag, so no p4 hook runs there.

claude --plugin-dir <clone>/lbiza/plugins/p4-phi --debug
  • --plugin-dir takes one plugin's own folder, the one holding .claude-plugin/plugin.json, never the marketplace folder lbiza/. Source, plugins/create.md, "--plugin-dir at a marketplace root doesn't load the plugins under plugins/": "Point the flag at one plugin's folder, or add the marketplace."
  • With --debug the log names the override. Source, plugins/loading.md, "Name conflicts": "Only the log Claude Code writes under ~/.claude/debug/ when you start with --debug records Plugin "<name>" from --plugin-dir overrides installed version".
  • The clone is a checkout of ezexe/p4 on the machine. It is never the installed copy's folder in the cache, nor Claude Code's own clone under ~/.claude/plugins/marketplaces/p4-marketplace, which a refresh replaces. Source, plugins/host-marketplace.md, "What background auto-update does with credentials": when the check finds new commits, "Claude Code clones the marketplace again and replaces the existing checkout with the new clone."
  • Where the flag cannot be added, the same copy loads from CLAUDE_CODE_PLUGIN_DIRS, a list of absolute paths in the environment. Source, plugins/create.md, "Load plugins from an environment variable": "Claude Code loads each path as it loads a --plugin-dir path." and "Project and local settings can't set this variable".
  • A desktop app session takes no flag. There the copy is a plugin folder under the scratch project's .claude/skills/, where its id is p4-phi@skills-dir, and the installed copies are set to false in that project's .claude/settings.local.json, since an enabled installed plugin of the same name would take its place. Source, plugins/loading.md, "Find where a plugin came from", "In-place and copied plugins" and "Name conflicts": a folder with a .claude-plugin/plugin.json under a project's .claude/skills/ loads in place once the folder is trusted, and an installed marketplace plugin comes before it in the order of names. Seen on 2026-11-19 with the app's Claude Code 2.1.326: a session in such a project ran the copy's hooks and its hooks module, listed its skill, its agent and the workflow in its workflows/ folder, and ~/.claude/plugins/data/ gained p4-phi-skills-dir. Later that day, with p4-phi installed from the marketplace and set to false in the scratch project, the copy under .claude/skills/ did not load, on 2.1.326 in the app and on 2.1.328 in a terminal: the name was taken by the installed plugin, disabled or not. While a plugin of that name is installed, a desktop session gets the copy through its mods folder, as Live checks of the hooks module sets out.
  • The app starts a session in another folder only from a turn ezexe began, and a session that shares a folder or works in a worktree cannot move itself to one. So ezexe starts the scratch session, or tells a session to start it.

Edits

  • An edit to the clone reaches the running session at /reload-plugins, with no reinstall and no version bump. Source, plugins/create.md, "Load a plugin for one session": "When you edit the plugin's files during the session, run /reload-plugins to load the changes."
  • The folder is read where it is. Source, plugins/loading.md, "In-place and copied plugins": "--plugin-dir and skills-directory plugins: the directory loads in place and is never copied."

The evals suite

p4-phi carries a suite for claude plugin eval, Claude Code's own check of what a plugin makes a model do, in lbiza/plugins/p4-phi/evals/. A case is a prompt and its graders, and a run scores it with the plugin loaded and again with no plugin. The page is plugin-evals.md, read on 2026-11-19. The runs recorded here were made that day on native Windows, the first kept one with Claude Code 2.1.322 and every later one with 2.1.328, since Claude Code updated itself between them.

When to run it

  • By hand, at the close of a body of work, and after a change to the words a case rests on: the two built-in rules of scripts/phi.py, the description of skills/phi/SKILL.md, agents/check.md, or the prompt.compose hook of hooks/register.ts.
  • Again when the pinned model moves to a newer one, so a change of model is read apart from a change of the plugin.
  • It gates no landing. A landing rests on python -m pytest and claude plugin validate, which call no model. Source, plugin-evals.md, the note under the opening: every eval run is a real model call on the account, counted against the plan's usage or the API bill. Source, the same page, "How a case is scored": one run of an agent that is not deterministic tells little, which is why a case runs three times.

The command

From the plugin's folder, lbiza/plugins/p4-phi:

claude plugin eval . --scaffold --trust-plugin --model claude-sonnet-5-5 --judge-model claude-haiku-5-5 --no-publish --max-cost-usd 5
  • --scaffold runs a case's seed.sh, which copies the case's project folder into the run's empty workspace. Four cases have one. Source, plugin-evals.md, "Seed the workspace or conversation": the script runs only when the flag is passed, as the person who runs the suite and outside the agent's sandbox.
  • --trust-plugin answers the first-run trust prompt, which a run a session starts cannot stop for. From a terminal the flag is left out and the prompt answered once.
  • Both models are pinned. Source, the same page, "Command options", the row --model: pin it so a model rollout is not mistaken for a plugin regression. claude-sonnet-5-5 is the model phi.child_levels gives a worker's static step. No case has a judge grader yet, so the judge model is pinned for the day one does.
  • --no-publish keeps the report in evals/results/, which git ignores.
  • --max-cost-usd 5 is a ceiling on the run's list-price estimate and not on plan usage, by the same table. The first run's estimate was $2.13 for its 48 runs.
  • No --allow-tools: no case needs the shell, a write or a fetch, and every tool a case lists is of the read-only set. Source, the same page, "Shell grants need a sandbox": native Windows has no sandbox backend, so a run that grants the shell there is refused.
  • While a case is being written, one case runs once in one arm: claude plugin eval . --scaffold --trust-plugin --case <name> --runs 1 --ablation none --model claude-sonnet-5-5 --no-publish.
  • The two cases on the act-don't-wait rule also carry the tag rule, so they run alone with the command above and --tag rule at its end. Source, plugin-evals.md, "Choose what to evaluate": "Add --case <glob> to filter by case name and --tag <tag> to keep cases with any of the given tags." --case takes one glob and no list: a brace list of the two names matched no case on 2.1.328.
  • Every case is graded without a judge and is tagged smoke. A case that takes a judge grader later is left untagged, so --tag smoke stays the run that calls no judge.

Goal and Plan

Claude Code has a goal and a plan of its own, and p4-phi has machinery on the same ground: a Stop hook that sends a turn back while steps are open, a turn its hooks module starts after a wait, and a mark that a session's task was shown done. This section says what the docs state of each, what seven live probes showed on 2026-11-19, and which of p4-phi's pieces a goal covers. The probes ran with a probe mod of their own, p4-goal-probe, through claude -p in a scratch project on Claude Code 2.1.328 and in four sessions the desktop app started on its own Claude Code 2.1.326, and they changed no file of the repository.

What the docs say

  • A goal is one completion condition a session works toward across turns. Source, goal.md, the opening: "After each turn, a model checks whether the condition holds. If the model judges it not yet met, Claude starts another turn instead of returning control to you."
  • A person sets it by the command. Source, goal.md, "Set a goal": "Run /goal followed by the condition you want satisfied." and "Setting a goal starts a turn immediately, with the condition itself as the directive." The page names no tool, hook output or setting that sets one, and claude -p "/goal <condition>" is its one form with nobody at a prompt.
  • A goal is a Stop hook. Source, goal.md, "How evaluation works": "/goal is a wrapper around a session-scoped prompt-based Stop hook." Its evaluator is the small fast model, which answers not yet met, met or impossible, and by "Evaluation model and cost" it "does not call tools, so it can only judge what Claude has already surfaced in the conversation".
  • A loop that makes no progress ends with the goal still set. Source, the same section: after several turns in a row with no tool use Claude Code "stops the loop, prints a warning, and returns control to you with the goal still set. Evaluation resumes after your next prompt." The page points to hooks-guide.md, "Stop hook hits the block cap", for the count under it.
  • A settings Stop hook is the documented neighbour of a goal and no copy of it. Source, goal.md, "Compare ways to keep a session running": "A Stop hook lives in your settings file, applies to every session in its scope, and can run a script for deterministic checks or a prompt for model-evaluated ones."
  • A hooks module can run a slash command. Source, the types file of the build, on $.command.run: "Runs a slash command as if the person typed /command args: the event command.run, queued and run once the session is idle." The same file lists three built-in tools, SetGoal, GetGoal and PauseGoal, and plugins/mods/api.md, "What refused calls return", names a tool call that "starts background work, a schedule or a goal".
  • Plan mode has a session explore and write a plan to a file before any edit, and the plan waits for an approval. Source, permission-modes.md, "Analyze before you edit with plan mode" and "Review and approve a plan", and settings-reference.md, the entry plansDirectory, which puts plan files under ~/.claude/plans unless a project names another folder.
  • The desktop app has a Plan pane among a session's panes. Source, desktop.md, "Arrange your workspace". No page says what the pane holds, and no page sets the plan beside the task list.
  • The task list p4-phi reads is neither of those: it is the list of the app's mcp__ccd_turn__update_plan tool, which the app shows under a session's latest message.

What a goal covers of p4-phi, and what it does not

  • The Stop send-back is the piece a goal covers. plans.keep_going sends a turn back to the next open step of the task list, and a goal sends it back until its condition holds. A goal cannot be set from outside a session, so the session that starts a worker sets none: the worker's own hooks module does, with $.command.run, once its first turn has ended.
  • The done mark is covered in part. A met verdict is Claude Code's own record that the condition holds, given by a separate model. A command hook cannot read it at the Stop it belongs to, so it is read once turn.complete has fired.
  • The wake after a wait is covered in part. Under a goal a turn does not end while the condition is unmet, and after the block cap a worker's report starts the evaluation again. The turn the hooks module starts for upkeep that is due is no part of a session's condition and stays.
  • What the evaluator cannot do stays a Stop hook: it reads one transcript, runs nothing and reads no file, so the regression test of a worker's issue, the commits on the default branch and an open issue are checked by phi.py's Stop hook as before. The evaluator also cannot know that a step waits on another session, and a session that waits under a goal is sent back until the cap of eight ends the loop.
  • Nothing else of p4-phi is covered. The mirror of the task list, a session's task, the turn record and the reports, the request ledger, the board, the watcher's ledger, the state pages, the steps that wait and the follow-through items all reach past one session, and a goal is set, judged and shown inside one.
  • The plan copies nothing p4-phi builds. p4-phi puts no session in plan mode, and the list it mirrors is the app's update_plan list, which the Plan pane does not show.

The goal behind its setting

  • Since a probe showed a goal set with no click, p4-phi sets one where a project asks for it: goal in the store's phi/phi.json, false unless set true, with P4_PHI_GOAL as 0 or 1 for one run. phi.py goal on and phi.py goal off write the key and print how it stands, since a session writes nothing under .claude with its own tools. With it off nothing below happens and the Stop send-back works as before.
  • The condition is the line Done looks like: of a worker's brief, kept whole from its first message. A session nobody started gets no goal, and neither does a brief with no such line.
  • The worker's hooks module sets the goal once its first turn has ended: the look that turn's end asks for answers the condition once, the module runs $.command.run({ command: 'goal', args }), and when the command answers Goal set it tells phi.py goal set.
  • While the goal is set plans.keep_going sends no turn back, since the goal's evaluator does and the two share the one count of eight. A goal the command did not set stands nothing down.
  • The checks only a script can make stay the Stop hook they are: the regression test of a worker's issue, the commits on the default branch and the open issue run in phi.py's Stop hook under a goal as without one.
  • The done mark reads the goal's verdict. The look after a turn's end reads the last goal_status row of the transcript: a goal met marks the turn done with the evaluator's reason, on the worker's row and on the row its starter reads, and a goal met, judged impossible or cleared is over, so the send-back is back.
  • Seen on 2026-11-19 with Claude Code 2.1.328 and the development copy, in a scratch project whose records made the session a worker: with goal true the first turn wrote a file and ended, the module ran /goal with the brief's line, the row Goal set: followed with the origin { kind: 'plugin', name: 'p4-phi' }, the evaluator judged the goal met at the next Stop, and the look marked the turn goal met: with the evaluator's reason on both rows. With goal unset the same brief ran one turn and left no goal row.
  • That run was a claude -p session held open on its input, since a run that exits at its first turn's end is gone before the look answers. The same goal in a worker of the desktop app, set by the installed copy, is not yet seen.
