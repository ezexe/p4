A puppeteer and the sessions it controls

Since version 0.10.0, p4-phi knows a session that controls the top sessions of other trees. ezexe files a top session in the sidebar section “puppeteers”, and it controls the topmost orchestrating sessions of one or more projects. Make each move on the model below, read the line phi hands out, and watch the board rewrite itself.

  • The filing makes it one.A puppeteer is a top session that the app's own file shows in the section “puppeteers”. phi reads that file each time it matters and keeps no mark of its own.
  • The mark is a pair.The puppeteer records each session it controls with phi.py controls. A controlled session stays the top of its own tree, in its own section, and is told of its puppeteer once.
  • Its state lives on a board.A puppeteer's context only grows, so phi keeps board.md for it, hands it reports by reference, and names the point where compacting is safe.

What holds the rule up

    
The rule began as ezexe/p4#58. scripts/controls.py holds it, and scripts/test_controls.py proves it.

    

      

        
How phi knows a puppeteer

        
    
          
  • A hook cannot call the app's tools, but the app keeps the sidebar on disk. claude_desktop_config.json, beside the app's claude-code-sessions folder, holds preferences.epitaxyPrefs["dframe-group-scopes"].
    • 
          
  • Each scope there has groups, with an id and a name, and assignments, which map code:<sessionId> to a group id.
    • 
          
  • A session is a puppeteer when it is a top session and that file assigns it to a group named “puppeteers”. A child filed there is not one.
    • 
          
  • A file that is missing or shaped otherwise makes nobody a puppeteer.
    • 
          
  • Nothing stops a session from filing itself, since the app asks nobody. The rule rests on ezexe's filing. phi says once, in the session and on its record, that it saw the session there, and every session it lists is told who claims it.
    • 
        

      

      

        
Where the pair is kept

        
    
          
  • The puppeteer's record is where every top session's is: session.json in the store of the folder it was opened in.
    • 
          
  • controls on that record lists each controlled session with the store its tree lives in.
    • 
          
  • A controlled session's own hook finds the pair and keeps puppeteer on its own record.
    • 
          
  • Each side reads the other's store, and neither writes into it. A request stays in the requester's store, and what became of it stays on the puppeteer's record.
    • 
          
  • A top session that a puppeteer starts in another project keeps its record in that project's store, from its first message on.
    • 
        

      

      

        
What a puppeteer does itself

        
    
          
  • It tells ezexe in one place where each controlled session stands, each by its full title, and relays ezexe's rule changes to all of them.
    • 
          
  • It writes no plugin or project files. phi gives it this as text and does not block its edits.
    • 
          
  • Its plan gets no hand-off advice and no nudge. Waiting on reports, and the few read-only checks against git and GitHub, are its own work.
    • 
          
  • Its turn may end on a step that waits on, awaits or collects the reports of sessions it controls, while one of them is not yet complete. Every other top session is sent back to its next open step.
    • 
          
  • Deleting data, force pushes and publishing still need ezexe's yes in the session that acts.
    • 
        

      

      

        
What phi refuses

        
    
          
  • controls from a session that is not a puppeteer, and nothing is recorded.
    • 
          
  • controls naming the puppeteer itself, a session the app holds no record of, or a session another session started. A child is reached through its top.
    • 
          
  • A puppeteer's archive of a session it does not control, unless the session is in a controlled tree, in the puppeteer's own tree, or is the puppeteer that handed over to it.
    • 
          
  • Its archive of a session that is mid-turn, has an open plan step, a running background task, a session still working under it, a start request of its own waiting, or an issue-closing commit on no remote branch.
    • 
          
  • An archive call whose reason is shorter than twelve characters.
    • 
          
  • A controlled session's own start of a new top session.
    • 
          
  • controls --decline with no open request of that id, or with no real reason.
    • 
          
  • controls --from naming a puppeteer that has not run controls --hand for this session.
    • 
          
  • request --to-puppeteer from a session that has no puppeteer.
    • 
        

      

      

        
What phi does not do

        
    
          
  • It does not compact a session, start a successor or move a session between sections. Those are the app's tools, and the puppeteer makes the calls phi names.
    • 
          
  • It speaks only when a hook fires. A boundary reached while the puppeteer is idle is named beside its next message.
    • 
          
  • The character count covers what phi's own hooks handed, so it is a floor under the context's real size.
    • 
          
  • It does not withdraw a tree's own start request. A puppeteer may decline only a request addressed to it.
    • 
          
  • For every other session the archive rule of ezexe/p4#49 is unchanged.
    • 
        

      

      

        
Two keys, both optional

        
    
          
  • phi.puppeteer_section names the sidebar section. It is “puppeteers” when the key is absent, and an empty string turns the rule off.
    • 
          
  • phi.puppeteer_chars is the number of characters phi may hand a puppeteer between compactions before the boundary notice says so. It is 200000 when the key is absent.
    • 
          
  • After three compactions the notice offers a successor in place of “Later”.
    • 
        

        
{
 "phi": {
  "puppeteer_section": "puppeteers",
  "puppeteer_chars": 200000
 }
}

      

    

  


  

    
One command, five forms

    
Only a puppeteer may run it. Every form ends by rewriting the board and printing where each controlled session stands.

    

      

        
The commandWhat it does

        
          
phi.py controlsPrints each controlled session by its full title, with its store, its state and what phi's records hold against archiving it. Then it prints the archive calls phi let through or refused, and the board's path.

          
phi.py controls <sessionId> ...Records the top sessions ezexe put under this puppeteer.

          
phi.py controls --drop <sessionId>Ends a pair. The dropped session is told once that it has no puppeteer.

          
phi.py controls --decline <request id> "<why>"Declines a request for a new top session. The requester is told at its next message and starts no session for it.

          
phi.py controls --hand <sessionId>Marks the hand-over to a fresh puppeteer on the old one's record.

          
phi.py controls --from <sessionId>Run by the successor. It takes over the same controlled sessions and the old puppeteer's notes.

        
      

    

  


  

    
A word that is already taken

    
Since ezexe/p4#38, puppeteer.py is every orchestrator's watcher. The puppeteer on this page is narrower: the one session ezexe filed in the section, paired with the sessions it controls. The phi skill says which is meant where both appear.

  


  

    Every rule, call and line here is read from the plugin's source: controls.py, phi.py, starts.py, plans.py, gaps.py and the phi skill, in ezexe/p4 under lbiza/plugins/p4-phi. The projects, titles and ids on this page are invented, and the model lives in your browser. Nothing on this page reaches a real session.
