A puppeteer and the orchestrators it controls

ezexe files one orchestrator in the sidebar section “puppeteers”, and that makes it a puppeteer: it controls the orchestrators of one or more projects, which stay at the top of their own trees. p4-phi reads the filing, hands the puppeteer its lines beside each message, keeps its board, and names the sessions its records hold complete, while every archive call waits on the app's approval card for ezexe. Make each move on the model below, read the lines p4-phi hands out, and watch the board rewrite itself.

  • The filing makes it one.A puppeteer is an orchestrator that the app's own file shows in the section “puppeteers”. p4-phi reads that file each time it matters and keeps no copy of its own.
  • A record on each side.The puppeteer records each orchestrator it controls with phi.py controls, as controls on its own session.json. A controlled session stays at the top of its own tree, in its own section, and keeps puppeteer on its own record.
  • Its state lives on a board.Claude Code compacts a puppeteer's context by itself, so p4-phi keeps board.md for it, hands it each report as one line and a page, and hands it the board's path first after every compaction.

What holds the rule up

    
scripts/controls.py holds the rule, scripts/phi.py runs it from p4-phi's hooks, and scripts/test_controls.py tests it.

    

      

        
How p4-phi knows a puppeteer

        
    
          
  • p4-phi's hooks are command hooks, which call none of the app's tools, but the app keeps the sidebar on disk. claude_desktop_config.json, beside the app's claude-code-sessions folder, holds preferences.epitaxyPrefs["dframe-group-scopes"].
    • 
          
  • Each scope there has groups, each with an id and a name, and assignments, which map code:<sessionId> to a group id.
    • 
          
  • A session is a puppeteer when no session started it and that file assigns it to a group named “puppeteers”. A worker filed there is not one.
    • 
          
  • A file that is missing or shaped otherwise makes nobody a puppeteer.
    • 
          
  • Nothing stops a session from filing itself, since the app asks nobody. The rule rests on ezexe's filing: p4-phi says once, in the session and on its record as puppeteerSeen, that it saw the session there, and tells each session it lists which session controls it.
    • 
        

      

      

        
Where each side's record is kept

        
    
          
  • The puppeteer's record is where every orchestrator's is: session.json in the store of the folder it was opened in.
    • 
          
  • controls on that record lists each controlled session with the store its tree lives in, and marks started on each one the puppeteer started itself.
    • 
          
  • A controlled session's own hook finds the puppeteer that lists it and keeps puppeteer on its own record. A puppeteer that has handed over to a successor counts for none of them.
    • 
          
  • Each side reads the other's store. A request stays in the store of the session that filed it, and what became of it stays on the puppeteer's record. The one row a puppeteer's hook writes into a controlled session's store is the claimed row of a start request it starts on that session's behalf.
    • 
          
  • An orchestrator the puppeteer starts in another project keeps its record in that project's store.
    • 
        

      

      

        
What a puppeteer does itself

        
    
          
  • It tells ezexe in one place where each controlled session stands, each by its full title, and sends the feedback and user memories ezexe changes to all of them with SendMessage.
    • 
          
  • It writes no plugin or project files. p4-phi tells it so in the line it hands the puppeteer once.
    • 
          
  • Its task list gets no advice to hand its steps out and no nudge. Waiting on reports, and the few read-only checks against git and GitHub, are its own work.
    • 
          
  • Its turn may end on a step that waits on the sessions it controls while one of them is still working, holds something open or is not shown done.
    • 
          
  • It publishes the issues the Finding: lines of its trees need, and places the session that resolves each.
    • 
          
  • When it messages a controlled session whose write set another controlled tree still holds, p4-phi warns it once, naming the holder by its full title and what frees the files, and never blocks the message.
    • 
        

      

      

        
What p4-phi refuses

        
    
          
  • controls from a session that is not a puppeteer, and nothing is recorded.
    • 
          
  • controls naming the puppeteer itself, a session the app holds no record of, or a session another session started. A worker is reached through its orchestrator.
    • 
          
  • A controlled session's own start of a session whose brief says This session is a new top session, the line every new orchestrator's brief carries.
    • 
          
  • controls --decline with no open request of that id addressed to this puppeteer, or with a reason shorter than twelve characters.
    • 
          
  • controls --from naming a puppeteer that has not run controls --hand for this session.
    • 
          
  • request --to-puppeteer from a session no puppeteer lists, or with a brief that has no Files: line.
    • 
          
  • controls --hand naming the puppeteer itself or a session the app holds no record of.
    • 
        

      

      

        
What p4-phi does not do

        
    
          
  • It does not compact a session, and a boundary carries no compact question and no line for ezexe to type. The context window page says: “Claude Code compacts automatically as you approach the limit, so a full context window doesn't end your session.”
    • 
          
  • It does not start a successor, move a session between sections or archive one. Those are the app's tools, and the session makes the calls.
    • 
          
  • It speaks only when one of its hooks fires, so a boundary reached while the puppeteer is idle is named beside its next message. A command hook with asyncRewake could wake it at once, and SendMessage with notify_when_idle could tell it when a session goes idle, and p4-phi uses neither.
    • 
          
  • It hands a start request only to the session that filed it. A puppeteer may decline only a request addressed to it, and the hook of the session that filed it then closes the row as withdrawn.
    • 
          
  • It refuses no archive call. The settings keeper writes an ask rule on mcp__ccd_session_mgmt__archive_session, so the app shows its approval card before every archive call, bypass mode included, and the tool refuses a session with live background work itself.
    • 
        

      

      

        
One key, optional

        
    
          
  • phi.puppeteer_section names the sidebar section. It is “puppeteers” when the key is absent, and an empty string turns the rule off.
    • 
        

        
{
 "phi": {
  "puppeteer_section": "puppeteers"
 }
}

      

    

  


  

    
One command and its flags

    
Only a puppeteer may run it. Every form ends by rewriting the board and printing where each controlled session stands.

    

      

        
The commandWhat it does

        
          
phi.py controlsPrints each controlled session by its full title, with its store, its state and what p4-phi's records hold against calling it complete. Then it prints when p4-phi first saw this session in the section and the board's path.

          
phi.py controls <sessionId> ...Records the orchestrators ezexe put under this puppeteer, each printed as controlled: "<title>" `<sessionId>`, store <store>.

          
phi.py controls --drop <sessionId>Ends the control of a session, printed as dropped from control: <sessionId>. The dropped session is told once, at its next message, that it has left the puppeteer's control.

          
phi.py controls --decline <request id> "<why>"Declines a request for a new orchestrator. The session that filed it is told at its next message, and starts no session for it.

          
phi.py controls --hand <sessionId>Run by the old puppeteer: keeps its hand-over to the successor on its own record.

          
phi.py controls --from <sessionId>Run by the successor. It takes over the old puppeteer's controlled sessions, its notes, its declined requests and the memories ezexe changed during the run.

        
      

    

  


  

    
The puppeteer and the watcher

    
A puppeteer is a session. The watcher is a process: puppeteer.py runs one in the background for each orchestrator, and it rewrites that orchestrator's ledger.md from p4-phi's records and the app's session records when one of them changes, with a reconcile line for each divergence between the two. phi.py ledger prints the ledger and rewrites it when it changed, and phi.py settle <sessionId> "<what took it up>" clears a session's row from the ledger's section of work left unfinished at an archive. A puppeteer has a watcher and a ledger like every orchestrator, and its board is a page of its own beside them.

  


  

    Every rule, call and line here is read from p4-phi's source: controls.py, phi.py, starts.py, relay.py, plans.py and puppeteer.py, in ezexe/p4 under lbiza/plugins/p4-phi/scripts. A command shown as <p4-phi>/scripts/phi.py carries the plugin folder's absolute path in the lines p4-phi prints. The projects, titles and ids on this page are invented, and the model runs in your browser. Nothing on this page reaches a real session.
